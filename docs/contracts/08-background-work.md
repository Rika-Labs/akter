# Workflows, schedules, and external effects

**Responsibility:** define workflows, schedules, and provider calls.
**Authority:** normative.  
**Owner role:** reliability/runtime.  
**Change policy:** provider support requires a written adapter contract and fault tests.

There is one actor kind: `Actor.make`. `key: Actor.singleton` MUST provide `X.get()` without an id, one cluster-wide activation (whose build may fork one background loop with `Effect.forkScoped`), and cluster-wide cron. `policy.cron` maps expressions to zero-input commands in `api`, with optional `policy.cronSkipIfOlderThan`; on named or minted actors it is per actor, and on a singleton it is once per deployment, in the deployment's default tenant ([ADR 0010](../decisions/0010-one-way-effect-native-api.md), [ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)).

Each cron entry MUST have at most one pending tick, an outbox timer keyed `$cron:<expression>` on its actor's shard. A named or minted actor's first committed turn in a generation writes missing ticks; runners write a singleton's missing ticks at startup. Only a runner that registers the actor type may claim, skip, or delete its ticks. A tick is delivered as a direct command whose caller is `System({ source: "cron", ref })` with no `onBehalfOf` and whose command id is the tick's intent id. After its receipt commits, the relay MUST rewrite the row to the first scheduled time after now, so ticks of one entry never overlap and missed ticks are never replayed one by one. A tick older than `cronSkipIfOlderThan` (default 1 day) when claimed is skipped and rewritten. After downtime, a pending tick fires once if it is inside that window. An entry removed by a deploy is deleted when its next tick is claimed; a tick already claimed still fires once.

Workflows MUST be actor members declared with `Actor.workflow` in `api`. Their body MUST live in `X.toLayer` as `(input) => Effect` and receives `X.Workflow`. A turn starts a workflow only through `X.intents(id)`, which records an outbox intent. Outside turns, calling the workflow on a handle returns a `WorkflowRun`.

`X.Workflow` MUST provide owner identity and caller attribution. Steps, durable sleep, owner-event waits, and races MUST be the member's typed constructors (`Ship.step`, `Ship.sleep`, `Ship.wait`, `Ship.race`), which compile to Effect's `Activity`, `DurableClock`, and `DurableDeferred`. Execution identity MUST include deployment, tenant, owner actor and id, workflow member, and key. Resume MUST restore tenant and `onBehalfOf` from the durable envelope.

Accepted durable work MUST continue after its originating principal loses access, including trusted internal redelivery and workflow recovery. Revocation blocks new external admissions and result reads, not the recorded obligation. Cancellation is explicit, and applications MAY reauthorize sensitive steps. External command retry expiry MUST NOT discard pending internal work or its deduplication evidence; see [receipts](04-receipts.md) and [retention](../operations/retention.md).

External effects MUST be recorded in the turn and executed after commit with stable identity, retries, and dead-letter visibility. Cancellation cannot undo a completed provider call. Verification: **Workflow tenant isolation**, **waitFor registration**, **Intent rollback**, and **Singleton uniqueness** gates.

Executors live in `X.toEffectLayer`, take `(effect) => Effect`, receive `X.Executor`, and have no database capability. They MUST run outside the relay's claim and settle statements, on a per-runner executor pool with a concurrency limit, so a slow executor cannot delay intent or timer delivery. A runner claims an effect row only when it has that effect's executor. Each attempt's claim is a lease that the runner renews while the attempt runs; an attempt whose lease is lost, or whose lease deadline passes on the runner's clock, MUST be interrupted. After a lease ends another runner may start the next attempt. Two attempts of one effect can therefore overlap. The first success of any attempt is routed and no later result is; a failure from an attempt that lost its lease MUST NOT overwrite a newer attempt's record; a success that arrives after the dead letter MUST mark that dead letter `ambiguous`. The attempt timeout and backoff are per-effect policy ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)). An executor's return value MUST be delivered to the effect's declared `onSuccess` command through the outbox, with the effect id as the command id. Exhausted retries MUST produce a dead letter and, when declared, deliver `onDeadLetter` once in a new actor turn ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)). A provider's ambiguous outcome MUST remain distinguishable from failure; unsafe retries require provider idempotency or reconciliation.

An effect performed with `turn.perform` MUST be written to `actor_outbox` on the performing actor's shard in the turn transaction, and a declared failure, defect, or rollback MUST discard it. Its executor MUST NOT run before that commit. Each attempt MUST be recorded durably before the executor runs, so an attempt interrupted by a crash counts toward `retry` and its outcome is unknown. The executor's success MUST be recorded in the same statement that turns the effect row into an intent to `onSuccess`, so a lost acknowledgment reruns the executor under the same effect id but at most one result is routed. The dead letter MUST record whether the last attempt's outcome is unknown (`ambiguous`): only a typed executor failure means the provider did not apply the call; a defect, timeout, interruption, or crash leaves the outcome unknown ([API](../api/01-server-api.md)).

Effect cancellation and per-actor effect concurrency caps are **not provided yet**. The rules in the rest of this paragraph are the target from [ADR 0024](../decisions/0024-effect-cancellation-and-per-actor-concurrency.md). That ADR is proposed, and they bind only once M2.13 implements it; until then, a performed effect cannot be withdrawn after its turn commits. `turn.perform(effect, { key })` names an effect within its actor, and `turn.cancelEffect(key)` MUST apply in the cancelling turn's commit, so a turn that rolls back cancels nothing. An effect that has never been attempted MUST be deleted and never run. An effect that has been attempted MUST never be attempted again after cancellation and MUST NOT be dropped silently: it is reported once through `onCancelled` with `Actor.Cancelled(E)` input whose outcome is `Succeeded`, `Failed`, or `Unknown`, and an attempt that may have reached the provider is `Unknown` and `ambiguous`. Without `onCancelled`, a success still routes to `onSuccess` and an unknown outcome is dead-lettered as ambiguous. A running attempt is interrupted best-effort; cancellation never undoes a provider call. Cancelling an effect that already completed changes nothing. `policy.effects[Tag].concurrency.perActor` MUST bound the attempts of that effect type for one actor that hold a live lease, across every runner; waiting rows MUST NOT delay other actors' effects. There is no deployment-wide per-type limit.

Workflow activities persist schema-defined results in `actor_workflow_step` on the owner's shard through the framework's `WorkflowEngine`, outside the originating actor turn; durable clocks are outbox timers. Their command identity derives from execution ID and activity name and remains stable across retries. Durable sleep and owner-event `waitFor` MUST survive restart; `waitFor` returns `Option.none` on timeout and closes the registration race.

[ADR 0022](../decisions/0022-workflow-engine-storage-and-version-markers.md) amends the paragraphs above; where they differ, these rules apply:

- Executions live in `actor_workflow_executions` and their steps in `actor_workflow_step`, both keyed by the owner's `routing_key` with a foreign key to its generation row (migration `0012_workflows`). Engine writes are fenced on the owner's generation. A finished execution keeps only its result, for `policy.keepWorkflows` (default 7 days, at least the retry window).
- The execution id is `w1.` plus the base64url JSON of `[tenant, actor type, actor id, workflow, key]`. The deployment is the database the row lives in, not an encoded component. The key defaults to the start's command id, or comes from `Actor.workflow(tag, { key })`.
- A turn's `later.Ship(input)` returns the execution id. A handle's `order.Ship(input)` returns a `WorkflowRun` with `executionId`, `poll`, `result`, and `interrupt`; `poll` and `result` are admitted like queries and `interrupt` like a command.
- Workflow bodies make actor calls only inside activities, and cannot call `X.intents`. An activity's actor call carries the execution's System caller with `onBehalfOf`, and its command id derives from execution id, step, attempt, and call ordinal. An activity's actor call is not sent once its derived id is within the target's command and delivery timeouts of expiring; the activity dies with `ActivityOutcomeUnknown` instead of being rerun under ids whose receipts may be pruned. This weakens the expiry paragraph above for that case only.
- Every resume is a reserved internal `$workflow/resume` command driven by one keyed outbox timer per execution; a resume that finds the run live preempts it for a settled step or interrupt instead of only re-arming, and a drained activation abandons its run for replay elsewhere. External `DurableDeferred` completion and child workflows are unsupported.
- Each step is a module-level constructor with an explicit, static name; raw primitives or constructors created inside a body MUST die with `Unregistered workflow step`, and dynamic step names are not supported. The registered constructors and the member's `versions` form the manifest. `wf.version(name)` returns the marker value recorded when the execution started (0 if it predates the marker). Startup and `durable workflows check` refuse a deploy when an open execution's workflow, start-manifest steps, recorded marker values, or recorded steps' result schemas are no longer supported, which guards renames and removals. A runner that can't run an execution's step or marker suspends it for a compatible runner, and never fails it.

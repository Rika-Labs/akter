# Workflows, schedules, and jobs

**Responsibility:** define workflows, schedules, and provider calls.
**Authority:** normative.  
**Owner role:** reliability/runtime.  
**Change policy:** provider support requires a written adapter contract and fault tests.

The testing harness's `ActorTest.advance` MUST extend this runner's registered attempt leases by the clock-jump duration before moving its outbox clock. Attempt registration, the running-attempt snapshot, lease extension and the jump MUST serialize with the relay pass, so a claim in progress cannot be omitted. This is a harness guarantee, not a prohibition on overlapping attempts after genuine lease loss.

Capped job claims and waiting-row wakes MUST serialize on their actor's keyed generation row in the actor-data transaction, since one actor's cap counts only rows on its shard. Different actors MAY claim independently. Workflow acceptance MUST use the common coordination authority described in [storage and ownership](06-storage-ownership.md). Fleet maintainer ownership MUST use that authority too, while its feed and derived-row transactions remain on the selected data database; a detected authority-session failure MUST stop the maintainer. A coordination pool is not a multi-shard logical feed ([ADR 0066](../decisions/0066-authoritative-coordination.md)).

There is one actor kind: `Actor.make`. `key: Actor.singleton` MUST provide `X.get()` without an id, one cluster-wide activation (whose build may fork one background loop with `Effect.forkScoped`), and cluster-wide schedules. A singleton's build MUST run on its owner when the singleton activates, not when a runner starts, so its loop exists only in the owning activation; a build that fails does not fail runner startup, and every command to that activation fails with the build's defect until the singleton is rebuilt. An owner whose shard lock in the database is no longer fresh MUST stop its loop and refuse turns before another runner can acquire the lock, so after the owner stalls (for example, lost heartbeats) its loop has stopped before the successor's starts; the database generation fence still rejects any stale turn. A loop MUST reach durable state and external systems only through commands and recorded jobs. `schedules` on `Actor.make` maps cron expressions and intervals to commands in `api` or `internal` whose payload is `Schema.Void`, with optional `policy.maxScheduleLag`; a tick's caller is System, so its target need not be publicly callable ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)); on named or minted actors it is per actor, and on a singleton it is once per deployment, in the deployment's default tenant ([ADR 0010](../decisions/0010-one-way-effect-native-api.md), [ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)).

Each `schedules` entry MUST have at most one pending tick, an outbox timer keyed by its entry (below) on its actor's shard. A named or minted actor's first committed turn in a generation writes missing ticks, each at the first scheduled time after the database clock when the turn writes it; runners write a singleton's missing ticks at startup. Only a runner that registers the actor type may claim, skip, or delete its ticks. A tick is delivered as a direct command whose caller is `System({ source: "cron", ref })` with no `onBehalfOf` and whose command id is the tick's intent id. After its receipt commits, the relay MUST rewrite the row to the first scheduled time after now, so ticks of one entry never overlap and missed ticks are never replayed one by one. A tick older than `maxScheduleLag` (default 1 day) when claimed is skipped and rewritten. After downtime, a pending tick fires once if it is inside that window. A tick whose entry the claiming runner's deployment no longer declares is released for a runner that still declares it, and deleted once it is older than `maxScheduleLag`. A claimed tick whose expression the claiming runner's deployment maps to a different command delivers that command on the same claim with the tick's intent id, unless a receipt for that id already exists, in which case the tick already fired and the row is rewritten to its next time; a tick already claimed still fires once, so a handler whose outcome depends on durable state MUST recheck that state.

A `schedules` entry MAY name an IANA time zone (`CRON_TZ=<zone> <expression>`, default UTC) or be a fixed interval (`@every <duration>`), and its tick key MUST include the zone or the interval: `$cron:<zone> <canonical expression>` or `$cron:@every <milliseconds>ms` ([ADR 0042](../decisions/0042-cron-time-zones-intervals-and-daylight-saving.md)). A zoned expression is read against the zone's wall clock. A wall-clock time that a spring-forward transition skips MUST fire at the first instant after the gap, once for all skipped matches of that gap; a wall-clock time that a fall-back transition repeats MUST fire once, at its first occurrence, whenever the tick is written or rewritten. An interval fires at every whole multiple of its length since the Unix epoch and ignores zones. The catch-up rule above applies unchanged to both: `maxScheduleLag` is measured in elapsed time from the tick's scheduled instant, and every rewrite moves the row to the first scheduled time after now, so missed zoned times and missed intervals fire at most once.

Workflows MUST be actor members declared with `Actor.workflow` in `api`. Their body MUST live in `X.toLayer` as `(payload) => Effect` and receives `X.Workflow`. A turn starts a workflow only through `X.intents(id)`, which records an outbox intent. Outside turns, calling the workflow on a handle returns a `WorkflowRun`.

`X.Workflow` MUST provide owner identity and caller attribution. Steps, durable sleep, owner-event waits, and races MUST be the member's typed constructors (`Ship.step`, `Ship.sleep`, `Ship.wait`, `Ship.race`), which compile to Effect's `Activity`, `DurableClock`, and `DurableDeferred`. Execution identity MUST include deployment, tenant, owner actor and id, workflow member, and key. Resume MUST restore tenant and `onBehalfOf` from the durable envelope.

Accepted durable work MUST continue after its originating principal loses access, including trusted internal redelivery and workflow recovery. Revocation blocks new external admissions and result reads, not the recorded obligation. Cancellation is explicit, and applications MAY reauthorize sensitive steps. External command retry expiry MUST NOT discard pending internal work or its deduplication evidence; see [receipts](04-receipts.md) and [retention](../operations/retention.md).

Jobs, the framework's staged external calls, MUST be recorded in the turn and executed after commit with stable identity, retries, and dead-letter visibility ([ADR 0063](../decisions/0063-framework-simplification.md) names them jobs so they are not confused with the Effect library). Cancellation cannot undo a completed provider call. Verification: **Workflow tenant isolation**, **waitFor registration**, **Intent rollback**, and **Singleton uniqueness** gates.

Executors live in `X.toJobLayer`, take `(job) => Effect`, receive `X.Executor`, and have no database capability. They MUST run outside the relay's claim and settle statements, on a per-runner executor pool with a concurrency limit, so a slow executor cannot delay intent or timer delivery. A runner claims a job row only when it has that job's executor, and claims no more rows than its pool has free permits, so no claimed row waits locally while its lease runs down. Each attempt's claim is a lease that the runner renews while the attempt runs; an attempt whose lease is lost, or whose lease deadline passes on the runner's clock, MUST be interrupted. After a lease ends another runner may start the next attempt. Two attempts of one job can therefore overlap. The first success of any attempt is routed and no later result is (to `onCancelled` when the job was cancelled, [ADR 0024](../decisions/0024-effect-cancellation-and-per-actor-concurrency.md)); a failure from an attempt that lost its lease MUST NOT overwrite a newer attempt's record; a success that arrives after the dead letter MUST mark that dead letter `ambiguous`. Each settle is one write guarded by the row's attempt and cancellation state, decided from the attempt's exit and the row before it is written. The attempt timeout and backoff are per-job binding policy ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)). An executor's return value MUST be delivered to the job's declared `onSuccess` command through the outbox, with the job id as the command id. Exhausted retries MUST produce a dead letter and, when declared, deliver `onDeadLetter` once in a new actor turn ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)). A failure that retrying cannot help, such as a result the `onSuccess` command cannot accept, exhausts the job with retries left: it MUST be recorded durably before its dead letter, so no later claim runs the executor again even if the dead letter fails to commit. An attempted job that is cancelled MUST instead be reported once through `onCancelled`, whose payload is `Actor.Cancelled(J)`; `onSuccess` keeps the executor's return type and `onDeadLetter` keeps `Actor.DeadLetter(J)` ([ADR 0024](../decisions/0024-effect-cancellation-and-per-actor-concurrency.md), amending ADR 0012 §3). A provider's ambiguous outcome MUST remain distinguishable from failure; unsafe retries require provider idempotency or reconciliation. [ADR 0030](../decisions/0030-executor-progress-frames.md) (M2.18; delivered to opted-in connections and streams since M2.18): an executor MAY also report transient progress with `X.Executor.progress`; progress never changes an attempt's outcome, is never written to the database, and follows [realtime](07-realtime.md)'s progress exception.

A job enqueued with `turn.enqueue` MUST be written to `actor_outbox`, as a row of kind `job`, on the enqueuing actor's shard in the turn transaction, and a declared failure, defect, or rollback MUST discard it. Its executor MUST NOT run before that commit. Each attempt MUST be recorded durably before the executor runs, so an attempt interrupted by a crash counts toward `retry` and its outcome is unknown. The executor's success MUST be recorded in the same statement that turns the job row into an intent to `onSuccess`, so a lost acknowledgment reruns the executor under the same job id but at most one result is routed. The dead letter MUST record whether the last attempt's outcome is unknown (`ambiguous`): only a typed executor failure means the provider did not apply the call; a defect, timeout, interruption, or crash leaves the outcome unknown ([API](../api/01-server-api.md)). Built by M4.7 ([ADR 0032](../decisions/0032-event-and-effect-payload-evolution.md), accepted): job rows and dead letters store the job's payload version and decode through its chain on each attempt and when a route is built; a settled job row that becomes its route intent resets the version to 0; a payload that fails to decode fails the attempt without clearing earlier ambiguity. Migration `0026_jobs` renamed the stored vocabulary (outbox kind `job`, keyed-job prefix `$job:`, dead-letter columns `job_id` and `job`, payload-version kind `job`, and the `durable.jobs` view) in place, keeping every row's id, attempts, ambiguity, and cancellation mark.

Job cancellation and per-actor job concurrency caps are implemented by M2.13 (migration `0015_effect_control`) as accepted in [ADR 0024](../decisions/0024-effect-cancellation-and-per-actor-concurrency.md). `turn.enqueue(job, { key })` names a job within its actor, and `turn.cancelJob(key)` MUST apply in the cancelling turn's commit, so a turn that rolls back cancels nothing. A job that has never been attempted MUST be deleted and never run. A job that has been attempted MUST never be attempted again after cancellation and MUST NOT be dropped silently: it is reported once through `onCancelled` with `Actor.Cancelled(J)` payload whose outcome is `Succeeded`, `Failed`, or `Unknown`, and an attempt that may have reached the provider is `Unknown` and `ambiguous`. Without `onCancelled`, a success still routes to `onSuccess` and an unknown outcome is dead-lettered as ambiguous. A running attempt is interrupted best-effort; cancellation never undoes a provider call. Cancelling a job that already completed changes nothing. A job binding's `concurrency.perActor` MUST bound the attempts of that job type for one actor that hold a live lease, across every runner; waiting rows MUST NOT delay other actors' jobs. There is no deployment-wide per-type limit.

Workflow activities persist schema-defined results in `actor_workflow_step` on the owner's shard through the framework's `WorkflowEngine`, outside the originating actor turn; durable clocks are outbox timers. Their command identity derives from execution ID and activity name and remains stable across retries. Durable sleep and owner-event `waitFor` MUST survive restart; `waitFor` returns `Option.none` on timeout and closes the registration race.

[ADR 0022](../decisions/0022-workflow-engine-storage-and-version-markers.md) amends the paragraphs above; where they differ, these rules apply:

- Executions live in `actor_workflow_executions` and their steps in `actor_workflow_step`, both keyed by the owner's `routing_key` with a foreign key to its generation row (migration `0012_workflows`). Engine writes are fenced on the owner's generation. A finished execution keeps only its result, for `policy.keepWorkflows` (default 7 days, at least the retry window), and is pruned even after its actor type drops the workflow.
- The execution id is `w1.` plus the base64url JSON of `[tenant, actor type, actor id, workflow, key]`. The deployment is the database the row lives in, not an encoded component. The key defaults to the start's command id, or comes from `Actor.workflow(tag, { key })`.
- A turn's `later.Ship(payload)` returns the execution id. A handle's `order.Ship(payload)` returns a `WorkflowRun` with `executionId`, `poll`, `result`, and `interrupt`; `poll` and `result` are admitted like queries and `interrupt` like a command.
- Workflow bodies make actor calls only inside activities, and cannot call `X.intents`. An activity's actor call carries the execution's System caller with `onBehalfOf`, and its command id derives from execution id, step, attempt, and call ordinal. An activity's actor call is not sent once its derived id is within the target's command and delivery timeouts of expiring; the activity dies with `ActivityOutcomeUnknown` instead of being rerun under ids whose receipts may be pruned. This weakens the expiry paragraph above for that case only.
- Every resume is a reserved internal `$workflow/resume` command driven by one keyed outbox timer per execution; a resume that finds the run live preempts it for a settled step or interrupt instead of only re-arming, and a drained activation abandons its run for replay elsewhere. External `DurableDeferred` completion and child workflows are unsupported.
- Each step is a module-level constructor with an explicit, static name; raw primitives or constructors created inside a body MUST die with `Unregistered workflow step`, and dynamic step names are not supported. The registered constructors and the member's `versions` form the manifest. `wf.version(name)` returns the marker value recorded when the execution started (0 if it predates the marker). Startup and `akter workflows check` refuse a deploy when an open execution's workflow, payload schema, start-manifest steps (or the start manifest itself, if missing), recorded marker values, or recorded steps' result schemas are no longer supported, which guards renames and removals. A runner that can't run an execution's step or marker, lacks its start manifest, would decode its payload or a recorded result under another schema, or finds it started under a newer accepted manifest whose shared steps' result schemas differ from its own, suspends it for a compatible runner, and never fails it. Starting an execution restores its start manifest if retention pruned it while an older deployment's runner still serves. A runner that resumes an execution whose start manifest declares other result schemas for steps not yet settled makes its own manifest the execution's start manifest, so the results it records are compared against the schemas that wrote them. Startup skips the comparison only when no open execution started under another manifest, and `akter workflows check` reads one repeatable-read snapshot.

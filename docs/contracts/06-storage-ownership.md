# Storage and ownership

**Responsibility:** define relational storage behavior.  
**Authority:** normative.  
**Owner role:** database/runtime.  
**Change policy:** Drizzle, Postgres, and each backend adapter must agree on the supported query matrix.

`actor_state` MUST use keyed rows scoped by `(routing_key, tenant_id, actor, actor_id, key)`. A command turn MUST decode stored values through the complete `migrations` chain before the handler and MUST write the current shape on successful handler commit. A later turn in the same activation MAY reuse the decoded value while the generation fence holds; the cached value changes only after a successful commit. An unhandled declared failure MUST discard migration writes along with the other business changes. `policy.maxStateBytes` MUST be enforced on the encoded value before compression and before business state commits.

Each keyed value is the schema-encoded JSON, compressed into `bytea` by a versioned codec; state is opaque to SQL, and queryable data belongs in actor tables ([ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md)). Codec version 1 is one plain zstd frame with no dictionary; there are no per-actor-type dictionaries. Every stored value MUST remain decodable by the codec version that wrote it. Current rows carry no codec column and need none: all of them are version 1. A change that introduces a second codec MUST first add a per-row codec version through a migration, with existing rows defaulting to 1, and MUST keep decoding version 1 ([ADR 0017](../decisions/0017-m1-record-corrections.md)). An idle actor's state MAY be offloaded to object storage, leaving a `cold_ref`; the next turn MUST rehydrate it before the handler. [ADR 0036](../decisions/0036-cold-tier.md) (accepted; built by L.2) designs it: the pointer lives on `actor_generations`, the fetch happens outside the transaction, and the write-back commits with the first successful turn after its receipt resolves. Activation-local values in the layer's build closure are not transaction-bound state: changes to them are not durable or automatically rolled back. An actor that omits state, tables, events, effects, and blobs still executes fenced, receipted commands; it is not a separate ephemeral kind. Target, built by M4.7 ([ADR 0032](../decisions/0032-event-and-effect-payload-evolution.md), accepted): event values and effect payloads also evolve through declared `Actor.migration` chains, store their payload version beside the value, and upcast on every read; they are never rewritten.

`Actor.blob` declares database-backed binary storage in `actor_blobs` (`bytea` chunks). `turn.blob` permits `get`, `set`, `append`, `compact`, and `delete` in command turns; off-turn readers receive `BlobRead`. Blob writes share the turn transaction and are exempt from `policy.maxStateBytes`; each entry is capped at 8 MiB, one actor's entries together at `policy.maxBlobBytes` bytes and `policy.maxBlobEntries` entries, and a write past any of these caps MUST fail the turn as a deterministic defect rather than be retried, changing nothing even if the handler catches the defect. The entry cap refuses only writes that create an entry. This surface does not promise an external object-storage adapter. Every `actor_blobs` row MUST carry the trusted `routing_key`, `tenant_id`, actor type, and actor id of its actor, supplied by the runtime; application code names only the declared blob and an entry, so equal names in two tenants, two actor types, or two actors never share bytes. `BlobRead` MUST NOT expose mutation, and a blob capability used outside the turn or query that received it MUST fail. Target, built by M4.13 ([ADR 0034](../decisions/0034-tenant-scoped-content-addressed-blobs.md), accepted): `Actor.content` entries are immutable references, written in turns on the actor's shard, to SHA-256-addressed content stored once per tenant on the tenant's routing key. Bytes are read only outside turns, from one snapshot. `Content.upload` and `Content.grant` are the only writes to content, framework writes on the tenant's shard outside turns and queries. Unreferenced content is removed by a grant-gated mark and sweep. Equal content in two tenants never shares bytes.

`Actor.table()` business tables MUST include trusted `routing_key`, `tenant_id`, and `actor_id` ownership columns, and their primary key, unique constraints, and indexes MUST lead with them, so business keys are unique per actor. One actor type owns each table; the runtime records the owner and MUST refuse to start when a declared table is missing, keyed without the ownership prefix, or owned by another actor type. Foreign keys on owned tables are unsupported. `OwnedTable`/`Scoped` mutation is available only in command turns; `ScopedRead` is select-only. The public contract exposes Drizzle types, while the framework binds builders to its transaction and scope. Unsupported or raw mutation that cannot preserve ownership MUST be rejected.

Application writes MUST use scoped row operations; `group` supports read-only joins within the actor's placement group, not mutation. Every supported query-client or backend adapter MUST derive ordinary actor-row read/write scope from trusted context, supply ownership columns on insert, and enforce ownership on update, delete, and upsert. Application code MUST NOT need manual ownership fields or predicates; attempts to override ownership MUST be rejected. An adapter MUST preserve execution-phase permissions, bind writes to the current turn transaction, and reject use of transaction-bound capabilities after that turn ends.

Adapters MUST publish their supported operation matrix and pass the shared ownership and transaction cases. Missing scope, an unsupported operation, or inability to join the turn transaction MUST NOT fall back to an unscoped client or separate transaction. Future advanced mutations require evidence before support expands. Runtime `actor_*` tables are private storage; SQL tools read committed runtime state only through the read-only `durable` inspection views, whose exposed columns are the stable contract and whose every row carries its `tenant_id` and actor identity ([ADR 0028](../decisions/0028-sql-inspection-views.md)). Optional RLS is additional protection, not a replacement for actor ownership or generation fencing. See [adapters](../architecture/05-adapters.md).

One database serves each deployment region. Every framework and business table MUST carry `tenant_id` with composite indexes; optional RLS MUST be applied per table, as the `durable_tenant` policy that `0018_rls` puts on framework tables and `Actor.table` puts on owned tables ([ADR 0051](../decisions/0051-row-level-security.md)). Every framework and actor-owned row MUST also carry the framework-computed `routing_key` of its actor's placement key. `Actor.make` accepts `placement: "tenant"` (default) or `"actor"`; the placement and its encoding version are recorded per actor type, and a deployment that changes either MUST fail at startup. Target, built by M4.11 ([ADR 0033](../decisions/0033-parent-actor-placement.md), accepted): `placement` also accepts `{ parent: P }` for a parent `P` that is itself actor- or parent-placed, at most four levels below the root; a family shares its root's `routing_key` under encoding 1; `actor_placements` records `parent` with its `parent_type`, and a deployment that changes a type's parent type MUST fail at startup like any placement change. Parent placement grants no authority. Tenant placement uses runtime `shardGroup` for compute and Neki shard placement on `routing_key` for data, never a database per tenant. See [ADR 0006](../decisions/0006-scale-rules-placement-and-query-tiers.md).

Cross-actor reads beyond the placement group MUST use declared `Fleet.view` definitions. It MUST NOT grant command-turn authority. See [security](10-security.md) and storage cases in [conformance](../verification/01-conformance.md).

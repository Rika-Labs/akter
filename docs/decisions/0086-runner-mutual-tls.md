# ADR 0086: Mutual TLS between runners

**Status:** implementation decision (2026-10-04), for [#541](https://github.com/Rika-Labs/akter/issues/541); amends [ADR 0068](0068-production-multi-runner.md)'s trusted-peer transport and the runner-to-runner clause of [contract 10](../contracts/10-security.md); the hosted provisioning path below is a proposal that [ADR 0075](0075-deployment-and-runner-orchestration.md)'s gate on hosted peering still covers.

**Responsibility:** authenticate and encrypt runner-to-runner traffic, so runners of one deployment accept messages only from each other, on a network other deployments share.

**Authority:** design decision record.

**Owner role:** security and runtime.

**Change policy:** supersede through a new ADR.

## Context

`Runner.socket` ([ADR 0068](0068-production-multi-runner.md)) carries every runner message (entity requests, replies, holder and connection frames, interrupts) as NDJSON over plain TCP. A peer that can open the port can deliver any of them, so contract 10 allowed this traffic only on an isolated network. That excludes the networks Akter runs on: the local stack puts every deployment's runners on one Docker bridge, and a hosted cell or a self-hoster's VPC shares a subnet among deployments. ADR 0075 consequently admits no peering ingress between hosted runners.

The Effect platform socket layers that `Runner.socket` accepted have no peer authentication, and their TLS server builds its credentials once. Effect's in-place `upgrade` sets no peer verification on Node's server side (a wrapped server socket reports `authorized: false` and the session still proceeds), and Bun's `tls.Server.setSecureContext` does not change what the listener presents or trusts. Both were reproduced before this decision.

## Decision

1. **`Runner.mtls` transport.** `Runner.mtls({ deployment, credentials, refreshEvery? })` is a transport layer for `Runner.socket`. It speaks TLS 1.3 only, on Node's `tls` module, which Bun and Node both implement, through `@effect/platform-node-shared`'s socket server and duplex adapter (now a dependency of `@rikalabs/akter`). The platform plaintext layers remain accepted, for an isolated network only.
2. **Identity.** A runner certificate names its deployment in one URI subject alternative name, `spiffe://akter/deployment/<deployment>` (`Runner.identity(deployment)`); a deployment is 1 to 128 characters of letters, digits, `.`, `_` and `-`. Both sides require the peer's chain to reach an authority in the runner's `ca`, the peer certificate to be inside its validity window, and the certificate to carry exactly one Akter identity, equal to the runner's own. Peers are authenticated by deployment, not by host name: every runner of a deployment is the same principal, and Fargate task addresses are not known when a certificate is issued. The server requests and verifies a client certificate during the handshake and checks the identity before handing the connection to the runner's RPC server, so a plaintext peer, a peer without a certificate, one from an untrusted authority, an expired one and one of another deployment never reach a runner handler. The client checks the server's identity in `checkServerIdentity`, so it never writes a runner message to an impostor.
3. **Credentials and rotation.** `credentials` is an Effect returning PEM `{ ca, certificate, key }`. It runs before the listener opens and then every `refreshEvery` (default one minute). Credentials are validated before use: the leaf carries this deployment's identity and no other, is within its validity window, matches the key, and chains to an authority in `ca`. Invalid credentials refuse startup; on a refresh they are logged at warning level and the previous ones stay in use. The listener chooses its credentials per handshake through its SNI callback (clients always send the same server name), and the client dials with the credentials current at that dial, including reconnects. Established sessions keep the session they authenticated; new connections use the new material. Zero-downtime rotation is therefore:
   - **Leaf and key renewal under one authority:** replace `certificate` and `key`.
   - **Authority rotation:** add the incoming authority to every runner's `ca` and wait until every runner has reloaded; replace each leaf and key with one from the incoming authority; remove the outgoing authority once no runner presents a leaf from it.
4. **Development authority.** `RunnerAuthority.make()` creates a P-256 authority and `issue({ deployment })` a fresh key and certificate for one deployment; `RunnerAuthority.from` restores a saved one. It is for local stacks and tests, and keeps its key in process memory.
5. **Local stack.** The control plane's Docker platform issues every runner and migration container its own key and certificate for its deployment, through `RUNNER_PEER_DEPLOYMENT`, `RUNNER_PEER_CA`, `RUNNER_PEER_CERTIFICATE` and `RUNNER_PEER_KEY`, which travel in the CLI environment like the rest of the snapshot and never in arguments. The authority is saved in `RUNNER_PEER_AUTHORITY_DIR` (a Compose volume), so runners started before and after an API restart trust each other; without the directory it lives as long as the API process. The example runner requires these variables and always peers over mutual TLS, so deployments on the shared Docker network cannot exchange runner messages.
6. **Termination guard.** `Runner.socket` refuses an `entityTerminationTimeout` longer than `shardLockExpiration` minus the effective refresh interval (`min(shardLockRefreshInterval, shardLockExpiration / 3)`), so a runner that loses lock storage stops its activations before another runner may take the shards. The defaults (35 s, 10 s, 15 s) pass; a three-second expiration allows at most two seconds.

## Hosted provisioning (proposal, not built)

Hosted runners are ECS Fargate tasks on Graviton (ARM64) per [ADR 0065](0065-aws-alchemy-infrastructure.md) and ADR 0075. The proposed path:

- **Authority: AWS Private CA in short-lived certificate mode**, one CA per release region, a subordinate of an offline organization root. It issues certificates valid for at most seven days for $50 a month per CA plus $0.058 per certificate (AWS list prices, October 2026). Short lifetimes stand in for revocation, so no CRL or OCSP is needed. CloudTrail and the CA's audit report record every issued certificate, and an end-entity template fixes the key usages.
- **Issuance:** only the control plane may call `acm-pca:IssueCertificate` on that CA. When `DeploymentLifecycle` registers a deployment, and again whenever its certificate passes about half of its lifetime, it generates a P-256 key and requests a certificate whose only URI SAN is the deployment's identity. The key is never logged or recorded in the deployment's environment snapshot.
- **Delivery:** the control plane writes `{ ca, certificate, key }` to one Secrets Manager secret per deployment, encrypted with a regional KMS key. Each deployment's runner task gets a task role that may read only that secret, created with the deployment. That keeps ADR 0075's rule that runner execution roles cannot read platform secrets. The runner's `credentials` Effect reads the secret through the Distilled AWS client, so renewal and authority rotation follow item 3 without restarting tasks.
- **Network:** runner security groups admit peering ingress only from the same deployment's group. Mutual TLS is then the authentication layer and network isolation stays as defense in depth, not the only control.

Rejected for hosted use: a **self-managed authority whose key lives in KMS** (`ECC_NIST_P256`, `kms:Sign`). It costs about $1 a month per key plus $0.15 per 10,000 signatures, against Private CA's per-certificate fee, but Akter would own X.509 encoding and CA hygiene in production, and KMS logs a signature without the certificate it signed. Revisit when per-certificate fees become material: 1,000 deployments renewing at half of a seven-day lifetime issue about 8,600 certificates a month, about $500 a month per region. Also rejected: **a sidecar mesh** (Envoy, App Mesh or ECS Service Connect TLS), which adds a per-task proxy on the hot path and authenticates by service, not deployment. And rejected: **issuing in the runner from a CA key it holds**, because any runner could then mint any deployment's identity.

Self-hosters can supply credentials from any authority that issues the URI SAN (cert-manager, SPIRE, step-ca, Private CA), through the same `credentials` Effect.

## Evidence

- `runtime/peering/transport.test.ts`, on Bun and Node, runs real TLS on loopback. A runner listener serves a peer of its deployment and refuses, without invoking its handler, a peer with no certificate, one from another authority, one for another deployment, an expired one and a plaintext NDJSON peer. A runner's client sends nothing to a listener presenting another deployment's, another authority's or an expired certificate, and only TLS records to a plaintext listener. Rotating the authority, then the leaf and key, then removing the old authority, changes what the listener presents and accepts at each step, ignores invalid refreshes, and keeps an established session working throughout. A client dials with refreshed credentials. Startup refuses another deployment's, expired, mismatched or untrusted credentials. Mutating either side's identity check or the client's per-dial credentials fails these tests or the rotation drill.
- `runtime/peering/authority.test.ts` loads 512 issued certificates into the runtime's TLS stack. BoringSSL in Bun rejects a non-minimal serial, which an earlier encoding produced about once in 128 certificates.
- `crash/drills/production.test.ts` runs the three-process SIGKILL, singleton failover, cron, drain and rolling-restart scenario over plaintext and over mutual TLS on real Postgres, with the same exactly-once accounting. A rotation drill keeps two runners under load while it moves both from the outgoing authority to the incoming one in three steps. It then proves each listener refuses the old authority and presents the new one, and admits a third process that holds only the new credentials. Every acknowledged command, 3,060 increments and 3,060 cross-actor sends, has its receipt and its state.
- `deployments/runners/docker.test.ts` starts real containers and checks that each gets its own key and a certificate that `Runner.mtls` accepts for its deployment and refuses for another, with no key material in its arguments.
- Hot-path cost: the existing Daytona two-runner cohort (two Bun runners, 64 callers over 10,000 keys, about half of the commands forwarded) ran three ordered repeats per transport. Runner CPU per command was 1.054 ms with mutual TLS against 1.055 ms plaintext. Throughput (median 1,526 against 1,466 commands/s) and p99 (129 against 123 ms) stayed inside the run-to-run range of the sandbox, with zero errors on both sides ([BENCHMARKS.md](../../BENCHMARKS.md#runner-mutual-tls-on-the-forwarding-path-541-2026-10-04)).

## Limits

- Authentication happens at the handshake. An established session survives its peer's certificate expiring or its authority being removed until either runner reconnects or restarts; there is no maximum session age.
- Measurements are loopback on one x86-64 host. Cross-host latency, Graviton's TLS throughput, Fargate and the hosted provisioning path above are unverified. Hosted multi-runner peering stays gated by ADR 0075 until that path is built and measured.
- Revocation before expiry is not supported; short-lived certificates and authority rotation are the mechanism.
- The development authority keeps its key in memory and, for the local stack, on a Docker volume; it is not a production authority.

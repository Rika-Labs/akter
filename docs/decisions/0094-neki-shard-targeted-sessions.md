# ADR 0094: Every statement on a routed table runs in a session targeted at its data shard

**Status:** implementation decision (2026-10-05). Demonstrated on `akter-preview` with the framework's 18 per-actor tables routed on its one shard, and on a lab cluster with two data shards. Routing the control plane's tables and splitting its database are later steps.

**Responsibility:** decide how the runtime learns where each `routing_key` bucket lives, which session each statement goes through, how statements on authoritative tables reach the authoritative shard, and how a turn that reaches the wrong shard fails.

**Authority:** implementation decision record. It is step 1 of [ADR 0093](0093-neki-routing-topology.md)'s "Moving to routed actor data later", amends [ADR 0067](0067-due-work-shard-ranges.md) (where the shard map comes from and how a range's session is targeted) and [ADR 0066](0066-authoritative-coordination.md) (which client takes deployment registries), and adds to [contract 06](../contracts/06-storage-ownership.md)'s Neki rule.

**Owner role:** runtime and database.

**Change policy:** supersede through a new ADR.

## Context

[ADR 0093](0093-neki-routing-topology.md) found that a Neki router plans every statement on a `routing_key`-routed table itself and refuses 117 framework statements, the turn's own among them, while a session targeted at the data shard (`__neki.shard`) forwards them unchanged. Before this change the runtime targeted nothing: `ShardMap` was one untargeted range, and a range that named a shard got one session opened with `SET __neki.shard`.

Observed on `akter-preview` and on the `akter-neki-lab` cluster (shards `sh1` authoritative, `sh2` and `sh3` data) on 2026-10-05:

1. **A startup option targets a session.** `options=-c __neki.shard=<uid>` in the startup packet gives a session that `SHOW __neki.shard` reports and on which `EXPLAIN (NEKI_PLAN)` is refused, like `SET __neki.shard`. Combined with `-c __neki.tx_mode=single -c __neki.fanout=single`, all three settings hold.
2. **A targeted session refuses router-managed functions only beside a table.** `SELECT statement_timestamp(), n FROM t`, `SELECT now(), n FROM t`, `SELECT set_config(...), n FROM t` and a `WHERE` that calls `current_setting` are refused with `cannot be forwarded to a shard targeted with __neki.shard`. A statement that reads no table runs: `SELECT set_config('lock_timeout', '1234ms', true), set_config('statement_timeout', ...), set_config('durable.turn', 'on', true)` returns, a following `INSERT` in the same transaction sees `lock_timeout` `1234ms` and `durable.turn` `on` in its column defaults, and the statement timeout cancels a later `pg_sleep`. `SET LOCAL` of a custom setting reaches the shard the same way. Beside a table, `transaction_timestamp()` and `CURRENT_TIMESTAMP` are refused too, and so is a SQL or PL/pgSQL function of the database's own that calls `statement_timestamp()`; `clock_timestamp()` is forwarded.
3. **A targeted session writes wherever it is pointed.** On the lab, a session targeted at `sh2` inserted a row whose key the topology places on `sh3`; it was stored on `sh2`, a keyed read through the router did not find it, and a scatter read did. The router does not check a targeted write's key, so a stale map would misplace rows without an error.
4. **Key-range bounds are values of the shard index expression, in signed order.** On the lab, a `range` index on `routing_key` with bounds `80` and `4000000000000000` split at keys 128 and 2^62; every negative key went to the first shard. A `range` index on `(routing_key >> 56) + 128` with bound `80` split at bucket 0. [`infra/src/neki/topology.ts`](../../infra/src/neki/topology.ts)'s `bucketHex` assumes an unsigned top-byte prefix, which holds for neither.
5. **The topology and its revision are readable by the service role.** `__neki.get_data_topology()` returns the document and `__neki.get_data_topology_revision()` a number that rises with every change; the revision also reads inside a transaction on a targeted session.

## Decision

### Where buckets live

`ShardDirectory` is the live map. On a Neki database, `Database.postgres({ neki: true })` builds it from `__neki.get_data_topology()` and the revision, read in one statement on the authority sessions before anything else starts. It finds the shard group that routes a table of the runtime's database and schema. That group's shard index must be a `range` on `routing_key` or on `(routing_key >> 56) + 128`, and its key ranges must cover the 256 buckets exactly once with every bound on a bucket boundary. Each key range becomes one bucket range naming its shard UID. A schema that routes nothing keeps the one untargeted range, so a database with `routedTables: []` behaves exactly as before. Any other topology stops the runtime at startup with `TopologyRefused`. The map is reread every ten seconds, and when a turn sees a newer revision; a failed reread keeps the last map and logs a warning. On a server without Neki's topology functions, such as Postgres standing in for Neki, there is no directory, and the static `ShardMap` reference applies as before.

A shard UID becomes a startup option, so one that does not match `[A-Za-z0-9_-]+` is refused when the map is checked.

### Which session a statement uses

The `ShardTarget` fiber reference says what a fiber's statements are about: an actor's `{ routingKey }`, resolved against the current map at each checkout, or a scan's `{ shard }`. Undefined means no data shard.

- **Off-turn and query clients** keep one pool for untargeted work and open one pool per data shard on first use, each the same size, whose sessions carry `-c __neki.shard=<uid>` from their startup packet. No statement can reach such a session before its target is set, and nothing that runs on it, `RESET` included, can leave it untargeted. A transaction keeps the session it began on.
- **Turn sessions** come from one turn pool per data shard, with the Neki turn settings as before. A turn resolves its actor's shard once, before it leases.
- **Authority sessions** are the untargeted off-turn pool behind a client of their own (`Authority`). While the map names data shards, deployment registries and other authoritative tables use it (`registry`) even from an untargeted fiber, so a transaction on it never takes in a statement meant for a shard, and a statement made inside a turn never reaches that shard's copy of the table. Deployment-wide locks keep using the designated coordination pool when there is one.

Who sets the target:

| Work                                                                                                                       | Target                                                                                |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| A command turn, its admission, commit and publication; connection, stream and progress handlers                            | the actor's routing key                                                               |
| Relay claims of intents, uncapped jobs, feed, control and subscription rows; capped-job probes and claims; holder liveness | each range's shard, in turn                                                           |
| Settling a claimed intent, cron tick or job attempt; lease extension; waking a capped job's waiting rows                   | the row's routing key                                                                 |
| Subscription expansion and delivery settles                                                                                | the source's routing key; registration writes the source's rows on the source's shard |
| Queries, `exists`, feeds, workflow polls, content references                                                               | the actor's routing key                                                               |
| Tenant content                                                                                                             | the tenant's routing key; the sweep reads every range's references                    |
| Retention, subscription widening and clean-up, payload checks, workflow compatibility, telemetry gauges, operator listings | once per range, each statement bounded by `routing_key BETWEEN` the range's keys      |
| Command dispatch, the relay's delivery of a request, a job executor's own code, a subscriber's delivery                    | none: they are other actors' work or the application's                                |

A scan bounded by its range reads each bucket once even when a shard still holds rows of a range it has handed on, or when one shard holds two ranges. With the default whole-space range the bound is omitted, so a single database runs the same statement as before. A service called from fibers outside the runtime (a transport's, a test's) captures the runtime's map when it is built.

### Statements that change shape on a targeted session

- **Turn admission.** A cold turn's generation insert no longer selects from the `set_config` statement; the timeouts are sent as their own statement first, in the same flight, which the shard applies to the rest of the transaction. A warm turn sends the same statement as before.
- **Turn groups** are off while the map names shards. A group joins turns of different actors in one transaction, which a session targeted at one shard cannot hold.
- **Workflow manifests** are deployment registries. A started execution writes its manifest on the registry client after its own row; executions moved to a newer manifest record it the same way. Compatibility reads executions per range and the manifests on the registry, and merges them. Retention prunes a manifest on the registry once no range reports an open execution under it; an execution that starts under it after that read restores it, as an older deployment's runner already does.
- **Payload clearing** locks the version row on the registry and reads events per range.
- **Clocks.** The runtime's statements already read `clock_timestamp()` on Neki. A handler's own SQL runs on the turn's targeted session, so it must do the same: the cloud runner actor's idle check now compares `last_activity_at` with `clock_timestamp()` instead of `now()`.

### A turn that reaches the wrong shard fails closed

On a map read from Neki, a turn's admission flight carries `SELECT __neki.get_data_topology_revision()` on its targeted session. When the router's revision differs from the map's, the runtime rereads the map before any handler runs. If the actor's bucket is no longer on the leased session's shard, or the router's revision went backwards, the turn drops its cached state and dies with `RetryTurn`: its transaction rolls back, nothing it staged commits, and the activation retries on the shard the new map names. A failed admission flight is checked the same way, so a shard that refuses or loses the turn after a move also leads the next attempt to the new map. A topology change that leaves the actor where it was costs one reread and lets the turn run.

### Authoritative writes inside turns

A turn's session sees only its shard's copy of every unrouted table. An actor type whose turns write such a table (an owned table the topology does not route, or the host's usage-accounting rows) has its turns refused as a deterministic defect when its data shard is not the authoritative shard, and nothing commits. While the actor data and the authority share one shard the copies are the same table, so these turns run as before. This is what [ADR 0093](0093-neki-routing-topology.md)'s third step has to resolve before shards split; this change only stops the write from landing in an empty copy.

## Alternatives rejected

- **`SET __neki.shard` on each session after it opens.** A failed or interrupted `SET` leaves a pooled session untargeted, and a `RESET` can clear it. The startup option has neither gap and costs nothing per checkout.
- **A fence row per bucket on each shard.** A reshard copies rows and keeps the source's by default, so the old shard's fence row would still pass. The topology revision is the router's own statement of where a bucket lives.
- **Routing every statement through one targeted pool and switching its target per checkout.** Neki refuses `SET __neki.shard` inside a transaction, and a session whose target changes between checkouts is exactly the leak the per-range sessions of [ADR 0067](0067-due-work-shard-ranges.md) were built to prevent.
- **Asking the router to plan keyed statements.** It refuses the turn's own statements; that is the problem this decision removes.

## Evidence

- **Postgres.** [`routing.test.ts`](../../packages/akter/src/runtime/database/routing.test.ts) splits the buckets between two shard names and records, for every committed write to the 18 routed tables, the session's target and the shard that holds the row. Turns, cross-shard intents, timers, jobs, capped jobs, cron, and retention leave no mismatch; a lease extended by a caller outside the runtime lands on the row's shard; a warm and a cold turn whose bucket moved after the map was read fail closed and then commit once on the new shard; a turn that writes host rows from a non-authoritative shard is refused and runs on the authoritative one. Removing the lease extension's targeting, or the revision check, fails these tests. [`neki/topology.test.ts`](../../packages/akter/src/runtime/database/neki/topology.test.ts) covers reading the topology documents, signed bounds included, and refusing the ones the runtime cannot map.
- **Statement corpus.** The integration suites of the framework, the API, the edge, deployments, metering and billing ran on Postgres with a map naming one shard and every statement logged with its session's target: 4,312 distinct statements and 530 schema statements. The schema statements were applied to `akter_dev_sess_soak2` on `akter-preview` (18 tables routed on one shard) and to `akter_dev_sess_lab` on the lab (18 tables routed, buckets split between `sh2` and `sh3`) with no refusal. With the statements' Neki text (the outbox clock and commit version the runtime sends on Neki), every statement that names a routed table, 842 of them, was replayed in a rolled-back transaction on a session targeted at each data shard: 855 executions on `akter-preview` and 1,710 on the lab. Two executions were refused on each cluster. One statement is the cold generation insert that selects from `set_config`, refused on every shard: the runtime sends it only on an untargeted session, and it was replayed on a targeted one because the Postgres run only ever sent it on untargeted sessions. The other is the runner idle check's `now()`, refused on `akter-preview` and fixed above; the corrected statement runs there on a targeted session, and on the lab the replay database's `deployment` table came from a test schema without its columns. Two test-only `EXPLAIN (ANALYZE)` statements were refused on targeted sessions as well. Of 3,433 statements replayed untargeted, 88 were refused: 81 reads of the first set of `durable.*` inspection views, taken before the framework's readers moved to [ADR 0095](0095-single-table-inspection-views.md)'s `_v2` views (see below), the fleet maintainer's logical-decoding peek, which reads no table and is refused with or without routing, and 6 test-only statements: Postgres monitoring functions and one statement of the edge's tests. The other failures were foreign keys, missing rows, and test schemas absent from the replay database.
- **API soak on `akter-preview`.** The API on this branch ran for 20 minutes against `akter_dev_sess_soak2` with the 18 tables routed: nine accounts signed up and verified, created an organization, project and deployment each, and polled their deployments every 20 seconds. Receipts grew from 22 to 54, including the eight `CustomerBound` commands a job's success delivers through the job relay; 24 actors were placed. The API logs at `INFO`, and the runtime logs a warning or error for every relay delivery, retention sweep (every minute) and cleanup failure; the log held no warning or error. A targeted session held open beside it lived 25 minutes until the host's network dropped.
- **Two data shards.** On the lab, eight actors split four and four by bucket ran 200 calls over six and a half minutes, covering cross-shard intents, timers, jobs, capped jobs and cron, with no failure. Every row of the five tables counted, 4 generations, 4 states, 524 receipts, 104 events and 4 outbox rows per shard, was on the shard that holds its bucket: negative keys only on `sh2`, non-negative only on `sh3`.

## Limits and open risks

- **Inspector reads stay untargeted.** The inspector reads [ADR 0095](0095-single-table-inspection-views.md)'s single-table `_v2` views on an untargeted session, which the router plans; how it plans them across more than one data shard is not shown. Operator repair reads one receipt from `receipts_v2` on the actor's shard. The first set joins `actor_placements` and is refused with `[122]` once its tables are routed; a targeted session reads it on one shard, but on a split a shard's copy of `actor_placements` is not the authoritative one, so it is not targeted either, and the route step drops it as ADR 0095 orders.
- **Off-turn writes are not fenced by revision.** A relay or job settle sent between a reshard's write switch and the next map reread goes to the old shard. Neki's documentation says the switch blocks source writes to the moved tables while it runs and keeps source rows afterwards; whether a targeted session can still write the retained source rows after the switch is not known. Until that is shown, a split should run with relays stopped or drained.
- **Connections multiply by data shards.** Each runner holds up to the off-turn, query and turn pool sizes once untargeted and once per data shard.
- **Row-level security tenancy on a targeted session** is not shown: a tenant role could not be set in the probe database on either kind of session, for a reason unrelated to targeting.
- Multi-shard atomicity, the reshard workflow, and the control-plane actors' authoritative writes ([ADR 0093](0093-neki-routing-topology.md) steps 3 and 5) are not addressed here.

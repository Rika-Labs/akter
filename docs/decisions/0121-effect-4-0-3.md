# ADR 0121: Adopt Effect 4.0.3 as one dependency cohort

**Status:** implementation decision (2026-10-11).

**0.2 status:** amended (the exact 4.0.3 cohort carries; SQL packages leave it); owned by [ADR 0135](0135-effect-primitive-inventory.md). See the [0.2 registry](0124-engine-rewrite-and-command-log.md#registry-of-earlier-decisions).

## Context

Effect 4.0.3 changes `Crypto.randomUUIDv4` and `Crypto.randomUUIDv7` from effects to functions. Alpha.6's `^4.0.2` peers admit the new version, so a fresh install fails while constructing the runtime. The upstream release also changes SQL transaction cleanup, shared-connection leasing, Cluster handoff and workflow recovery.

With the new cohort, registering singleton keepers can activate a handler before layer construction returns. The existing singleton startup test passes on unmodified main with 4.0.2 and fails on 4.0.3 before a command is sent. Contract 08 separates singleton handler activation from runner startup.

## Decision

Pin the workspace's Effect/platform/SQL/Vitest catalog to 4.0.3 and publish Effect-family peers with a `^4.0.3` floor. Keep the framework's platform-node-shared dependency exactly 4.0.3. Call both Crypto UUID methods with `()` to retain the existing string representation; do not support both API shapes.

Use `Effect.schedule(Schedule.spaced(wakeInterval))` for the singleton keeper instead of `Effect.repeat`. The first automatic wake waits the same interval as later wakes, at most one second or half the idle interval when shorter. A direct command still activates immediately. Missing cron ticks are still bootstrapped at registration, before the keeper runs. This preserves owner-bound activation without relying on the upstream scheduler's incidental ordering during registration.

Retain the runtime's transaction and authority boundaries. Direct commands do not use persisted Cluster messages or `WithTransaction`; their receipts remain authoritative. Runner storage retains the existing advisory-lock configuration and startup coordination. No new opt-in termination annotation or storage layer is adopted.

## Alternatives and consequences

Pinning peers back to 4.0.2 would avoid the new API but reject the current compatible cohort and defer its recovery fixes. Dual-shape UUID shims would conceal unsupported pairings. Removing the startup assertion would accept activation during registration without a design decision. Scheduling the first keeper wake makes the existing one-second residency bound explicit and can delay an otherwise unrequested initial activation by that interval; it does not delay direct commands or cron bootstrap.

## Evidence and revisit conditions

[`pglite.test.ts`](../../packages/akter/src/runtime/database/pglite.test.ts) retains its assertions that no singleton builder ran during layer construction, a failed builder affects commands rather than startup, repeated commands do not rebuild it, and short-idle singletons remain resident. Existing conformance suites exercise singleton ownership, recovery, cron and workflow behavior. Clean tarball smoke exercises the new UUID calls with freshly installed peers on Bun and Node. Dependency and command results are recorded in [framework package verification](../verification/framework-package.md).

Revisit this cohort and the API calls together when Effect changes its Crypto or Cluster contracts. Revisit the keeper schedule only with evidence that registration remains separate from activation and that the owner/recovery bound is preserved.

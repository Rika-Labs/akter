# ADR 0116: Bucket-range routing across customer Postgres databases

**Status:** proposed (2026-10-09). Docs only; physical data sharding and online range moves are not implemented or supported. Acceptance would authorize the contract amendments below, not establish runtime or hosted support.

**Responsibility:** let one deployment region grow beyond one Postgres primary without distributing an actor turn.

**Authority:** proposed architecture decision.

**Owner role:** runtime/database and operations/reliability.

**Change policy:** accept or supersede through an ADR; claim support only with the [required verification evidence](../verification/bucket-range-sharding.md).

## Context and conflicts with current contracts

Akter Cloud supplies compute over customer-owned Postgres ([ADR 0113](0113-customer-postgres-cloud-contract.md)). More runners do not increase a primary's write, WAL, storage or connection capacity. A deployment can eventually exhaust one database even though its actors are independently transactional.

Useful prerequisites exist, but they are not a sharding implementation:

- The [placement codec](../../packages/akter/src/runtime/storage/codec.ts) gives each actor a stable signed 64-bit `routing_key`. Its arithmetic shift by 56 yields one of **256 signed buckets, -128 through 127**, not 0 through 255. Tenant placement colocates a tenant's tenant-placed actors; actor placement spreads actors; parent placement keeps a family on its root's key. Hash collisions share placement, never identity or authority.
- [ADR 0067](0067-due-work-shard-ranges.md) and the [current scheduling map](../../packages/akter/src/runtime/database/shards.ts) partition scans into inclusive ranges on **the same database**. Its validator permits partial scheduling coverage; a physical placement map must instead cover every bucket exactly once.
- Turns are generation-fenced and receipted, and the [outbox already delivers across routing keys](../contracts/05-messaging.md). This is at-least-once transport with receiver deduplication, not a cross-database atomic transaction.
- [ADR 0066](0066-authoritative-coordination.md) already separates Cluster and deployment coordination from data transactions and keeps local data fences when coordination is lost. It does not discover placement, move rows, or provide a global snapshot.

The proposal deliberately conflicts with current normative rules. Record and resolve these before implementation; do not infer permission from historical Neki ADRs:

| Current rule                                                                                                                                                                                         | Amendment proposed on acceptance                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

The statement that every framework row has `routing_key` has exceptions: deployment registries, migration ledgers, adoption observations and Fleet checkpoint rows. ADR 0067 explicitly audits these exceptions. They need classified owners, not invented actor keys. The cold-tier wording in storage layout also still describes null state and an admission-round-trip fetch; [ADR 0036](0036-cold-tier.md) instead specifies a generation-row pointer and an off-transaction fetch. That newer accepted design governs any future cold-tier integration; the tier remains unbuilt.

## Decision

### 1. Opt-in physical placement, not a distributed SQL database

Route complete buckets to customer-provided ordinary Postgres databases in one region. Each database is a data shard with independent capacity, HA and backups. A routing key, actor address, event cursor, command id and workflow execution id do not change when its bucket moves. One actor, tenant-placed group or parent family never straddles databases.

This borrows the data-locality and capacity unit of [Shopify pods](https://shopify.engineering/a-pods-architecture-to-allow-shopify-to-scale), not their full isolation claim. Shopify prohibits cross-pod actions; Akter deliberately retains asynchronous cross-database messages, shared runners and a shared coordination authority. Those dependencies can propagate overload or outages. A database shard is not a Kubernetes pod and is not automatically an isolated failure domain.

Keep the ordinary single-database API and fast path unchanged. Sharded mode is a future explicit configuration, not reinterpretation of today's `DATABASE_URL`. No automatic shard provisioning, load-based rebalancer, cross-database joins, two-phase commit, dual writes, or transparent failover to an empty database.

### 2. One durable shard map on the coordination primary

The deployment's designated **coordination primary** owns the canonical map and move journal. It may share the original data database initially; it is one authority, not a second writable copy per shard. All runners bootstrap from that same authority. A physical replica is never the map authority.

Proposed durable records, with names to be settled at implementation:

- A deployment/region identity and monotonic map revision.
- A shard catalog: stable database id, region, required schema/metadata revision and a **secret configuration reference** for its connection pools. A database identity is not its mutable hostname/URL; changing a DSN must not silently change its history. URLs/credentials do not appear in public maps, logs, headers or inspection responses.
- Exactly 256 bucket-owner rows: `(bucket, database_id, placement_epoch)`. Contiguous equal assignments are exposed as inclusive ranges for ADR 0067's scanners. Transactional publication checks complete, non-overlapping coverage and valid database identities. Persisted per-bucket identities avoid changing the fence merely because ranges split or merge.
- A move journal: move id, exact buckets, source/target ids, old/new epochs, phase, copy snapshot/stream checkpoint, final source barrier, target validation result, and the published cutover or abort decision. Compare-and-set transitions prevent competing moves; serialize map changes in the initial design.

For example, `[-128, -97] → db-a`, `[-96, 31] → db-b`, `[32, 127] → db-c` covers the existing signed space without rehashing. Pin bucket **-128**, which contains authority placement, to the designated authority-data database in this first design. It may also contain ordinary hashed keys; all of them share that bucket's capacity. Authority placement grants no authorization and does not grant access to tables on a separate coordination database.

Runners cache a validated map and refresh on a bounded poll or a stale-placement refusal. Notifications are hints. A missing map in sharded mode, unknown database, gap, duplicate, wrong region/deployment, unavailable required metadata or incompatible map format fails startup/admission closed. Never fall back to the bootstrap database. An outage of map refresh need not stop already validated, unchanged data assignments; local durable gates below remain the write authority. It stops startup and map changes, and Cluster/coordination-dependent work still obeys its existing loss rules.

### 3. Local placement fences, in addition to actor generations

Each data database has durable gate rows per bucket containing deployment/database identity, placement epoch, accepted metadata revision, move id and phase: `importing`, `prepared`, `serving` or `retired`. Imported target buckets and retired source buckets are **not serving**. Only the move protocol's privileged operator can change gates; runtime roles cannot enable a bucket. Gate transitions compare the expected local epoch, move id and phase. Activation is only `prepared → serving` for that move; a retired epoch never reopens. A delayed mover from a completed move cannot re-enable a source closed by a later move.

Every data-mutating transaction first locks its bucket gate `FOR SHARE`, validates the requested epoch, serving state and compatible metadata revision, then takes the existing actor-generation/resource locks. Hold the gate through commit/rollback. Multi-bucket maintenance locks gates in ascending order before other data locks and uses bounded batches. This includes generation acquisition, turns, outbox claims/renewals/settles, workflow steps, subscriptions, connections, content writes, retention, operator repairs and derived writes. A mutation outside a turn still needs a short gated transaction. No provider/network operation holds a gate or generation transaction open.

Read-only queries, receipt reads and inspection validate the gate and data in one `REPEATABLE READ, READ ONLY` snapshot: do not issue `FOR SHARE` in a read-only transaction. A snapshot opened before closure may finish with its legitimate pre-cutover committed view; a new snapshot on a closed source refuses. Existing query deadlines bound old snapshots. Initial sharded reads use primaries, so replica replay cannot make a closed source appear serving.

A mover closes gates with conflicting `FOR UPDATE` locks. It waits for every previously admitted local mutation to finish, then commits the non-serving state. Thus even a paused runner with the old map cannot commit on the source after closure. A coordination lease or a map revision alone cannot fence a transaction on another database. The actor's `FOR UPDATE` generation fence still determines **which activation** may commit; the gate determines **which database** may commit. Neither substitutes for the other. Copy/validation/cleanup use a privileged, phase-guarded move path, not the public serving path.

Stale placements restart activation/query routing and surface retryable `ActorUnavailable`; the caller/relay retains its original identity and deadline. Retry is bounded by the existing admission/delivery policy, not recursive forwarding between databases. Closed sources refuse new reads as well as writes rather than serving stale copied receipts/state. Activation caches and connection ownership messages bind the placement epoch; a moved actor acquires a generation greater than its copied generation before serving.

Adding these transactions costs statements and connections in sharded mode. Gate checks can join the first pipelined flight but do not receive an unmeasured two-flight/throughput claim. The unsharded default must retain its current claim and turn accounting.

### 4. Registry ownership and Effect Cluster

The coordination database continues to own `actor_coordination`, its independent migration ledger, `cluster_runners` and table-backed `cluster_locks`; session advisory ownership also uses that authority. Effect's [SQL runner storage](https://effect.website/docs/v4/api/effect/cluster/SqlRunnerStorage) coordinates **compute** shards. The usual 256 compute shards are not the 256 data buckets: their assignment/count may differ, and any actor's compute owner resolves its data database from the map. Do not create an independent Cluster per data database or persist direct commands in Cluster message storage.

Keep ADR 0066's authority-then-local-resource lock order and local data fences, with the bucket gate before data mutation. Retention iterates active data ranges in short batches. Loss of coordination after the last probe is still not atomic rollback across databases; recovery rereads committed data. One data-primary outage blocks its buckets, not unrelated data transactions, while shared runner permits and the coordinator remain possible shared bottlenecks.

Classify metadata explicitly:

| Record class                                                                                                                                                             | Owner in sharded mode                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Deployment identity/retry window, placements/table ownership, subscription declarations, adoption policy, accepted workflow/payload definitions and writer compatibility | Canonical deployment metadata on the coordination authority; versioned, validated local metadata on each data shard where the runtime or joined views need it. Local copies do not accept independent policy changes.                                                                            |
| Workflow start manifests                                                                                                                                                 | Immutable manifests must exist locally before a turn can reference them; retained executions keep their manifests available. The current engine can restore a manifest inside the starting turn. Preserve that local atomicity; do not move that insert to a remote coordinator inside the turn. |
| Framework/application migration histories, physical catalog/grants/triggers, adoption write observations and Fleet feed/checkpoint state                                 | Database-local facts/ledgers. Aggregate their status explicitly; do not treat one shard's catalog as proof about another.                                                                                                                                                                        |
| Per-actor/per-tenant records, operator audit rows with routing keys, owned tables and internal-delivery dedup evidence                                                   | Their key's data database, moved with that key. Shard-map/operator move audit belongs on the coordinator.                                                                                                                                                                                        |

One coordination mutex is not a deployment-wide workflow compatibility snapshot. For a compatibility-changing rollout, freeze new workflow starts/metadata writers with local barriers on **every active data database**, serialize with map changes and acceptance, check all open executions and retained versions, then publish the accepted revision and release the barriers. Missing shards refuse acceptance. Immutable local manifests and writer registrations precede serving that release; incompatible older writers stay fenced. State upcasts remain lazy, local turn work. Payload/manifest removal and retention require an all-shard negative result, including moving ranges, not the current one-database check.

### 5. Runtime behavior across two databases

Assume sender A is on db-a and receiver B on db-b:

| Path                                 | Required behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actor turn / batch                   | Resolve the trusted address to a key/bucket, choose db-a's pinned turn session, validate gate and generation, and commit receipt plus every consequence there. A declared failure retains only its failure receipt there. Initially restrict sharded turn groups (ADR 0084) to the **same database and bucket**, avoiding incremental multi-gate lock ordering; unsharded grouping is unchanged. No batch/group becomes distributed.                                                                                                               |
| Local / `group` read                 | One read-only snapshot on the addressed key's database. `group` means the exact placement key, not the whole bucket or every actor that happens to share a database. Parent families stay colocated; tenant-placed types share their tenant key. Actor-placed actors on different keys cannot acquire a cross-database `group` join.                                                                                                                                                                                                               |
| Outbox / relay                       | A's committed intent stays in db-a. Claim one mapped range on its database with `SKIP LOCKED`, release the claim transaction, deliver to B through its compute owner, and delete/settle A's row **only after B's committed terminal acknowledgment**. There is no database-to-database transaction. A failed delivery/settle preserves lease, original intent id and backoff. Re-resolve the sender as well as receiver after a move.                                                                                                              |
| Capacity / failures                  | Rotate the first range and share free permits across **all** databases and claim families, as ADR 0067 requires. A failed range must not be counted as empty or monopolize the other ranges; retries retain bounded backoff and database-specific saturation signals.                                                                                                                                                                                                                                                                              |
| Timers / cron                        | Stay under the sender's key in its outbox even when targeting another database. Preserve timer keys, due/scheduled times, ids, claims and attempts. | Jobs                                 | Obligation, attempts, cancellation, routes and dead letters stay on the enqueueing actor's database. Executors run off-transaction. Renewals and settlements need that bucket's gate plus existing attempt guards; capped claims still lock the actor's generation row locally. Moves do not reset a lease, attempt count, cancellation or ambiguity. Provider success without recorded settlement remains ambiguous and may be retried under the **same job id**, not an exactly-once provider claim.                                             |
| Workflows                            | Execution, version markers, steps, waits, resume timers and results stay with the owner. `w1` identity denotes the logical deployment/owner, not a database endpoint; resolve it from owner placement when polling/resuming. An activity may call B off-turn with its recorded derived call id; interruption before recording the activity result can replay B's receipt. Keep the existing `ActivityOutcomeUnknown` expiry exception; never remint to escape it. Owner-event waits remain local; other-owner events arrive through subscriptions. |
| Event subscriptions                  | Source-side subscription rows, tag summaries, retention holds and fan-out work live with the source; subscriber epochs/applied cursors live with the subscriber. Subscription control travels from the subscriber's outbox to the source database, then settles the original row separately. Routed declaration metadata is distributed before use. Delivery retains source order, cursor/gap reporting and subscriber deduplication, not a global event order.                                                                                    |
| Minted children                      | Preserve the committed creating-intent provenance and derive the child proof locally (ADR 0048). Broadcast/progress remain best-effort, not migrated durable history.                                                                                                                                                            |
| Shared content                       | Uploads/grants/bytes route by the tenant key; actor references route by the owning actor key. Attaching a signed grant remains local to the actor turn, with no remote content read. Initial sharded uploads buffer/hash the bounded body before the gated publication transaction rather than holding a gate across client streaming. GC scans references on every active database, preserves grant/time/skew margins, and inhibits deletion on any failed shard, changing map or active move. A local negative scan is insufficient.             |

All clocks remain database clocks, not runner wall clocks. Before enabling a shard or completing a move, verify it has not rolled back behind the source's clock/issued identities and meets a declared cross-database skew bound. Preserve absolute due times and external expiry; never extend ids to hide skew. Content grant GC needs its execution-time and skew margins too. Clock rollback while serving remains unsupported unless a later decision supplies detection.

#### Receipt retention is a new correctness requirement

The [current receipt sweep](../../packages/akter/src/runtime/storage/retention.ts) protects a receiver receipt with a local `NOT EXISTS` against `actor_outbox`. That sees A's row when A and B have different keys on one database; it **cannot see it when A is on another database**. After B commits and A cannot delete its row, pruning B's receipt would let later trusted redelivery execute B again. Fixed extra retention or a successful scan of some shards does not solve an unbounded partition.

The initial sharded design therefore keeps durable **receiver-side internal-delivery deduplication evidence** indefinitely: the full receipt while retained, then a terminal tombstone binding receiver identity, delivery id, command/input digest and committed outcome needed for a trusted acknowledgment. It commits with B's turn, follows B during a move, and a late trusted delivery acknowledges the prior commit without rerunning the handler. It grants no external result access; ordinary full receipts keep finite expiry/retention and current authorization. Subscription applied cursors continue to provide their existing permanent evidence.

This adds storage proportional to delivered internal work. Do not claim bounded dedup storage. A garbage-collection protocol must separately prove that no sender obligation, in-flight delivery or supported restore can resurrect the id before removing its tombstone. A cross-database acknowledgment/GC protocol is deliberately not part of this first design.

### 6. Online range movement: copy, fence, publish, activate

"Online" means unrelated buckets and source writes during bulk copy keep serving. The moved range has an **operator-visible admission pause**, budgeted for final catch-up/validation; it is not zero-downtime dual writing. Failure after publication can extend that pause: safety takes precedence over the healthy-path pause budget. Start with one move at a time, within one region, never bucket -128. An indivisible hot bucket cannot be split without a later key/bucket design.

1. **Prepare.** Persist the move's source epoch `e`, target epoch `e+1` and phases under the coordinator's map-change exclusion. Check target identity, schema, roles/RLS, local metadata, clock and capacity. Its gates are `importing` for this move; refuse unrelated preexisting rows in the imported range. Exclude schema/placement changes, destructive retention and content GC that could invalidate the copy/validation while the move runs.
2. **Copy while the source serves.** Establish one consistent source snapshot tied to a retained logical-decoding position, bulk-copy every keyed framework/owned row in the range, then apply committed changes and deletes from that position. Online moves require `wal_level=logical`, replication privileges, sufficient WAL retention and complete old/key tuples to route updates/deletes; customers lacking these cannot claim online movement. Commit each source transaction's relevant rows together on the target, in constraint-safe order; do not replay triggers/jobs as business actions. Import transactions lock target gates and require this move's `importing` phase/epoch; the importer cannot enable serving or overwrite another range. Persist restartable copy/checkpoint progress. A snapshot without its complete subsequent change stream is insufficient.
3. **Fence the source.** Stop scheduling new local work for the range, pause/drain its activations, and close **all** its source gates to `retired` in one transaction using exclusive gate locks. Previously gated mutations finish first; a timeout/unknown close outcome is not proof of closure. Verify the committed closure, then record a source WAL barrier at/after that commit. Stop workflow/job fibers best-effort; provider calls or already-sent remote commands may still complete off-transaction and cannot settle through the closed source gate.
4. **Catch up and validate.** Apply through that barrier, commit it on the target and exclusively close its gates to `prepared`, draining/blocking import transactions as well as runtime writes. Independently verify every included table/key/digest, generation/event counters, receipts/tombstones, pending outbox work, workflow manifests and constraints. Persist target readiness evidence for this exact move/epoch/barrier. Copy leased work unchanged: a lost late source settle is recovered by redelivery after the preserved lease, using receiver deduplication; an external attempt is subject to the existing ambiguity rules.
5. **Publish the decision.** In one coordinator transaction, compare the expected map revision/owner epochs and publish all moved buckets as `(target, e+1)`, with the verified barrier/readiness record. This durable decision is the cutover linearization point. There is no distributed commit: both sides are still fenced, so failure here may prolong unavailability but cannot create two writers.
6. **Activate and retire.** Re-read the committed decision and compare-and-set this move's prepared target gates to `serving` at `e+1` in a target transaction. Only then resume admission/claims, acquire fresh actor generations and resync holders. Old routing attempts fail on the permanently closed source gates and refresh. Retain source copies non-serving through a documented recovery/backup window; clean them with the migration role in bounded batches, never by dropping shared tables. Remove the copy slot only after journaled completion. Gate tombstones outlive row cleanup and survive restart.

Bulk copy includes source subscription rows/summaries, subscriber cursors, operator audit and tenant content/chunks/sweep rows under their own tenant routing key. Use the migrated catalog and registered ownership tables, not the historical count of 18 or an `actor_generations` join as a permanent copy manifest. Future eligible adopted legacy rows may have no materialized owner; future cold pointer/GC records also need explicit inventory. Database-local ledgers/identities, canonical registry rows and serving gates are **not** copied as actor data. Tenant-derived Fleet rows are rebuilt/handed off as below. Immutable cold objects, if later built, need no rewrite for a same-region move because the routing key/deployment stay unchanged, but their pointers and backup retention do.

Abort is allowed only **before** a committed cutover decision. After publication, data might already have committed on the target even if the mover lost its reply. Availability never justifies enabling both copies.

### 7. Reads, Fleet, inspection and adoption

**Read-your-writes and replicas.** Keep today's scalar protocol for unsharded deployments. Before sharded serving, version the headers/client bookkeeping to carry placement-scoped components `(bucket, placement_epoch, database/WAL lineage, LSN)` and retain maxima only within matching components, not across the deployment. An actor/group query selects its component; unrelated buckets impose no order. Start sharded mode with primary-only reads. Replica enablement later requires a same-owner/epoch/lineage replay check before the query snapshot. An older-epoch token after a completed move goes to the new primary: the fenced handoff preserved every committed fact of that bucket; comparing its old numeric LSN to the new WAL proves nothing. Never answer from a replica merely because its number is larger. Unknown/future lineage takes the conservative primary path; malformed tokens are refused. Watches carry the same scoped versions. Old clients must negotiate/refuse sharded protocol rather than silently drop their guarantee. This protocol work is a prerequisite, not a claim made by this ADR.

**Fleet (ADR 0056).** Its supported source is tenant-placed, so each tenant's aggregate can still be recomputed locally. Run one publication/slot and maintainer **per data database**, colocating each tenant's derived rows with its source. Keep definition metadata canonical, but checkpoint/status local to the feed. Ownership uses a shard-specific authority resource plus a data-session lock/fence, so loss of the coordinator alone cannot admit a second slot advancer while the old data session lives. Slot advancement and derived writes need local exclusion; ADR 0066's heartbeat alone is not a fence on another primary.

`Fleet.subscribe` routes the authenticated tenant to its current tenant-key database. A deployment-wide operational listing reports a checkpoint/status vector, not `max`/`min` of unrelated `applied_lsn` numbers. A tenant's `asOf` binds its owner epoch and feed/WAL lineage. During a move, source derived writes are gated, target aggregates are rebuilt/validated from the final source data, and the new feed starts from a recorded target position **before** admitting new target writes. Imported copy changes are not two live owners' contributions. Reconnect/reconcile subscriptions and mark incomplete state `building`/`stale`; never compare source and target LSNs for readiness. Actor-placed sources, arbitrary cross-database joins and global aggregates remain refused. Until this path is built and verified, sharded startup with Fleet declarations must refuse, not run the one-slot engine on only the first database.

**Inspection (ADRs 0028/0112).** Preserve the joined `durable.*` views on **each** database, with validated local placement metadata and existing schema-only/RLS privileges. They become shard-local SQL surfaces, not one deployment-wide schema; do not resurrect `_v2` or silently hide missing shards. In sharded mode live views include only serving owner buckets; imported/retired copies require privileged move/recovery diagnostics, and shard availability is reported separately rather than inferred from empty views. Actor-specific inspector/export/repair resolves one database and retains its snapshot/audit guarantees. Tenant/whole-deployment lists require explicit off-turn fan-out over active owner ranges, revision-bound pagination and per-shard status; shard failures either fail the request or are labelled incomplete, never zero/missing actor. Multiple snapshots are not one repeatable-read deployment snapshot, so the current inspector's one-snapshot response contract needs an explicit amendment for aggregate endpoints. Copy/retired ranges are not counted twice. Operator credentials and tenant predicates/RLS apply independently to every connection.

**Adopted tables (ADR 0054).** A global unique business key becomes only per-database unique after splitting; foreign keys, sequences, triggers, shared parents and legacy SQL readers/writers may depend on one database. Initially refuse writable adoption when physical sharding is configured; adopted tables are **not eligible** for movement. An explicit future adoption plan may permit it only after enforcement has no allowed legacy writers, every row has a validated key, every unique constraint and dependency is confined to an indivisible bucket/placement group, and sequences/keys cannot collide across databases or a move. Cross-bucket foreign keys and global uniqueness need an application redesign or stay unsharded; no global constraint service on the turn path. Read-adopted tables have no routing key and remain local only; refuse any declaration that would require a remote in-turn read. Observation/backfill/enforcement/role and trigger checks run on each physical catalog, not just the coordinator. Preserve adopted rows whose owner actor has not materialized. Existing adoption keeps its full single-database semantics when sharding is off.

### 8. Migrations, recovery, PGlite and hosted configuration

Do not edit applied migrations. Implementation adds new numbered transactional data/coordination migrations for map/gates, dedup evidence and metadata/feed changes; their numbers are assigned when built. Each data database keeps its own framework/application history and startup mutex, while Cluster tables stay on the designated authority. Apply application DDL/roles on every participating target before admission. A successful migration on db-a and failure on db-b is a partial **deployment rollout**, not a distributed DDL transaction: resume/repair db-b and keep incompatible shards/releases fenced. Use expand/contract and all-shard compatibility checks before contracting anything; moves cannot overlap schema changes in the first design.

All runners must first be upgraded, with previous alpha runners stopped, to a gate-aware single-database runtime before physical sharding is enabled. Old code does not take the gate and would defeat the move protocol. Downgrade to today's unsharded runtime requires consolidating all buckets onto one database and a stopped-runner upgrade/restore rehearsal, not deleting the map. Gate/map changes are privileged, audited operations; normal runner credentials cannot edit or re-enable them. The fence assumes all runtime writers take the gate; arbitrary SQL writers/superusers bypassing that protocol are outside the guarantee and must be excluded during moves. RLS and content grant secrets/deployment identity must agree on every shard.

For the initial multi-database backup guarantee, stop ingress, drain/stop **all** runtime and privileged writers, settle or journal-abort/complete any move, and record a durable backup manifest for the coordinator and every active data database at that quiescent boundary. Back up whole databases, not actor-table fragments. Independent online dumps/PITR timestamps are not a common snapshot: one could restore a delivered message without its receiver dedup evidence, or forget a delivered message whose sender row was already deleted. Restore the whole manifest set with all runners stopped, check clocks, assign fresh placement/generation ownership before serving, and reconcile provider effects beyond the backup as today. Online consistent backup across shards needs a separate proved protocol; provider HA must also preserve acknowledged gate closures and map decisions. Do not claim support without a recovery rehearsal.

PGlite remains one process, one locked directory, transactional migrations and one local database. It is not a shard target or coordination service for this feature; refuse multi-database configuration/moves. Keep existing PGlite and unsharded Postgres conformance unchanged. Multiple PGlite files are not an equivalent concurrency/fencing proof.

This ADR belongs to the public framework. Akter Cloud currently accepts one customer `DATABASE_URL` and one diagnostic database report; this proposal neither changes that contract nor claims a hosted multi-database feature. A future private-platform implementation must accept customer-managed shard/coordination credentials, probe locality/reachability and budget pools **per database**, expose incomplete probes honestly, and independently verify provisioning/network/HA. ADR 0113's single-database runner-cap formula cannot simply be multiplied by shard count. Per-shard turn/off-turn/query pools plus coordination can exhaust connections or runner memory first; use explicit total/per-database budgets and lazy pools, not unbounded pools per bucket.

## Alternatives and when a deployment should need this

| Alternative                                                                                                  | Prefer it when                                                                                                                                                                                                                   | What it does not solve                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Larger/tuned single Postgres, better indexes, shorter turns, admission/pool tuning, local table partitioning | The workload fits one primary with measured headroom and acceptable cost/restore time. This preserves global SQL, adopted constraints, one WAL token/feed and simple recovery. It is the launch/default answer.                  | Still one primary's CPU/IO/WAL/storage/connection ceiling. More runners or partitions do not create another write authority.                                                            |
| Physical read replicas (ADR 0052)                                                                            | Read-heavy state/events can move off the primary with the existing read-your-writes fall-through.                                                                                                                                | No additional primary write/WAL capacity, no removal of its durable storage/backup boundary. Table/blob query limits still apply. Replica lag can send load back to the primary.        |
| Cold tier (ADR 0036)                                                                                         | Long-idle opaque state/blob storage dominates cost. It is designed but unbuilt, so not a current escape hatch.                                                                                                                   | Leaves generations, receipts, events, tables, workflows and due work hot; does not increase active turn or owned-table write throughput. Object-store recovery adds another dependency. |
| Separate deployments per customer/tenant                                                                     | Independent tenants can accept separate operational identities/APIs and do not need one actor namespace. This may give better isolation with less framework complexity.                                                          | Does not spread one tenant's actor-placed workload within one deployment; cross-deployment messaging is not promised.                                                                   |
| Bucket-range Postgres sharding                                                                               | A measured, sustained primary bottleneck remains after the simpler options, and traffic/data is spread over independently placed buckets. The operator accepts multi-database operations and the supported feature restrictions. | Does not split one hot actor, tenant-placed tenant, parent family, bucket or the authority bucket; does not remove shared coordinator/runner bottlenecks or promise linear scaling.     |

No actor-count or turns-per-second threshold is a product guarantee. Require workload measurements: primary saturation/WAL/IO/connection waits, latency/backlog under realistic peak load, bucket skew, storage/backup limits and recovery times. Demonstrate that moving ranges gives enough headroom after extra connections, cross-shard message traffic, copy WAL and dedup storage. A single tenant with tenant placement still fits only one data shard; switching its type to actor placement is a separately planned ownership/data migration, never an implicit rehash. If one bucket dominates, this proposal is not the remedy.

## Consequences, evidence and revisit conditions

On acceptance, supersede **only ADR 0112's prohibition on physical data-shard selection** and amend its logical-only authority grouping for this opt-in mode. Its removal of Neki/provider-specific topology/settings/DDL, ordinary transactional migrations, joined inspection catalog and Postgres/PGlite backend scope remain in force. Historical sharded Neki APIs and evidence are not restored. This proposal does not alter current normative contracts merely by being filed.

The benefit is additional write/storage capacity without changing actor identity or local atomicity. The cost is a routing authority, per-database fences/pools/schema/HA/backup operations, a move protocol, permanent internal dedup storage, versioned read/Fleet tokens and reduced transparency for inspection/adoption. Cross-shard messages remain useful, but couple otherwise independent databases through backlog and recovery. Fail closed rather than pretending one unavailable shard or stale checkpoint is empty/healthy.

No runtime evidence is produced by this docs-only PR. Existing range, coordination, mint and same-database recovery cases are prerequisites, not physical-sharding proof. [The verification plan](../verification/bucket-range-sharding.md) specifies the executable gates and failure results that must be attached under `docs/verification` before any support-matrix/API/hosted claim changes. Acceptance must update contracts 02/04/05/06/07/08/09/10, protocol/versioning, storage/topology, migrations/backup/inspection operations and the support matrix alongside implementation; leave accepted historical ADRs intact and link this amendment.

Revisit when a real deployment reaches the measured single-primary limit; one bucket/coordinator saturates; dedup storage needs safe collection; users require movable brownfield constraints, actor-placed Fleet sources or online multi-database backups; or move pauses/copy WAL cannot meet the deployment's declared budget. Keep this proposal deferred if simpler single-database scaling still meets the workload.

# ADR 0090: Fly Machines runner platform, Resend email and the Fly client-IP boundary

**Status:** implementation decision (2026-10-05) for [#611](https://github.com/Rika-Labs/akter/issues/611), implementing Dallen's provider choices of 2026-10-04. It supersedes the ECS Fargate runner provider, the ARM64 task definitions, the ECR image registry and the NLB/Cloudflare client-IP gate of [ADR 0075](0075-deployment-and-runner-orchestration.md). The rest of ADR 0075 stands. It withdraws the AWS Private CA hosted-provisioning proposal of [ADR 0086](0086-runner-mutual-tls.md); runner mutual TLS itself is unchanged.

**Responsibility:** run customer deployments' runners as Fly Machines, deliver control-plane email through Resend, and place the hosted client-IP trust boundary at Fly's proxy.

**Authority:** design decision record.

**Owner role:** cloud, security and reliability.

**Change policy:** supersede through a new ADR.

## Decision

**One Fly app per deployment.** `flyRunners` implements `RunnerPlatform` over `@distilled.cloud/fly-io`, the only Fly client. The first start of a deployment creates an app named `appPrefix` plus a SHA-256 hash of the deployment id, cut to Fly's 30-character app-name limit, in the configured organization and on a private network named like the app, so no two deployments share a 6PN network. The app's create request carries an idempotency key from the same hash, and the platform allocates a shared IPv4 and an IPv6 address, so `https://<app>.fly.dev` resolves. An app that lives in another organization, or already holds a machine of another deployment, is refused. The hosted configuration is the JSON `RUNNER_FLY_CONFIG` with `FLY_API_TOKEN`; the Akter region a deployment names maps to a Fly region and, optionally, an ordered list of fallback regions.

**The edge reaches a runner through Fly's proxy.** A runner's id is `<app>/<machine id>` and its url is `https://<app>.fly.dev`, always over TLS, so the `http` scheme option and the production TLS check of the ECS configuration no longer exist. Each machine publishes its port on 443 and 80 with Fly's `tls` and `http` handlers and its own concurrency ceilings, because Fly's default per-machine limit would queue the edge's connections below the runner's own admission control. The runner trusts exactly what it trusted before, the edge's signed assertion, so the public hostname grants nothing. The url is reported as soon as the machine exists, which lets the runner actor register it at once; the edge's readiness probe still gates traffic.

**Idempotent start by machine name.** A machine is named for the hash of its deployment and idempotency key, so a start lists the app's machines and returns the one with that name before it creates anything. A failed create, other than for capacity, is followed by the same lookup, so a create whose answer was lost or that lost a race returns the machine that exists. An image must be `registry.fly.io/<app>@sha256:<digest>`, so a deployment always runs the bytes CI pushed; tags and other registries are refused before Fly is called. Machines are created with `restart: no`, `SIGTERM` with a 30-second stop timeout, and the environment snapshot as the machine's own environment.

**State is what Fly observed.** `created`, `starting` and unknown states are `starting`; `started` is `running`; `stopping`, `suspending`, `stopped`, `suspended`, `destroying` and `destroyed` are `stopped`. `terminated` is reported only when the machine is in one of the stopped states and Fly recorded an `exit` event, the one fact that a process ended rather than that a stop was requested. `stop` sends `SIGTERM`, polls until Fly reports the machine stopped, and then destroys it, so scale-to-zero cycles leave no machines behind and the call returns only after termination. A machine that never started is destroyed with force, because there is no process to drain.

**Capacity.** When Fly refuses a machine for lack of capacity, the platform tries each fallback region in order and, with none left, fails with the transient `capacity` code. `unavailable` and `capacity` are the retryable codes; the job's retry reuses the start key and finds any machine an earlier attempt made. The `wrong-architecture` and `definition-mismatch` codes were ECS-only and are gone.

**Migrations are one-shot machines.** `flyMigrations` starts a machine in the deployment's app with `init.cmd` set to the migration command, no public service and no addresses. It succeeds only when Fly recorded the process's exit with code 0; a stopped machine without that exit, or with another code, fails. The machine is destroyed whatever the result, so its environment does not outlive it, and a retry runs the idempotent migration again.

**Architecture.** Fly Machines run linux/amd64 only. The reusable deploy workflow builds linux/amd64 on an x86 runner and pushes to `registry.fly.io/<app>` with a Fly token as `FLY_API_TOKEN`, replacing `ECR_PASSWORD`. The local Docker platform's defaults are for development machines and are not hosted-architecture evidence.

**Email.** `EMAIL_MODE` is `local` or `resend`. `resend` sends through `@distilled.cloud/resend` with `RESEND_API_KEY` from `EMAIL_FROM`, which must be on a domain verified in Resend, and startup refuses it without the key. Production refuses `local`. A failed send raises an `EmailError` with no field, because Resend's answer can echo a message that holds a sign-in link.

**Client IP.** `EDGE_TRUST_FLY_PROXY` replaces `EDGE_NLB_ONLY` and `EDGE_CLOUDFLARE_RANGES`. When it is set the edge believes `Fly-Client-IP`, which Fly's proxy sets and overwrites, and only when it is exactly one address; every other forwarding header is ignored, and the edge removes `Fly-Client-IP` with the other attribution headers before it writes its own `x-forwarded-for`. Without the gate, or with an absent or malformed header, the client is the TCP peer. The gate is a statement that the edge is reachable only through Fly's proxy. A process in the same Fly organization that connects to the edge directly over `.internal` can set the header, so the edge app must not be reachable from untrusted machines on that network.

**Region ids.** Akter region ids (`us-east-1`, `us-west-2`) remain product ids that cloud-api, the console and the lifecycle contract name. `RUNNER_FLY_CONFIG.regions` maps each to a Fly region (`us-east-1` to `iad`), and a start for an unmapped region is refused before Fly is called.

**Customer environment variables.** No code in the control plane, API or edge uses KMS or envelope encryption today: a deployment's environment snapshot, whatever its build records plus the platform's own variables, is stored as JSON in `deployment.environment_snapshot`, and the workflow template records an empty one. Nothing consumes the Fly secret key `CUSTOMER_ENV_KEY`, so none was added.

## Consequences

Retired deployments' apps are not deleted. An app with no machines costs nothing, but a retirement hook that deletes the app of a deployment that will not serve again is still to be built. The environment snapshot is the machine's own environment, readable by anyone who can read the app's machines through Fly; moving it to Fly app secrets needs live evidence for how machines receive secrets. A stop polls Fly every 500 milliseconds. Runner-to-runner peering inside a deployment would use the app's `.internal` addresses with the mutual TLS of ADR 0086; the Fly platform provisions no peer credentials yet, so hosted multi-runner peering stays gated as ADR 0075 states, and the AWS Private CA, Secrets Manager and KMS path of ADR 0086 is withdrawn.

## Evidence

`runners/fly.test.ts` runs the real platform over real HTTP against `runners/fly-fake.ts`, which keeps apps, addresses and machines in memory and answers as Fly's API does. It checks the exact calls and bodies of a first start, one app and one machine per start key with a distinct app per deployment, a racing create returning the existing machine, refusal of another organization's app and another deployment's machines, the state mapping including that a stop request is not a stop and only a recorded exit is a termination, a stop that returns only after Fly reports the machine stopped and then destroys it, force-destroying a machine that never started, ids and images and regions refused without calling Fly, failures named by fixed code and Fly's error name with neither the provider's text nor the token, fallback-region placement and the `capacity` code for both statuses Fly may use, and the one-shot machine's shape. `runners/migrations.test.ts` requires the recorded exit code 0 and the machine's destruction, and waits for a running machine to exit. `apps/api/src/config.test.ts`, `email.test.ts`, the edge's `client-ip.test.ts`, `config.test.ts` and `server.test.ts` cover the configuration, the Resend request and the Fly-Client-IP gate end to end through a real edge. Real Fly capacity, private networks, proxy behavior and TLS, cross-app image pulls, the registry push and Resend delivery are unverified.

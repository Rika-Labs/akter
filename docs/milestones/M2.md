# M2: Many runners, background work, and sessions

**Responsibility:** define the M2 slices, their order, and the exit test.  
**Authority:** delivery plan.  
**Owner role:** delivery/runtime lead.
**Change policy:** a change requires delivery lead sign-off.

M2 runs actors on several runners at once and adds the members that do work in the background or hold a session:

- the multi-runner relay;
- singletons proven across runners;
- cron;
- workflows with version markers;
- connections with parking and hibernation;
- `Actor.stream`;
- effect cancellation and a per-actor effect concurrency cap;
- `turn.mint`, which creates child actors deterministically inside a turn;
- executor progress frames;
- the design of cross-actor event subscriptions, which M3 builds.

M2 also carries the first half of the performance roadmap: the two-round-trip turn, turn batches, and commutative merging. Two round trips per turn is the target; there is no one-round-trip path. It also builds the testing base that every later milestone uses: the multi-runner harness, a statement-count CI gate, property tests, deterministic simulation, and the first failure drills.

The exit test is `examples/chat` on three runners, with one runner killed mid-test. It adds a cron digest, a workflow, typing sent as connection frames, a per-actor cap on moderation calls, and a `Thread` child actor minted for each reply thread. The code below is that example.

Spellings follow [server API](../api/01-server-api.md), [context](../api/02-context.md), and the [contracts](../contracts/README.md). Members the docs name but don't fully specify are **proposed** here, including `concurrency.perActor`: `ActorTest.cluster` and everything on it (`it.cluster`, `ActorTest.Cluster`, `kill`, `owner`, `advance`, `receiptsFor`), `ActorTest.simulate`'s options, `wf.version`, and the `Actor.connection` options. Their ADR settles them, and the implementing slice updates the API docs.

## Rules for every slice

The rules in [M1](M1.md#rules-for-every-slice) still apply, plus these:

- **Multi-runner cases.** Anything about ownership, relay claims, singletons, or failover runs on the M2.1 harness against real Postgres. PGlite isn't a proof backend for them.
- **Benchmark scenario.** Every slice adds a scenario under `tooling/benchmarks/src/scenarios/` and commits a results file from a cloud VM. A slice with nothing to measure says why in its PR.
- **Statement counts.** Once T2 lands, a change in statements per operation fails CI unless the PR updates `benchmarks/baselines/statements.json` and explains the change.
- **Migrations.** Migrations follow the wave order in the [reserved-numbers table](README.md#reserved-numbers). A slice that needs an unplanned migration takes the next number above the highest merged one, then renumbers every unmerged reservation above it and updates their issues.
- **General examples.** ADRs for the features first asked for by agent products (M2.12–M2.17, and M3.7, M4.13 and M4.14 in later milestones) use general examples, such as payments, orders, imports, and projections.

## Slice details

**M2.1: multi-runner harness.**

- **What it is.** N runtimes in one process against one real Postgres. Each runtime is a distinct Cluster runner with its own address and expiring per-address shard locks.
- **Controls.** `kill`, `restart`, `pauseHeartbeat`, and `owner(ref)`, all proposed.
- **Evidence.**
  - The **In-process multi-runner** gate.
  - The failure-matrix row "Runner dies in a paused turn".
  - Invariant A1 with a real second runner, and invariant M3 across a runner kill.

**M2.2: singleton uniqueness and failover.**

- **What it proves.** One activation and one `Effect.forkScoped` loop exist across 2–3 runners. After a kill, exactly one survivor takes over. Lock expiry and resumed service are timed separately. The loop proves it ran by sending a command, never by writing outside a turn (invariant A3).
- **Evidence.** G1 without cron, and the loop half of "Singleton runner dies".

**M2.3 and M2.4: multi-runner relay.**

- **What ADR 0021 decides.**
  - `FOR UPDATE SKIP LOCKED` claims.
  - Executors outside the relay transaction, on a per-runner pool with a concurrency limit and renewable leases.
  - Configurable executor timeout, lease, and backoff (M1.7 fixed them).
  - Capped backoff for rows that die without settling.
  - Wake-ups after commit, never `LISTEN/NOTIFY`. ADR 0021 (accepted) keeps them local to the committing runner, which may claim any row, with polling as the correctness path.
  - Whether the relay and cron need migrations. ADR 0021 uses `0011_relay` for `scheduled_at_ms`; cron needs none.
- **Evidence for M2.4.**
  - The **Outbox delivery** gate on two or more runners.
  - The **Effect routes** and **Due-work scans** checks.
  - Invariants M1, M2 and P1.
  - Both relay-crash rows in the [failure matrix](../verification/02-failure-matrix.md), with a runner kill between the steps.
  - E1's multi-runner half: a stream written through turns on different runners over time keeps its cursor order.
- **Benchmark.** Concurrent effect throughput must beat M1's single relay, which settles at most 16 effect rows per pass (the M1.7 `effect-round-trip` result). A slow executor must not delay intent delivery.

**M2.5: cron.**

- **What it does.** Per-actor cron runs as a keyed self-timer, and singleton cron runs once per deployment. `cronSkipIfOlderThan` and the catch-up rule come from ADR 0021. A tick the relay has already claimed fires once, like any claimed timer. Schedules take a time zone (IANA name, default UTC) and may be fixed intervals as well as cron expressions; each actor's run history is derived from the receipts of its tick commands, so it needs no table, and it's bounded by `keepReceipts`. ADR 0021 needs two amendments: the tick key must include the zone (today it's `$cron:<canonical expression>`, evaluated in UTC, so one expression in two zones would collide), and the catch-up rule must cover zones and intervals. A wall-clock time that doesn't exist during a spring-forward transition fires at the first instant after the gap; a time that repeats during fall-back fires once.
- **Evidence.**
  - The cron half of the **Singleton uniqueness** gate: two runners produce one logical tick.
  - G1 with cron.
  - The **API shape** check: a cron target that takes input doesn't compile.
  - Across daylight-saving transitions in a non-UTC zone, a skipped time fires once just after the gap and a repeated time fires once, never twice.

**M2.6 to M2.8: workflows.**

- **The engine.** It is the framework `WorkflowEngine` from [ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md): steps in `actor_workflow_step` on the owner's shard, and clocks as outbox timers.
- **What ADR 0022 settles.**
  - the schema;
  - `WorkflowRun`;
  - `waitFor` registration;
  - typed step constructors (`Ship.step`, `sleep`, `wait`, `race`) with static names, and the manifest derived from them;
  - `wf.version`;
  - typed step constructors with explicit names (decided 2026-09-26), so a step's identity never comes from its position in the code;
  - the deploy check from [ADR 0014](../decisions/0014-adoption-observation-and-client-reach.md).
- **Evidence.**
  - The **Workflow engine** suite, run against both engines.
  - The **Workflow tenant isolation** and **`waitFor` registration** gates.
  - The **Workflow compatibility** check.
  - W1 and W2.
  - "Workflow resumes elsewhere" on the harness, and "Event races workflow wait registration".
  - H2: a workflow keeps running with its recorded attribution after its starting caller loses access.
- **Run view.** M2.7 and M2.8 expose each execution's steps, attempts, inputs, outputs and errors through CR.4's views (`durable.workflows` and `durable.workflow_steps`; see ADR 0028), so the inspector (CR.5) can show a step-level run history.
- **Size.** M2.7 is a three-PR stack (L+, about four days): engine and storage; typed step constructors, the registry, the manifest, and marker rows at start; then waits and resume with tenant and attribution. The constructors added about a day when ADR 0022 chose them over declared name lists.

**M2.9 and M2.10: connections.**

- **What ADR 0023 settles.**
  - A transport layer holds sockets and outlives activations. M2 uses an in-process test transport, and M3 adds WebSocket.
  - `actor_connections`, with 16 KiB state.
  - Waking across runners.
  - `Actor.stream`.
  - The session revocation bound.
  - Decided 2026-09-26: a broadcast may wake a parked actor, and after the owner actor's runner crashes the client's socket stays open and resyncs from its cursor. ADR 0023 (#64) amends [contract 07](../contracts/07-realtime.md) so parking survives the loss of the actor's owner, but not the death of the process holding the socket. In a single-process deployment those are the same process, so the guarantee doesn't apply there.
- **Evidence.**
  - The **Connection park** gate and C1.
  - "Parked connection wakes" and "Live or parked session loses authorization".
  - A command, intent, timer, or subscription event that wakes a parked actor on one runner broadcasts to connections parked on another, and a frame wakes a parked actor on another runner ([ADR 0023](../decisions/0023-connections-parking-and-streams.md), Q3).
  - An owner killed between commit and broadcast flush resyncs its connections in place with no lost event (C4, Q10).
  - H2's session half: a parked session that loses access reauthorizes or disconnects within the bound.
  - Owner death: the socket holder keeps the socket open and sends `Resync`, the client answers `ResyncDone`, and the connection closes with `OwnerLost` if no new owner takes over within 30 seconds. This proves the failure-matrix row ADR 0023 adds for owner loss.
- **Size.** Two PRs: connections, parking, and the test transport first, then `Actor.stream`.

**M2.12 and M2.13: effect cancellation and per-actor caps.** General uses: rate-limiting calls to any provider, and cancelling a scheduled send such as a reminder email.

- **What ADR 0024 decides.**
  - It replaces [contract 08](../contracts/08-background-work.md)'s paragraph saying cancellation and per-actor caps are not provided and a performed effect can't be withdrawn, and amends [ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md) §3.
  - A keyed effect cancelled from a later turn, mirroring `Intent.key` and `Intent.cancel` (spelling proposed, for example `turn.perform(e, { key })`).
  - Semantics by state: a pending effect is deleted in the cancelling turn and never runs; a running one is interrupted best-effort. A completed provider call can't be undone ([contract 08](../contracts/08-background-work.md)), so a result that arrives after cancel stays visible rather than lost. Because ADR 0012 requires a route's input to match the executor's return type, the ADR prefers a separate `onCancelled` route over a flag on `onSuccess`.
  - `policy.effects[Tag].concurrency: { perActor: n }`, enforced across runners by the relay's claim, and whether a deployment-wide limit per effect type belongs too.
- **Evidence for M2.13.**
  - Cancel before claim never runs; cancel while running never loses or doubles an outcome (P1); a cancel in a turn that rolls back cancels nothing.
  - With `perActor: n`, no more than n executions for one actor are in flight across three runners and a runner kill.
  - New failure-matrix rows "Effect cancelled while executing" and "Effect result arrives after cancel".

**M2.14 and M2.15: `turn.mint`.** General use: an order that creates one shipment actor per package.

- **What ADR 0025 decides.** `turn.mint(Shipment)` returns an id derived by a documented hash (a v5- or v8-style UUID, not v7) from the tenant, the parent's actor type and id, the turn's command id, the call's ordinal, and the child's type. A replay returns the same id, and the same command id at two different parents mints different children. The child is created only by a creating intent sent in the same turn. It amends [ADR 0010](../decisions/0010-one-way-effect-native-api.md), [ADR 0013](../decisions/0013-m0-reconciliation.md), [contract 01](../contracts/01-actor-authority.md), the glossary's "Minted actor", and the server API, which all make `X.create()` the only way to mint.
- **Evidence for M2.15.** A turn rerun after a `beforeCommit` crash or a commit-unknown outcome mints the same child ids; a mint inside a turn batch stays deterministic; the same command id at two parents mints distinct children; a declared failure creates no child (invariant M1); only the parent's intent can create the child.

**M2.16: cross-actor event subscriptions (design).** General uses: projections and fan-in. ADR 0026 (accepted 2026-09-26, every recommended default) decides a declared subscription that delivers each committed source event as a System command whose id derives from the subscription's name, the subscriber, the source, and the cursor (so two subscriptions never share an id), durable subscriber cursors, explicit retention gaps, whether a lagging subscriber holds back `keepEvents` pruning, and same-tenant scope. It amends [contract 04](../contracts/04-receipts.md), which today says command ids come from handles and clients, following ADR 0012's derived System ids. A delivery wakes a hibernated subscriber (decided 2026-09-26). ADR 0026 also settles: whether contract 07's revocation bound for subscriptions covers actor-to-actor subscriptions; the caller and attribution a delivery carries under [contract 10](../contracts/10-security.md); and what happens when the subscriber declares `createdBy` and doesn't exist yet, since today that returns `NotCreated` without a receipt and a delivery would retry forever. [Contract 05](../contracts/05-messaging.md)'s owner-only `waitFor` is unchanged. [M3.7](M3.md) builds it in wave 4, pulled forward from wave 6.

**M2.17 and M2.18: executor progress frames.** General uses: progress from transcoding, bulk imports, or report generation, shown before the result commits.

- **What [ADR 0030](../decisions/0030-executor-progress-frames.md) (accepted) decides.** `X.Executor` gains `progress(E, frame)`. Frames are best-effort, pre-commit, and never state or events; they go to the owner actor's connections and streams that opted in. [Contract 07](../contracts/07-realtime.md) gains a labelled exception to "only committed state publishes".
- **Evidence for M2.18.** Frames reach a parked connection on another runner; a lost frame loses nothing durable; frames after the `onSuccess` commit are dropped; a caller without access gets none.

**CR.3: docs site.** Docs only, so it starts now. A static site built from `docs/api` plus new guides (quickstart, concepts, testing, deploy), an "Effect all the way into the commit" guide, `llms.txt`, a Markdown copy of each page, and a comparison page that cites competitors' docs and makes no scale, availability or speed claims. Contracts and ADRs stay in the repo and are linked.

**CR.4: SQL inspection views.** ADR 0028 adds read-only, versioned views in a `durable` schema over actors, receipts, events, outbox, effects, dead letters, and workflow executions and steps. Its migration is `0013`, so it merges after M2.7's `0012_workflows`. `0013` includes the workflow views; a cron run-history view is additive after M2.5. Views never widen tenant access and can't be written through. They're a public, stable surface that works in `psql`, Grafana or Metabase, and the base for the `durable dev` inspector ([CR.5](M3.md)).

**P1 and P4: round trips.**

- **What ADR 0020 designs.** The turn at two round trips, as [ADR 0005](../decisions/0005-turn-latency-batching-and-regional-placement.md) describes. Round trip 1 is `BEGIN`, tenant scope, the generation fence, and the receipt insert-or-resolve. Round trip 2 is the writes, the receipt result, and `COMMIT`. The ADR picks the mechanism with a spike.
- **Contract order is unchanged.** Fence, then receipt, then handler. Two round trips is the target, and no path runs a handler before its receipt is checked.
- **Evidence.**
  - The **Two-round-trip turns and state cache** check: exactly two round trips with no handler statements.
  - A generation advanced by another runner makes the stale activation fail and reload.
  - Every existing crash case stays green, and T2's baseline is updated.
- **P4 status.** Implemented in [#130](https://github.com/Rika-Labs/durable-actors/issues/130): a turn pool of leased, multiplexed sessions, pipelined admission and commit groups, and an activation cache that reloads after a stale fence. The `Statements` gate now also records turn round trips per operation.

**P5 and P6: batches and merging.**

- **Rules.** Batches take only commands already waiting, with a cap of 32. Each command keeps its own receipt and failure isolation. Batch N+1's admission round trip may be sent while batch N commits, but its handlers wait for their own fence; ADR 0020 amends [ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md)'s in-memory speculative batches and the matching allowance in contract 02, and P5 updates the **Pipelined batches** check, invariant B1, and the "Pipelined batch N fails to commit" row to match. Commutative merging takes up to 1,024 queued inputs and never waits.
- **Evidence.**
  - The **Turn batches**, **Pipelined batches**, and **Merging** checks.
  - B1 and C2.
  - "Pipelined batch N fails to commit" and "Commutative merge turn fails".
- **P5 status.** Turn batches are in [#160](https://github.com/Rika-Labs/durable-actors/issues/160): a framework mailbox per activation, batches of up to 32 waiting commands in one two-round-trip transaction, per-command receipts and declared-failure isolation, and defect isolation by rerunning a failed batch's commands one per transaction. Pipelined batches follow in a second PR.

**T2 to T7: testing.**

- **T2: statement gate.** Statements per operation is the only benchmark metric that is stable across machines, so it is the one CI enforces.
- **T3: property tests.** Generated inputs with `effect/unstable/arbitrary`, plus model-based tests of receipts, cursors, timers, and table scoping.
- **T4 and T4b: CI reliability.** T4 fixes the known CI flakes and adds a nightly stress run. T4b extends the process-kill suite to reducers, dead letters, blobs, and owned rows.
- **T6: deterministic simulation.** Implements `ActorTest.simulate` from [ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md), which covers invariant X1:
  - It runs the real turn path under a seeded scheduler, with these faults: crash before and after commit, dropped replies, relay crash, clock skew, and runner kill. Primary failover waits for M5.
  - 20 fixed seeds run on PRs and 10,000 seeds nightly.
  - Status: `ActorTest.simulate` covers every fault above except runner kill, which T7 and the multi-runner harness cover, since a simulation runs one runtime ([ledger](../verification/01-conformance.md#deterministic-simulation-t6)).
- **T7: failure drills.** Three runner processes run under load, and a runner and the relay are killed with SIGKILL. The drills measure recovery time and count lost and duplicated work.
  - Status: `crash/drills/runner.test.ts` runs on Postgres in `test:integration` ([ledger](../verification/01-conformance.md#failure-drills-t7)).
- **Scale.** Scale runs are in [#66](https://github.com/Rika-Labs/durable-actors/issues/66), on dedicated hardware. T7's drills check correctness on a cloud VM: no lost or duplicated work after a kill.

## Excluded

- Transports (HTTP, WebSocket, SSE), the Promise client, and browser optimistic reducers are M3. HTTP and the client run alongside M2's waves 3 and 4.
- Drain, observability, restore, and the single-region hosted edge are M4. Regions are [later](M4.md#later-when-hosted-usage-asks).
- Neki is M5 and [#66](https://github.com/Rika-Labs/durable-actors/issues/66).
- Tenant-scoped content-addressed blobs and PGlite as an embedded production backend are M4. Building cross-actor event subscriptions is M3.
- A one-round-trip turn. Two round trips is the target.
- Exact cancellation of a timer the relay has already claimed. [Contract 05](../contracts/05-messaging.md) keeps it firing: its delivery "completes at most one receiver transition".

export const Send = Actor.command("Send")
export const Digest = Actor.make("Digest", {
  key: Actor.singleton,
  api: { Send },
  policy: { cron: { "0 8 * * *": Send }, cronSkipIfOlderThan: "1 hour" },
})

// M2.7: an appeal waits for a moderator's decision, durably.
export class AppealDecided extends Actor.Event<AppealDecided>()("AppealDecided", {
  messageId: Schema.String,
  restore: Schema.Boolean,
}) {}
export const Appeal = Actor.workflow("Appeal", {
  input: { messageId: Schema.String },
  output: Schema.Boolean,
  versions: { "notify-moderators": { current: 1 } },
})
export const Notify = Appeal.step("notify", { input: Schema.String })
export const AwaitDecision = Appeal.wait("decision", AppealDecided)
export const DecideAppeal = Actor.command("DecideAppeal", {
  input: { messageId: Schema.String, restore: Schema.Boolean },
})

// M2.10: typing indicators travel as frames, never as commands.
export const Presence = Actor.connection("Presence", {
  state: Schema.Struct({ user: Schema.String }),
  frames: {
    client: Schema.Struct({ typing: Schema.Boolean }),
    server: Schema.Struct({ typing: Schema.Array(Schema.String) }),
  },
})

// M2.15: each reply thread is its own minted actor (no key), created by the room's turn.
// Open and Reply are ordinary commands declared like Post.
export const Thread = Actor.make("Thread", { api: { Open, Reply }, policy: { createdBy: Open } })
export const StartThread = Actor.command("StartThread", {
  input: { messageId: Schema.String },
  output: Schema.String,
})

export const Room = Actor.make("Room", {
  // ...M1 members, plus:
  events: [MessagePosted, RoomArchived, AppealDecided],
  api: { Post, Archive, Recent, History, React, Appeal, DecideAppeal, StartThread, Presence },

    connections: "park",
    effects: {
      // M2.13: at most two moderation calls in flight per room
      ModerateMessage: {
        retry: { times: 5 },
        concurrency: { perActor: 2 },
        onSuccess: Moderated,
        onDeadLetter: ModerationFailed,

  },
})

### Handlers (`examples/chat/src/room/layer.ts`)

```ts
Appeal: Effect.fn(function* ({ messageId }) {
  const wf = yield* Room.Workflow
  if ((yield* wf.version("notify-moderators")) >= 1) yield* Notify.run(messageId, moderators.notify)
  const decided = yield* AwaitDecision({
    where: (e) => e.messageId === messageId,
    timeout: "3 days",
  })
  return Option.match(decided, { onNone: () => false, onSome: (e) => e.restore })
}),

StartThread: Effect.fn(function* ({ messageId }) {
  const turn = yield* Room.Turn
  const id = yield* turn.mint(Thread) // the same id if this turn is replayed
  const thread = yield* Thread.intents(id)
  yield* thread.Open({ room: turn.id, messageId }) // creates the thread after this turn commits
  return id
}),

DecideAppeal: Effect.fn(function* ({ messageId, restore }) {
  const turn = yield* Room.Turn
  yield* turn.emit(new AppealDecided({ messageId, restore })) // resolves the waiting workflow
}),

Presence: Effect.fn(function* (frames) {
  const conn = yield* Room.Connection
  yield* Stream.runForEach(frames, ({ typing }) =>
    conn.broadcast({ typing: typing ? [conn.state.user] : [] }),
  )
}),
```

## Exit criteria

M2 is complete when all of these hold:

- Every slice above is merged with its cases passing on Postgres in CI, and on PGlite where they apply.
- `examples/chat` passes on three runners with a runner killed mid-test.
- T6 runs nightly with no unreproduced failures.
- Every slice's benchmark scenario has committed results, and statements per operation match T2's baseline.
- The conformance ledger, support matrix, and API docs record what M2 proved.

This closes multi-runner support on one Postgres database. It does not close transports, Neki, or hosted support.

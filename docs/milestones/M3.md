# M3: Served actors and the browser client

**Responsibility:** define the M3 slices, their order, and the exit test.  
**Authority:** delivery plan.  
**Owner role:** delivery/runtime lead.
**Change policy:** a change requires delivery lead sign-off.

M3 serves actors over the network with `Actor.serve`:

- HTTP commands and queries, with OpenAPI;
- WebSocket connections;
- SSE event feeds;
- the browser-safe Promise client, `@durable-actors/core/client`, which runs reducers optimistically;
- cross-actor event subscriptions, designed in [M2.16](M2.md): committed source events delivered as commands to subscriber actors, waking them if they're hibernated.

The exit test is `examples/chat` served to a browser UI, driven by a Playwright test that loses its connection, reconnects, and replays from its cursor.

Spellings follow [server API](../api/01-server-api.md), the [TypeScript SDK](../api/03-typescript-sdk.md), the [protocol contract](../contracts/protocol.md), and the [error model](../contracts/error-model.md). [ADR 0027](../decisions/0027-served-protocol.md) (accepted 2026-09-26) settles the wire format.

## Rules for every slice

The [M2 rules](M2.md#rules-for-every-slice) apply. Transport slices also follow [contract 07](../contracts/07-realtime.md)'s change policy: every transport tests the race between a snapshot and live events, loss, replay, and revocation.

## Slice details

**M3.1: ADR 0027, the served protocol.** Accepted 2026-09-26 with every recommended default. It decides:

- the wire format for commands, queries, event feeds, and connections;
- how the command id and its expiry travel;
- the error envelope: `retryAfter`, `InvalidInput`, and `TransportError` exist only at this boundary;
- `Actor.serve` authentication: `Actor.auth.none` is the explicit opt-out, and a JWT verifier is the first provider;
- how OpenAPI is generated;
- the principal header size limit;
- SSE resume from an exclusive cursor;
- the revocation bound for live sessions (ADR 0023's default, carried over the wire).

**M3.2: HTTP.**

- **Evidence:**
  - the **Per-call caller over HTTP** gate and H1;
  - R3 over HTTP;
  - the row "HTTP credentials absent/changed";
  - the **Internal section** check: internal commands are absent from HTTP and OpenAPI;
  - `retryAfter` on retryable reasons.
- **Other languages:** a guide shows how to generate clients from `/openapi.json` with standard tools. Hand-written Rust, Swift or Python SDKs are out of scope; [M6.6](M6.md) covers MCP and generated clients in full.
- **Benchmark:** `http`, which measures transport overhead against the embedded path.

**M3.3: WebSocket and SSE.**

- **Evidence:**
  - contract 07's four transport tests;
  - rows "Socket-owning process dies" and "Live or parked session loses authorization";
  - a parked connection stays parked over a real socket;
  - executor progress frames ([M2.18](M2.md)) reach a WebSocket client.
- **Benchmark:** `ws` and `sse`, covering reconnect waves and fan-out.

**M3.4: Promise client.**

- **Behavior:** a command keeps its id across retries. An expired id comes back as `CommandExpired`, and the client never mints a replacement. Feeds and connections wait for M3.5, because they need M3.3's transports.
- **Evidence:** R3 through the client, plus rows "Caller gives up before a reply" and "External identity expires before delivery or retry".
- **Benchmark:** `client`.

**M3.5: client feeds, connections, and optimistic reducers.**

- **Behavior:** event feeds are `AsyncIterable` and resume from an exclusive cursor. Connections have typed `send` and `close`. A browser handle applies a reducer at once, reapplies pending inputs on top of each committed state, and drops each input when its receipt arrives.
- **Evidence:** C3, the row "Optimistic reducer rejected by the server", and the client half of the **Reducers** check, in a Playwright e2e test.

**M3.6: examples.** A set, not a single demo:

- the counter and the chat room, served to a small browser UI;
- presence and live cursors over connections;
- billing, with cron and a workflow;
- `examples/coding-agent`, a showcase built only from public members (effects, workflows, and streams). It adds no framework feature ([vision](../vision/06-developer-experience.md)).

`examples/orders` is its own slice (CR.8).

- **Status:** the browser UIs are in. `examples/counter/src/web` serves the counter at `/counters/<id>` (Promise client) and `/react/counters/<id>` (`@durable-actors/react`); its `Increment` now emits an `Incremented` event on a feed, and each page shows the count from that feed. `examples/chat/src/web` serves the `Cursor` actor's `Live` connection at `/cursors/<doc>` and `/react/cursors/<doc>`. Playwright covers each in [`apps/e2e`](../../apps/e2e): `counter.e2e.ts` (increments show, and a second tab sees them live) and `cursors.e2e.ts` (two pages see each other's cursor move and leave, and a late page sees where the others are), each against both flavours of the page. Screenshots are in `docs/verification/screenshots`. Presence and live cursors have no example directory of their own, so they stay in `examples/chat` (ADR 0001 lists only `counter`, `chat` and `coding-agent`).

**CR.5: `durable dev` and a local inspector.** A `durable dev` command in `apps/cli` runs the app on PGlite or Postgres and serves a local inspector over CR.4's views: actors and generations, decoded state, each command's receipt and what committed with it, the event timeline, outbox, timers, effects and dead letters, workflow step history, and connections. Commands run through M3.2. Retrying a dead letter waits for M4.6's audited repair.

- **Status:** `durable dev --entry` and `Inspector.serve` (the JSON API over the views, tenant-scoped by its `auth` and read-only) are in the first CR.5 PR, with `conformance/inspector.ts`; the second adds the browser page at `/_durable/inspector`. Connections are not shown until an inspection view covers them.

**CR.6: `@durable-actors/react`.** `useActor`, `useCommand` (one command id per user intent, reused across retries, with expiry surfaced), `useQuery`, `useEventFeed` (cursor persisted and resumed, `RetentionGap` surfaced), `useConnection`, and M3.5's optimistic reducers. SSR-safe.

- **Evidence:** a Playwright e2e test that retries a command after a dropped response and sees one receipt, and resumes a feed after reconnect with no gap.

**CR.8: `examples/orders`.** The flagship example: an app with existing `customers` and `products` tables. An `Order` actor owns order-line rows; `Place` writes rows, events and a `Charge` effect with a provider idempotency key; `turn.mint` creates `Shipment` children. The HTTP route reads `customers` and `products` with the app's own Drizzle client, outside the actor, and passes the values it needs as `Place` input; the walkthrough says that read isn't in the turn's snapshot. The cross-order report is plain application SQL over the owned table, outside any turn, because [queries](../api/04-drizzle.md) may read only owned tables and fleet-wide reads wait for `Fleet.view` ([M6.3](M6.md)).

- **Evidence:** a CI crash drill on Postgres kills the runner at every fault point, using the process-kill harness from T4b and T7. It asserts that no acknowledged order is lost and that the fake provider's ledger applies at most one charge per idempotency key. The executor may run more than once ([contract 08](../contracts/08-background-work.md)), so the drill counts applied charges, not calls.

**CR.12: published performance targets.** A benchmark page on the docs site, generated from committed results, with methodology, hardware and network round-trip time. It's published only after P4 and P5, measured with the runner and Postgres on separate machines. Every latency target sits next to a correctness column: acknowledged-but-lost commands and commands applied twice under repeated SIGKILL, both expected to be 0. It also publishes a comparison with Rivet (approved 2026-09-26): the same counter and chat workloads on self-hosted Rivet in its recommended setup, over the same real network, with the scripts and method published. Latency is compared per whole command, never per in-memory read.

**M3.7: cross-actor event subscriptions.** General uses: projections and fan-in.

- **Evidence:**
  - every committed source event takes effect on the subscriber exactly once (derived id and subscriber cursor per subscription, epoch, and source cursor), across runner kills and relay crashes;
  - a rolled-back source turn delivers nothing (E1);
  - a pruned gap is delivered as `RetentionGap`, never skipped;
  - a cross-tenant subscription can't be expressed, and a tenant mismatch at delivery is a defect;
  - new failure-matrix rows "Subscriber crashes after delivery commit" and "Source events pruned before delivery".
- **Benchmark:** `subscriptions`, measuring lag from source commit to subscriber commit, and fan-in from 10^4 sources.
- **Status:** built in two PRs. The first (storage and delivery: `0017_subscriptions`, declarations, feed and control rows, delivery, receipts and the applied cursor, epochs, `policy.subscribers`) is #186; the second, stacked on it, adds retention holds with `RetentionGap`, the removed-declaration cleanup, the hibernated and parked wake cases with post-commit broadcasts, and the workflow-wait composition. `0017` merges after `0015_effect_control` (#125) and `0016_final_effect_failures` (#159).

**T9: M3 benchmark pass on a cloud VM.** Reconnect waves and fan-out at scale are in [#66](https://github.com/Rika-Labs/durable-actors/issues/66). T9 covers:

- transport p50 and p99 against the embedded path;
- reconnect waves;
- the 16 KiB connection-state limit;
- parked-connection memory;
- the largest supported principal header.

## Excluded

- Read-your-writes from replicas (Q1), the hosted edge, and signed assertions are M4.
- Offline clients and generated MCP and Python clients are M6.
- Live query `watch` is M6.

## The served chat room

### Server (`examples/chat/src/main.ts`)

```ts
const ChatServer = Actor.serve({
  actors: [Room, Digest], // definitions; their layers are provided below
  auth: Actor.auth.jwt({ issuer, audience: "chat", jwks, tenant: (claims) => claims.org_id }),
  basePath: "/api",
  openapi: { path: "/openapi.json" },
})

BunRuntime.runMain(
  Layer.launch(
    HttpRouter.serve(ChatServer).pipe(
      Layer.provide(BunHttpServer.layer({ port: 8080 })),
      Layer.provide([RoomLive, RoomReads, RoomEffects, DigestLive]),
      Layer.provideMerge(Actors.layer({ authorize })), // the same authorize as examples/counter
      Layer.provide(Database.postgres({ url: Redacted.make(url) })),
    ),
  ),
)
```

### Browser (`examples/chat/src/web/room.ts`)

```ts
import { Room } from "../room/contract.ts"

const room = Room.client({ baseUrl: "/api", headers: { authorization } }).get(roomId)

await room.React(1) // applied to room.state at once, confirmed or rolled back by its receipt
const id = await room.Post({ body: "hello" }) // same command id across retries

for await (const entry of room.events(MessagePosted, { after: cursor })) render(entry) // SSE feed with Last-Event-ID resumption (ADR 0027)

const presence = await room.Presence.connect({ user: me })
presence.send({ typing: true })
for await (const frame of presence.frames) showTyping(frame.typing)
```

### What the tests prove

test("replays events after a dropped socket and never shows a gap as continuous", async ({ page }) => {

  await page.context().setOffline(false)

## Exit criteria

M3 is complete when all of these hold:

- Every slice is merged with its cases passing on Postgres in CI, and on PGlite where they apply.
- The Playwright test for the chat room passes in CI.
- T9's cloud-VM results are in the [performance document](../../BENCHMARKS.md).
- The support matrix records served HTTP, WebSocket, and SSE on Postgres.

This closes self-hosted served support on one Postgres database. It does not close hosted support.

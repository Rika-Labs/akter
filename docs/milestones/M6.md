# M6: Adoption, observation, and reach

**Responsibility:** define the M6 slices, their order, and the exit test.  
**Authority:** delivery plan.  
**Owner role:** delivery/runtime lead.
**Change policy:** a change requires delivery lead sign-off.

M6 follows [ADR 0014](../decisions/0014-adoption-observation-and-client-reach.md). It helps brownfield Postgres applications and clients outside the browser, without adding a new way to mutate data:

- adopting existing schemas;
- bounded live-query observation;
- fleet views;
- inspection and export;
- offline clients;
- generated MCP and language clients;
- scale-to-zero serving.

Every slice starts with its ADR or a design section, because each one names a question that ADR 0014 left open.

## Order of work

ADR 0014's order:

1. adoption;
2. observation, then fleet views;
3. offline;
4. inspection and export;
5. generated protocols;
6. scale-to-zero.

Adoption, offline, export and protocols touch separate subsystems, so they can run in parallel once their ADRs are accepted.

## Slice details

**M6.1: adoption.**

- **What it does:** an existing table maps its tenant and actor columns. The CLI first reports legacy direct writers, then enforces actor-scoped writes with database privileges or a guard.
- **Evidence:** the **Adoption** check, and A4 for adopted tables. Neither a second pool nor raw SQL can bypass the guard. [ADR 0054](../decisions/0054-existing-schema-adoption.md) is proposed.

**M6.2: query observation.** Only a documented query algebra produces invalidations. Anything else is rejected, never treated as live by mistake. A rerun may coalesce intermediate states.

- **Evidence:** the **Query observation** check. [ADR 0055](../decisions/0055-query-observation.md) is proposed.

**M6.3: fleet views.** [ADR 0056](../decisions/0056-fleet-views.md) proposes the engine: built into the runtime, fed by one logical replication slot, and needing migration `0025_fleet`. [ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md) listed Electric SQL, Materialize, RisingWave, Feldera, and `pg_ivm` as candidates, and the ADR says why it does not adopt them. Views are explicitly eventually consistent and never on the turn path.

**M6.4: inspection and export.** An export is a reproducible seed of current state and pending obligations. It is neither history nor an authorization bypass. Inspection itself shipped with M4.6 ([ADR 0050](../decisions/0050-operator-authority-and-audited-repair.md)); this slice adds the export and the seed a test starts from.

- **Evidence:** the **Inspection and export** check, in `conformance/export.ts`.
- **Status:** built ([#335](https://github.com/Rika-Labs/durable-actors/issues/335)); the ledger lists the cases. No migration.

The design section is this slice. ADR 0050 and the [inspection views](../operations/inspection-views.md) settle most of it, and each choice below follows them.

1. **Authority.** `export` is a new operator action, granted on its own with the same `{ tenant, actorType?, actorId? }` scope as `inspect`. Neither `inspect` nor `receipts.read` implies it: `inspect` shows the same state on screen, but a seed is a file that outlives the request and can be replayed, so who may copy an actor out is granted and audited separately. A seed holds no receipt outcomes. `GET /operator/actors/:type/:id/export?tenant=` answers the seed, 404 when the tenant has no such actor, and 409 `ExportRefused` when a stored value does not decode or the actor holds more than 10,000 pending intents or 10,000 pending effects. The tenant comes from the request and the grant, never from the actor's row. A seed of another tenant's actor is a 404 whatever the grant.
2. **Audit and read-only.** The route follows ADR 0050's read rule: the audit row (action `export`, actor, capability, outcome `"read"`) commits before the answer, an authenticated operator refused by scope is recorded as `"denied"`, and an unauthenticated request is not recorded. The export runs in one read-only, repeatable-read transaction, so its state and pending work come from one snapshot and Postgres refuses any write it could attempt. It reads the runtime tables through the actor's routing key, not only the `durable` views, because the views do not show whether an effect was cancelled or has failed for good, and such an effect is not pending. The audit row names the operator and actor, never a value.
3. **Contents.** A seed is one JSON file, `format: 1`: the actor type and id, the `created` marker, the stored state and its migration version, the pending intents and timers (target, command, payload, key, and `dueInMs`), and the pending effects (name, payload, payload version, key, and `dueInMs`). Due times are relative to the export, so a replay follows the test's clock. Cancelled effects and effects that have failed for good are left out.
4. **What a seed never carries.** The tenant, callers, and credentials are absent, so a seed cannot confer authority and a replay runs under the test's own tenant and caller. Receipts, events, workflow executions, and dead letters are omitted and counted in `omitted`, so a reader sees what a replay starts without. Rows of owned tables, blob entries, subscription cursors, and connections are omitted and not counted. This is a current-state seed: there is no history, no rewind, and a fresh generation.
5. **Replay.** `test.actor(X, id, { seed })` takes the path of a seed file, read through Effect's `FileSystem`, so a test that names a seed provides one. In one transaction it writes the actor's row, state, and pending work, staging the work as the caller the test runs as; `advance` then delivers it like any other work. It never overwrites: an existing actor, a seed of another actor type, a malformed or other-format file, and an effect the actor does not register each die and write nothing. A row the database refuses rolls the whole seed back.
6. **CLI.** `durable export Room/r1 --url <runner> --tenant <t> --output r1.seed [--token-env <name>] [--json]` reads the operator token like the other operator commands. The file is created for its owner alone and never replaces an existing file, because it holds the actor's data. The command prints counts, never a value.
7. **Redaction and retention.** No redaction option is built. The `export` capability, scoped to a tenant and actor type, is the boundary: an operator who may not see a payload holds no such capability. The runtime keeps no copy of a seed; retention of the file is the operator's, like dead letters' and audit rows'.

**M6.5: offline.** Queued commands keep their original ids. An expired id surfaces as a conflict, and the client never mints a new id to keep retrying.

- **Evidence:** the **Offline replay** check.

**M6.6: generated protocols.** OpenAPI, MCP and the Python client agree on schemas, member names, errors and command identity. A durable MCP tool call needs a stable operation id supplied by the caller.

- **Evidence:** the **Generated protocols** check.

**M6.7: scale-to-zero.** A cold runner recovers committed and due work. It doesn't claim parked-connection continuity without a gateway.

- **Evidence:** the **Scale-to-zero** check, with warm and cold benchmarks reported separately.

```sh
durable adopt observe invoices --report     # legacy writers, before enforcement
durable export Room/r1 --output r1.seed
```

## Excluded

- Historical rewind of past turns, until per-turn history has a defined retention and storage cost (ADR 0014).
- Arbitrary live SQL, and live fleet queries by default.

## Exit criteria

M6 is complete when every slice is merged with its check passing in CI, each ADR is accepted, and T15's cloud-VM results are in the [performance document](../verification/03-performance.md). The exit example is `examples/chat` served cold (M6.7), watched live (M6.2), and exported to a seed that `ActorTest` replays (M6.4). The API docs must describe only what shipped. The [post-foundation sketches](../api/post-foundation-sketches.md) move into the API docs as each one ships.

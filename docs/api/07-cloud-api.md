# The Akter Cloud API

**Responsibility:** describe the console's control-plane HTTP API and how it is built from its contract.  
**Authority:** normative API design.  
**Owner role:** cloud API.  
**Change policy:** a change to the contract in `packages/cloud-api` is a change to this document and to every client derived from it.

`@akter/cloud-api` (`packages/cloud-api`) declares the API once as an Effect `HttpApi` named `CloudApi`: every endpoint lives under `/api`, requires `Authentication`, and is described by Schema types. `apps/api` implements it. The console builds its client from the same declaration with `HttpApiClient`, and the served OpenAPI document is derived from it, so there is no second description to keep in step. A browser carries the Better Auth session cookie, a machine client sends `x-api-key`, and the `akter` CLI sends the session it got from Better Auth's device authorization grant as `Authorization: Bearer <token>` ([ADR 0085](../decisions/0085-cli-login-and-source-deploys.md)). A bearer session stands alone: a request that carries `Authorization` is answered by the bearer scheme only, so an invalid token is 401 even beside a valid cookie, and an `x-api-key` beside it is refused.

## Groups

- **Account:** `me`, profile, active organization, preferences (`/me/preferences`), notifications and pinned actors (`/me/pinned-actors`).
- **Organizations, members, invitations, API keys.** An organization's `plan` (in `/me`, `/me/active-organization`, organization reads and invitation previews) is a tagged value: `{ "_tag": "known", "id": <plan id> }` for a plan the pricing configuration defines, `{ "_tag": "unknown", "id": <stored id> }` for a stored plan it does not, so org context still loads, and `{ "_tag": "unbound" }` for an organization with no billing account, which is never reported as Free.
- **Projects:** list and create under `/organizations/:organizationId/projects`, then by id; environments, endpoints, variables, domains, regions and integrations.
- **Deployments:** list, create, upload a build context (`POST /projects/:projectId/sources`, a gzip-compressed tar of at most 64 MiB answered with its `sha256:` digest and size, stored once per project; access and the builder are checked before the body is read, `NotImplemented` answers a control plane without a builder, and a body over the limit is 413 `PayloadTooLarge` as soon as its `content-length` or its stream passes it), record a successful build (`POST .../deployments/:deploymentId/build`), detail, build log, roll back, redeploy. A create may name `source: { digest, dockerfile }`, an uploaded archive and the Dockerfile's path inside it; the control plane's builder then builds that archive instead of its own context, a redeploy rebuilds the same archive, a digest the project was never sent is `NotFound` (`source`), and a control plane without a builder answers `NotImplemented`. Recording an image requires a content-addressed digest, the deployment's commit and a complete string-valued environment snapshot. An identical retry does not enqueue another rollout. A rollback names an earlier deployment that was once live and redeploys its image and environment snapshot as a new deployment whose `rolledBackFrom` is that id; the deployment it replaces ends `rolled-back` once the new one is `live`, and stays `live` if the new one fails. A rollback is titled `Rollback to <short sha>: <message>` and a redeploy `Redeploy <short sha>: <message>`, where the message is the one the commit was first deployed with in that environment, so a redeploy of a rollback never nests titles. Unmeasured runner actor counts and CPU percentages are null. See the [deploy pipeline](08-deploy-pipeline.md).
- **Runtime:** inspection of a deployment's actors, commands, jobs, workflows, connections and dead letters, served by asking runners through the edge ([contract 11](../contracts/11-control-plane.md)). `POST .../runtime/commands` sends one command (`address`, `command`, JSON `payload` and an optional `commandId`, used as a client idempotency key and minted by the control plane when omitted) and answers with the actor's `result` and a `replayed` flag; the same key and payload reuse the durable runner assignment, while a different payload is a 409 `Conflict`. An error the actor returns is a 422 `CommandFailed` with its `errorTag` and `error`; runner admission refusals are typed 4xx `CommandRefused` errors whose `reason` is the framework's own refusal (`InvalidCommandId`, `InvalidInput` and the other `ActorError` reasons), taken out of the runner's envelope, with its tag in `reasonTag`. It needs write permission on the project and returns `NotFound` when that environment has no live deployment. The runner sees the command's caller as the signed-in user (`user:<id>`) or API key (`api-key:<id>`) that sent it, after the control plane has authorized the send ([contract 11](../contracts/11-control-plane.md)). A never-created actor address is valid and is created by first delivery; no inspector read is required. The runtime reads come from the runner's read-only inspector, after project read access is established: durable facts from its views, and live ones (rates, latency, awake actors, mailboxes, placement, subscribers, connections and the command stream) from the serving runner's memory, reported only while that runner is the only one; a field nothing measures is `null`, never invented ([contract 11](../contracts/11-control-plane.md), [ADR 0087](../decisions/0087-live-runtime-telemetry.md)). `GET .../runtime/actors/:actorType/:key` inspects one actor: committed state, generation, receipts, the newest cursor and emission time of each retained event, jobs and dead letters, the event feed cursor, the tenant and the newest timeline page; while one runner serves, each event's open feed subscribers, the actor's sockets, whether it is awake, its mailbox depth and, while awake, the runner and region holding it; turn and owned rows are `null`, and an actor that does not exist is `NotFound` with resource `actor`. A receipt carries its command, outcome tag (never the stored value), `caller` (`{ kind: "user" | "anonymous" | "system", subject, source }`, as the runner recorded it) and `expiresAt`; its commit time `at` is the database clock when its commit wrote it, `null` for a receipt written before runners recorded it. `.../receipts` and `.../timeline` page one actor's receipts (latest expiry first) and timeline (newest first: retained events at their emission time, and each command whose turn emitted events at that time, with `detail` the command id); `.../events` lists the newest event of each name. `overview` reports actor and pending-job totals, dead letters by job name and `lastDeployAt`, when the environment's newest deployment was created (`recentDeployments` is `null`; the deployments list has them); while one runner serves it also reports command rates and turn times, the awake count and the deepest mailbox; `sidebar-counts`, `actor-types` and `actor-types/:actorType` count actors by type, with awake actors, rate, p99 and deepest mailbox while one runner serves (`commands` is `null`); `actor-types/:actorType/activity` and `.../latency` report one type's committed turns over `1h`, `24h` or `7d` since the serving runner began recording (`since`), percentiles `null` with no turn; `actor-types/:actorType/instances` pages a type's actors with their last command and its commit time, and whether each is awake while one runner serves (a `status` filter is `NotImplemented`); `search` matches actor type names (`kind: "actor-type"`) and actor addresses (`kind: "actor"`) by prefix, at most 20 of each; `commands` pages the tenant's receipts as the command log, filtered by actor type and outcome (`replayed` is always empty, since a replay records no receipt), with `at` and `durationMs` the receipt's commit time and turn duration on the database clock (`null` on older receipts), `payloadPreview` `null` (receipts keep no payload) and `errorTag` the declared failure's tag; `commands/stream` sends each command the serving runner commits from then on as SSE, with a payload preview of at most 256 characters the runner cut and redacted; `connections` counts open sockets, SSE responses and event feeds, overall and by type (`parked`, `replayGaps` and their history are `null`); `schedules` lists each cron entry with its next due tick and its last committed run; `jobs` counts pending jobs as queued or retrying and dead letters, overall and by job name; `dead-letters` pages them newest first, each `id` its job id and `lastError` the first line of the stored cause, without stack frames or file paths; `workflows` pages executions newest first, `step` the step reached last numbered by the distinct steps recorded (`total` `null`), `waitingFor` its pending clock or wait step, `failed` a run that ended with a declared failure, defect or interruption, and `status` `null` when a finished run's result does not decode; a `status` filter is applied by the runner, so a page is short only at the end; `timers` reports the pending count and the soonest due time. Lists take `limit` (1 to 100, default 50) and an opaque `cursor`; one the API did not issue is `NotFound` (`cursor`). Activity, latency, the stream and connections are `NotImplemented` while more than one runner serves the environment; owned-table rows and dead-letter retry and discard remain `NotImplemented`. The declared workflow `step.index` counts from 1 and never exceeds a known `step.total`.
- **Billing, usage and the audit log** (`/organizations/:organizationId/audit-log`).

## Billing and usage

`GET /organizations/:organizationId/billing` returns the entitlement plan, provisional pricing flag, renewal date, payment method, billing email, monthly spend limit/estimate and `caps`. `plan` is a tagged union: an organization with a billing account gets `{ "_tag": "known", "id": <plan id>, ... }` with the plan's name, price and estimate, and one with no billing account gets `{ "_tag": "unbound" }` with no name, price or allowances, the spend limit is null and the current spend zero. Invoices come from `/billing/invoices`; the local Stripe stand-in serves each simulated invoice as a one-page PDF at its `pdfUrl` (`/billing/invoices/:invoiceId/pdf` on the API origin, never mounted in Stripe or production mode). `GET /billing/plans` lists every tier of the pricing configuration, cheapest first, to any signed-in caller: base price, allowances (included command equivalents, the hard command cap or null, included storage GB, concurrent connections), overage prices, features derived from that configuration (`command-cap`, `command-overage`, `storage-overage`, `storage-cap`, `checkout`) and each tier's `provisional` flag, with a catalog-wide `provisional` while any tier is. `PUT /billing/spend-limit` accepts nullable cents and checks the organization's plan before storing anything, so an unknown plan is refused with the limit unchanged; checkout and portal are `POST /billing/checkout` and `POST /billing/portal`. `POST /billing/plan` changes the prices on the existing subscription and returns its durable request identity/status. These mutations require an owner/admin or an unrestricted admin API key. Checkout and plan changes accept `pro`, `team` or `enterprise`; server configuration builds return URLs, never the caller. An optional `Idempotency-Key` names a mutation across retries. A session request survives process loss and returns the same URL for the same identity and input; conflicting input is refused.

Paid tier changes replace the existing subscription's base and meter prices together; they do not create another subscription. Entitlements follow canonical provider state, so a change awaiting payment cannot grant its requested plan. The portal manages billing details, payment methods, invoices and cancellation. Stripe does not support portal tier updates for these usage-based multi-price subscriptions; plan changes use the controlled endpoint instead. A live or ambiguous checkout request blocks another initial subscription until durable provider proof resolves it.

An ambiguous failed checkout can be recovered by retrying its original `Idempotency-Key` with identical input; the conflict response names that identity when another request is blocked. A retry keeps the provider identity rather than permitting a second initial subscription. Checkout and plan changes refuse a catalog that differs from the active pricing configuration, and plan changes invoice immediately with payment-gated updates.

The unauthenticated provider route `POST /api/billing/webhook` verifies `Stripe-Signature` against the exact raw body and configured endpoint secret. It is not a console endpoint. It resolves the organization from a durable customer binding, records a provider event once and reads canonical subscription state in a job; webhook snapshots and metadata cannot grant a plan. A temporarily unbound customer gets a retryable 503.

`GET /organizations/:organizationId/usage?period=YYYY-MM` returns the UTC month's hourly-imported usage, meter allowances/overages, daily committed commands and project totals. The `commands` meter is command equivalents: committed commands plus one fifth of reads. The `reads` meter is informational and shows the remaining shared allowance in read units; its cost is included once in the command-equivalent meter. Storage is sampled logical GB-months above the plan allowance at $0.30/GB-month. Project estimated costs allocate organization variable overage once; the subscription base remains organization-wide. Missing historical samples are not invented. `latestStorageSample` is the sum of the latest sampled bytes of each bound tenant of a serving deployment, with the newest of their sample hours, or null before any sample, whatever period is requested; a drained deployment's last sample is left out.

`caps` (in both the usage report and the billing summary) is the current admission state of `commands` (usage units, the same units as `QuotaExceeded`'s `limitUnits` and `usedUnits`: one per read and `unitsPerCommand` per command, a factor the `commands` cap always carries and no other cap does, so commands are `used / unitsPerCommand`), `spend` (cents, priced on the subscribed plan), `connections` (live leases) and `storage` (the largest latest sample of a serving deployment's tenant, since the edge checks storage per deployment and tenant; Free only). Each has `limit` (null when the cap does not apply), `used`, `atCap` (usage reached the limit) and `refusing` (the edge would refuse the next new command, or for `connections` the next connection). An organization with no billing account, which the edge refuses with `QuotaUnbound`, reports every cap `refusing` with `reason: "unbound"` and no limit. A plan the pricing configuration does not know answers both reads, and `PUT /billing/spend-limit`, with a 503 `Unavailable` whose `reason` is `unknownPlan`, as the edge refuses it. It is computed from the same rows by the same rules the edge admits by, so `refusing` can be true before `atCap` when a command no longer fits but a read still does.

`BILLING_MODE=local` uses persistent local Stripe tables and no provider credentials. `BILLING_MODE=stripe` requires `STRIPE_API_KEY` and `STRIPE_WEBHOOK_SECRET`; production rejects local mode and the published development webhook secret. API, edge and `akter billing setup` consume the same optional `BILLING_PRICING_CONFIG` JSON configuration. Planning paid values remain provisional until benchmark-backed prices are configured. `METER_CELLS` is a redacted operator array of `{ deploymentId, databaseUrl }`; durable `cloud_meter_tenant` allocations bind tenants, or a deployment's `*` fallback, to organizations/projects. The collector has no public ingest endpoint. Customer runners provide `CellUsageLive({ deploymentId })` from `@akter/metering`; configuring a collector alone does not enable runner accounting.

The intended public console origin is `https://app.akter.dev` (site `akter.dev`, documentation `docs.akter.dev`); these domains are not yet registered. Deployment configuration can use that origin for the API's same-origin `/api` surface and console return links. Local defaults remain loopback. Production checkout/plan changes refuse provisional paid prices; catalog setup is not permission to publish them before the benchmark. Billing reports distinguish the subscribed billing tier from effective entitlements during failed payment, so revoking paid access does not erase an existing subscription's cost estimate.

Hosted edge quota refusals distinguish command allowance, spend limit and concurrent connection limits. `POST .../runtime/commands` answers them with the framework's tags and payloads: `QuotaExceeded` (429, its `limitUnits`, `usedUnits` and `requestedUnits` in usage units with the `unitsPerCommand` one command weighs, so a refusal can be stated in commands), `SpendLimitExceeded` (402), `ConnectionLimitExceeded` (429) and `StorageQuotaExceeded` (429). Unknown allocations fail closed: a command the edge cannot bill, because the deployment's tenant has no organization, the organization has no billing account or its plan is not in the pricing configuration, is a 402 `QuotaUnbound` with the edge's `deployment`, `tenant` and `reason` (`tenant`, `account` or `plan`), never a generic 503. Metered hosted MCP requests are not yet attributable to a command receipt and are refused rather than guessed. Realtime messages are free, with WebSocket and SSE sessions sharing the concurrent connection cap.

Free storage uses a 0.5 decimal GB sampled admission cap with no overage billing; paid storage is $0.30/GB-month over allowance. At or above 500,000,000 bytes in the tenant's latest sample, new commands receive `StorageQuotaExceeded` (429), while reads, queries and existing command reservations continue. A later lower sample restores command admission. Storage is sampled hourly: growth can briefly overshoot by up to one sampling interval, and Free excess is never billed. The Free command cap and spend limits apply only when new requests are admitted at the edge. Already admitted internal turns, relay deliveries, timers and jobs may finish; there is no strict cell-side command-credit system.

## Errors

`Unauthorized` (401) comes from the authentication middleware. A caller without the role or key permission an operation needs gets `Forbidden` (403); the project access barrier gives that same answer for a missing project or one in another organization. After access is established, a resource absent from that scope is `NotFound` (404). A taken project slug or environment name is `Conflict` (409). An endpoint declared but not yet implemented answers `NotImplemented` (501).

`NotFound` (404) names what is missing in `resource`, a closed set (`actor`, `actor-type`, `api-key`, `command`, `cursor`, `deployment`, `domain`, `environment`, `invitation`, `live deployment`, `member`, `organization`, `project`, `source`), so a missing actor and an environment with no live deployment differ without reading `id`. Temporary edge or capacity failure is `Unavailable` (503), with `retryAfterSeconds`. `Unavailable` carries an optional `reason` from a closed set only when the cause is a known condition rather than an outage; `unknownPlan` means the organization's stored plan is not in the pricing configuration. A generic outage has no `reason`. Command retries MUST retain their supplied `commandId`; a new id would be a new command. Invalid runner admission is a typed 4xx `CommandRefused`, not a 500; actor access denial maps to `Forbidden`, while a refused deployment credential remains `Unavailable` so an operator can repair rotation or reachability. The API's request timeout defaults to 35 seconds, leaving response slack around the edge's 30-second cold-start bound. Operators who change that edge bound must configure `RUNTIME_REQUEST_TIMEOUT_SECONDS` accordingly. A malformed runner response remains an opaque defect.

Actor-mailbox backpressure also maps to `Unavailable`, including a runner's HTTP 429 `MailboxFull`. A remote runner `Defect` maps to an opaque, non-retryable 502 `RunnerDefect`; trace details and response bodies never reach the client. Keyed sends store only canonical payload hashes and retain expired keys as 410 tombstones for 30 days, so clients must not reuse a key for at least the retry window plus 30 days.

## Durable records behind it

Projects, environments, per-user preferences, pinned actors and audit entries are read and written only through the `Repository` service in `apps/api/src/repository.ts` ([contract 11](../contracts/11-control-plane.md)). Handlers translate its domain errors to the contract's errors, map its `DateTime` values to the contract's timestamps, and add what the repository does not store: the live status of a pinned actor, and the project's environments' deployments.

| Repository operation                                                            | Contract endpoint                                    |
| ------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `listProjects`, `getProject`, `createProject`, `updateProject`, `deleteProject` | Projects `list`, `get`, `create`, `update`, `delete` |
| `listEnvironments`, `getEnvironment`, `createEnvironment`, `deleteEnvironment`  | Projects environment endpoints                       |
| `getPreferences`, `updatePreferences`                                           | Account `getPreferences`, `updatePreferences`        |
| `getNotifications`, `updateNotifications`                                       | Account `getNotifications`, `setNotifications`       |
| `listPinnedActors`, `pinActor`, `unpinActor`                                    | Account pinned-actor endpoints                       |
| `recordAudit`, `listAudit`                                                      | Audit `list`, and any handler that records an action |

A handler checks the caller's access first (`Access.organization` or `Access.project`, whose organization it then passes to the repository), so the repository never receives an organization from a request body. Preferences need a person, not an API key, and are stored per user, not per organization. Changes made through Better Auth (organizations, members, invitations, API keys) are audited as a `requested` entry before and a completed entry after, in separate transactions, because Better Auth's own transaction cannot include the audit write.

The CLI that talks to this API is built with `effect/cli`, like every `akter` command ([CLI](06-cli.md)).

# Actor lifecycle

**Responsibility:** describe identity, activation, turns, and passivation.  
**Authority:** design.  
**Owner role:** runtime.
**Change policy:** a change that alters a contract guarantee requires an ADR.

An actor has a durable identity and a disposable activation. `Actor.make`'s `key` section selects named ids, framework-minted ids (key omitted), or `Actor.singleton`; durability follows declared sections rather than a separate actor kind ([ADR 0010](../decisions/0010-one-way-effect-native-api.md)). All three modes are implemented: `X.create()` mints branded UUIDv7s, singletons register through `Sharding.registerSingleton`, and `create` is restricted to minted actors in types and at runtime. Every runner serves a singleton's entity, and a keeper that Cluster's singleton registration runs on one runner wakes the default tenant's instance every second (or every half of `hibernateAfter`, if that is shorter, so the instance never idles out between wakes), so after its owner dies the activation, and its background loop, starts on whichever survivor takes the shard once the dead runner's lock expires. That movement has in-process multi-runner evidence on Postgres ([conformance](../verification/01-conformance.md#singleton-uniqueness-and-failover-m22)).

Even an actor without state, tables, events, effects, or blobs has fenced, receipted commands. Acquiring a handle writes nothing; the first turn establishes durable rows. A parent turn can mint an unkeyed child with `turn.mint`, which derives the id from the turn's identity without SQL; the child is created only by that turn's creating intent, whose System caller carries the mint proof. Before `created` is set, the child's creating transaction checks that the proof derives its id and that the parent's outbox still holds that intent's committed row (same tenant, sender, intent id as the command id, target, and command). The row, not the parent's receipt, is the evidence: it stays until its delivery commits, and retention never prunes it, while a receipt can be pruned before a long-delayed intent is due. `policy.createdBy` can require an explicit creating command before other commands are accepted — implemented as a `created` flag on the generation row, checked after receipt lookup under the fence and set atomically with the first successful creating command. Rows predating the policy read `created = false`, so applying it to existing data requires an application backfill migration.

Wake creates an activation `Scope` and runs the layer's build Effect, which acquires activation-local values (such as a `Ref`) and may fork background fibers with `Effect.forkScoped`; parked connections resume. `policy.hibernateAfter` ends the scope after idleness, currently realized as the entity `maxIdleTime` policy; parked connections are not implemented yet. Sleeping runs `Effect.addFinalizer` finalizers, interrupts forked fibers, and releases process-local resources without deleting receipts, state, events, timers, workflows, or business rows. Parked connections allow this while sockets remain open at their holder's transport; open streams keep the activation awake. With connections ([ADR 0023](../decisions/0023-connections-parking-and-streams.md)), the runtime owns the activation and shares it between the command entity and a connection entity: both reset one idle timer, and whichever runs first acquires the generation.

A singleton's background loop is a fiber forked in its build with `Effect.forkScoped`. It does not keep the actor awake. Expected failures are handled explicitly; a blanket cause-swallowing handler must not disguise a failed loop as completed work. Parking restarts the loop on the next wake, and transport-process loss still requires client reconnection. A singleton's build runs in its activation's scope, so a retryable defect's restart, such as a failed generation fence, interrupts the old loop and starts a new one with the rebuilt activation. The activation's resources belong to Cluster's entity scope, so they end with the entity even when a restart races its shutdown. With table-backed shard locks, a lock can expire under a runner that keeps serving, so a singleton activation reads its runner's lock row when it starts and every sixth of `shardLockExpiration`; once the row is older than half the expiration it closes its scope, which stops the loop, and refuses commands with a retryable defect, all before a healthy runner (which refreshes every third) could lose the lock or another runner acquire it. Advisory locks are held by the holder's database session, so no other runner can take the shard while it runs. A build that fails leaves the activation answering each command with that defect instead of rebuilding in a loop. Cron is M2.5 scope and is not implemented.

Each command is a serialized, fenced turn. The runtime locks the generation, checks the receipt, decodes keyed state through its migration chain (or reuses the activation's cached state), runs the handler, and commits state, table changes, events, intents, effects, and the receipt together. Queries read committed state and rows without an activation transaction. The implemented slice covers state, receipts, the migration chain, outbox intents and timers, and effects with routes — events are an M1 member — and bounds each turn by `policy.commandTimeout`/`policy.lockWait` and each mailbox by `policy.mailboxCapacity`.

Retryable runtime failures are defects that restart the activation; the caller's handle retries the same command id. A deterministic defect rolls back, records its cause in the turn span and log, and returns a `Die` to the caller while the activation remains resident; no receipt is written and no user code runs ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)).

Workflows are actor members in `api`. Outside a turn, calling the workflow on a handle returns a `WorkflowRun`. Inside a turn, `X.intents(id)` starts it as an outbox intent. The execution key is `[deployment, tenant, actor, id, workflow, key]`.

Cron is `policy.cron`, mapping expressions to zero-input commands. It is a per-actor outbox timer for named or minted actors and cluster-wide for a singleton. See [dispatch](04-dispatch.md).

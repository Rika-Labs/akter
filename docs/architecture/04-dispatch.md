# Dispatch and fencing

**Responsibility:** describe how work reaches one current actor generation.  
**Authority:** design.  
**Owner role:** runtime/reliability.
**Change policy:** a change that alters a contract guarantee requires an ADR.

Effect Cluster sharding routes a volatile command message to the current activation, but durable storage is the authority. The receipt committed inside the turn is the command's only durable admission record. External admission checks current authorization and command expiry; trusted recovery of already accepted work retains its durable authority. A command turn follows one order:

1. begin the transaction and set tenant scope;
2. `SELECT ... FOR UPDATE` the actor generation row;
3. resolve the command receipt under the [receipt contract](../contracts/04-receipts.md), replaying a matching outcome only through the appropriate caller-access or trusted-recovery path;
4. decode state through migrations, or reuse the activation's decoded copy from the same generation, and run the handler;
5. stage state, actor-table changes, events, intents, effects, and the receipt;
6. commit once, then notify delivery.

The framework pipelines steps 1–3 into one admission round trip and steps 5–6 into one commit round trip; handler-issued `turn.rows` statements are the only other round trips. [ADR 0020](../decisions/0020-two-round-trip-turn-pipeline.md) sends each group as pipelined extended-protocol statements on a multiplexed connection leased to the turn; PGlite runs the same groups one statement at a time. The activation caches the generation it fenced and its last committed state; a warm admission skips the state read, and a fence that finds another generation discards the cache and fails the turn as a stale generation, so the restarted activation reloads before any handler runs. Turn batches (below) are not implemented yet; every turn holds one command. The activation consumes its mailbox with `Entity.toLayerQueue`. When more commands for the actor are already waiting, it runs them as a turn batch in delivery order: one admission round trip resolves every receipt, handlers run in sequence, and one commit round trip persists all outcomes. While batch N commits, batch N+1's admission statements may ride in the same flight, but its handlers run only after its own fence and receipts are validated; replies, broadcasts, and outbox visibility follow each commit. A lone command is never delayed to form a batch. A defect or failed commit restarts the activation; uncommitted commands are retried by their callers, one per transaction until the failing command is processed. See [ADR 0005](../decisions/0005-turn-latency-batching-and-regional-placement.md).

A stale generation, lock timeout, commit-unknown result, or command execution timeout is a retryable defect: the activation restarts and the caller's handle retries the same command id. A caller's delivery timeout instead stops waiting and may return `ActorError` with reason `Timeout`; it does not cancel the admitted turn. An old writer may continue computing, but the generation fence prevents its commit. Deterministic defects roll back and follow the telemetry-only path described in [lifecycle](02-lifecycle.md).

Commands use volatile Cluster messages (`Persisted: false`), no Cluster `primaryKey`, and serialized entity handling ([ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md)). The framework owns deduplication through receipts and owns the only turn transaction; no reply is sent before commit.

Nothing staged by a handler is visible when the turn fails before commit. In particular, an intent is never delivered after a failed turn. A committed `actor_outbox` row is delivered after commit as a direct command and deduplicated by the receiver's receipt.

Client-minted command ids remain stable across retries. An authorized retry within the external retry horizon with different input produces `ActorError` with reason `CommandConflict`; the same input returns the stored receipt. Receipt access checks run without the handler. A caller mismatch or expired external identity must not fall through to a new handler execution, even after cleanup. The concrete identity/expiry protocol remains to be specified; see [ADR 0004](../decisions/0004-receipt-access-revocation-and-expiry.md).

Singleton registration guarantees one live activation (and so one background loop) across runners: the singleton's shard lock places it, a keeper wakes it on the lock holder, and a stale owner whose heartbeat stopped fails the generation fence on its next commit and so cannot commit after its successor. Cron is not tied to singleton residency: every `policy.cron` entry, on named, minted, and singleton actors alike, is one keyed outbox timer (`$cron:<expression>`) on its actor's shard. The relay rewrites it to the next scheduled time after the tick's receipt commits, and skips a tick older than `cronSkipIfOlderThan`. A singleton's ticks live in the default tenant and are written by every runner at startup with `ON CONFLICT DO NOTHING`, so one logical tick exists however many runners start ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)).

Timers are keyed outbox rows: `Intent.key` replaces an earlier pending timer with the same key, and `Intent.cancel` deletes it in the turn transaction. Durable polling remains the correctness path: every runner polls every second, with jitter. A commit that writes an already-due row wakes its own runner's relay, which may claim any row, so no runner-to-runner wake is sent; one through Cluster routing remains permitted if measurements need it. Missed wakeups must not lose work. Postgres `LISTEN/NOTIFY` is not used on the turn or wake path, because committing a `NOTIFY` can serialize the whole database. See [ADR 0006](../decisions/0006-scale-rules-placement-and-query-tiers.md).

Runners don't own buckets. Each relay pass scans every bucket's `(bucket, due_at)` range, so scan cost follows due work rather than stored actors, and claims only as many rows as it can start at once with `FOR UPDATE SKIP LOCKED`, on an index that separates intent and effect rows (`bucket, kind, due_at`). The claim moves each row's `due_at` to the end of a lease and increments `attempts`, so the row is not due for anyone else, and no lock or transaction stays open during delivery. Settling writes (delete, reschedule, route) name the claim they hold, so a relay whose lease has passed changes nothing. A row whose settle dies waits `max(claim lease, backoff(attempts))`, capped, before it is due again. Effect rows are claimed only up to the runner's free executor permits, and only for effects that runner has executors for. Executors run on a per-runner pool outside the pass and renew their lease while they run ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)).

# Dispatch and fencing

Scheduling bucket ranges are independent of compute shard ownership. The relay takes one combined due-work claim per range from the internal `ShardMap`, with the next range receiving only the remaining lane capacity, and rotates the starting range each pass. Capped-job discovery and holder liveness use the same ranges. The default map is one range covering all 256 buckets on the same database, with no extra statement or network flight. Ranges are static scan boundaries, not physical shard targets or a public database option ([ADR 0067](../decisions/0067-due-work-shard-ranges.md), amended by [ADR 0112](../decisions/0112-postgres-and-pglite-only.md)).

**Responsibility:** describe how work reaches one current actor generation.  
**Authority:** design.  
**Owner role:** runtime/reliability.
**Change policy:** a change that alters a contract guarantee requires an ADR.

Effect Cluster sharding routes a volatile command message to the current activation, but durable storage is the authority. The receipt committed inside the turn is the command's only durable admission record. External admission checks current authorization and command expiry; trusted recovery of already accepted work retains its durable authority. A command turn follows one order:

1. begin the transaction and set tenant scope;
2. `SELECT ... FOR UPDATE` the actor generation row;
3. resolve the command receipt under the [receipt contract](../contracts/04-receipts.md), replaying a matching outcome only through the appropriate caller-access or trusted-recovery path;
4. decode state through migrations, or reuse the activation's decoded copy from the same generation, and run the handler;
5. stage state, actor-table changes, events, intents, jobs, and the receipt;
6. commit once, then notify delivery.

Nothing is read before delivery. An external command's id form and window are checked in dispatch without a clock; its expiry is checked against the fenced read's database clock, before the receipt is released or the handler runs, on its first delivery. The expiry recheck before the reply uses the database clock read in the commit flight after the transaction ends. A served command therefore costs the turn's two round trips and no others ([ADR 0072](../decisions/0072-served-command-in-two-round-trips.md)).

The framework pipelines steps 1–3 into one admission round trip and steps 5–6 into one commit round trip; handler-issued `turn.rows` statements are the only other round trips. [ADR 0020](../decisions/0020-two-round-trip-turn-pipeline.md) sends each group as pipelined extended-protocol statements on a multiplexed connection leased to the turn; PGlite runs the same groups one statement at a time. The activation caches the generation it fenced and its last committed state; a warm admission skips the state read, and a fence that finds another generation discards the cache and fails the turn as a stale generation, so the restarted activation reloads before any handler runs. The Cluster entity hands each command to the activation's own mailbox as it arrives, and one worker per activation drains it, so an activation still has one turn transaction in flight. When more commands for the actor are already waiting, the worker runs up to 32 of them as a turn batch in delivery order: one admission round trip resolves every receipt under one fence, handlers run in sequence on the state the previous one left, and one commit round trip persists all outcomes. Consecutive calls of one commutative reducer in the batch merge into one turn of up to 1,024 calls: their inputs are combined and reduced once, and each call keeps its own receipt ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)). A batch stops before a command id it already holds, so a retry queued behind its original replays the original's receipt. Replies, broadcasts, and outbox visibility follow the commit. The worker keeps its turn session across consecutive batches: when a batch commits and more commands are already waiting, the next batch's `BEGIN` and admission statements go out in the same flight, behind the `COMMIT`, and its handlers run only after its own fence and receipt replies arrive ([ADR 0020](../decisions/0020-two-round-trip-turn-pipeline.md)). If the earlier batch fails to commit, the later one rolls back before any of its handlers runs. A lone command is never delayed to form a batch. A defect aborts the whole batch: after a deterministic defect its commands run again one per transaction on the same activation, and after a retryable one (a stale fence, a failed commit, a crash point) the activation restarts, Cluster redelivers the unanswered commands, and each command of the failed batch runs in a transaction of its own. See [ADR 0005](../decisions/0005-turn-latency-batching-and-regional-placement.md). See [ADR 0005](../decisions/0005-turn-latency-batching-and-regional-placement.md).

A stale generation, lock timeout, commit-unknown result, lost database connection, or command execution timeout is a retryable turn failure: the command entity ends the activation (closing its resources and workflow engine, and sealing its broadcasts), waits the activation's backoff (50 ms doubling to 5 s, reset by a settled turn), starts the next activation in place, and answers `ActorUnavailable`; the caller's handle retries the same command id, and the receipt makes the retry exactly-once. The runtime restarts the activation itself rather than dying so Cluster restarts the entity and re-sends the command: Cluster drops a re-sent command whose turn fails again before the restart completes, which left callers waiting out `deliveryTimeout` during a database failover. A caller's delivery timeout instead stops waiting and may return `ActorError` with reason `Timeout`; it does not cancel the admitted turn. An old writer may continue computing, but the generation fence prevents its commit. Deterministic defects roll back and follow the telemetry-only path described in [lifecycle](02-lifecycle.md).

Commands use volatile Cluster messages (`Persisted: false`), no Cluster `primaryKey`, and serialized entity handling ([ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md)). The framework owns deduplication through receipts and owns the only turn transaction; no reply is sent before commit.

Nothing staged by a handler is visible when the turn fails before commit. In particular, an intent is never delivered after a failed turn. A committed `actor_outbox` row is delivered after commit as a direct command and deduplicated by the receiver's receipt.

Client-minted command ids remain stable across retries. An authorized retry within the external retry horizon with different input produces `ActorError` with reason `CommandConflict`; the same input returns the stored receipt. Receipt access checks run without the handler. A caller mismatch or expired external identity must not fall through to a new handler execution, even after cleanup. The concrete identity/expiry protocol remains to be specified; see [ADR 0004](../decisions/0004-receipt-access-revocation-and-expiry.md).

Singleton registration guarantees one live activation (and so one background loop) across runners: the singleton's shard lock places it, a keeper wakes it on the lock holder, and a stale owner whose heartbeat stopped fails the generation fence on its next commit and so cannot commit after its successor. Schedules are not tied to singleton residency: every `schedules` entry, on named, minted, and singleton actors alike, is one keyed outbox timer on its actor's shard, keyed `$cron:<zone> <canonical expression>` or `$cron:@every <milliseconds>ms`, so one expression in two zones is two timers ([ADR 0042](../decisions/0042-cron-time-zones-intervals-and-daylight-saving.md)). The relay rewrites it to the next scheduled time after the tick's receipt commits, and skips a tick older than `policy.maxScheduleLag`. A singleton's ticks live in the default tenant and are written by every runner at startup with `ON CONFLICT DO NOTHING`, so one logical tick exists however many runners start ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)).

Timers are keyed outbox rows: `Intent.key` replaces an earlier pending timer with the same key, and `Intent.cancel` deletes it in the turn transaction. Durable polling remains the correctness path: every runner polls every second, with jitter. A commit that writes an already-due row wakes its own runner's relay, which may claim any row within its static scheduling ranges on the same database, so no runner-to-runner wake is sent; one through Cluster routing remains permitted if measurements need it. Missed wakeups must not lose work. Postgres `LISTEN/NOTIFY` is not used on the turn or wake path, because committing a `NOTIFY` can serialize the whole database. See [ADR 0006](../decisions/0006-scale-rules-placement-and-query-tiers.md).

Compute ownership does not determine data buckets. Each relay pass scans static bucket ranges through `(bucket, due_at)`, so scan cost follows due work rather than stored actors, and claims only as many rows as it can start at once with `FOR UPDATE SKIP LOCKED`, on an index that separates intent and job rows (`bucket, kind, due_at`). The claim moves each row's `due_at` to the end of a lease and increments `attempts`, so the row is not due for anyone else, and no lock or transaction stays open during delivery. Settling writes (delete, reschedule, route) name the claim they hold, so a relay whose lease has passed changes nothing. A row whose settle dies waits `max(claim lease, backoff(attempts))`, capped, before it is due again. Job rows are claimed only up to the runner's free executor permits, and only for jobs that runner has executors for. Jobs with a per-actor cap serialize claims on that actor's generation row; when both capped and uncapped jobs are due, passes alternate which kind takes the free permits first, and a probe that may have hidden other capped actors runs another pass at once. Executors run on a per-runner pool outside the pass and renew their lease while they run ([ADR 0066](../decisions/0066-authoritative-coordination.md), [ADR 0112](../decisions/0112-postgres-and-pglite-only.md)).

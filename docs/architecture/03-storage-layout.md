# Runtime storage layout

**Responsibility:** organize framework-private durable records.  
**Authority:** design.  
**Owner role:** database/runtime.
**Change policy:** a change that alters a contract guarantee requires an ADR.

Each deployment owns one Postgres database per region; a single-region deployment has one. A tenant's rows live in its home region's database ([ADR 0005](../decisions/0005-turn-latency-batching-and-regional-placement.md)). Every framework and actor-owned application table includes `tenant_id`; composite indexes include tenant scope, and deployments may enable row-level security as an additional isolation control. Actor identity and generation complete the ownership key where applicable.

Every framework and actor-owned row also carries `routing_key bigint`: an XXH3-64 hash of a versioned encoding of the actor type's placement key. The placement key defaults to the tenant; an actor type may instead be placed per actor. Placement with a parent actor is target design. Rows sharing a placement key share a shard, which makes group queries single-shard snapshots. The encoding never changes for existing rows. Update-heavy framework tables avoid indexes on columns that change every turn and set a fillfactor below 100 so updates stay heap-only. See [ADR 0006](../decisions/0006-scale-rules-placement-and-query-tiers.md).

Core records include generation fences, command receipts, `actor_state` keyed values, actor-owned tables, events, the outbox (intents, timers, workflow starts, and effect obligations), workflow executions, dead letters, blobs, and connections. Commands have no message table: they are direct, and their receipt is their durable record. Framework tables are protected from application mutation. Actor tables remain ordinary Drizzle tables automatically scoped by `turn.rows`; `group` permits read-only joins within the placement group. Every supported write adapter uses the same turn transaction and trusted ownership context.

`actor_state` stores one value per declared key as schema-encoded `bytea` compressed by codec version 1 (one plain zstd frame, no dictionary; see [contract 06](../contracts/06-storage-ownership.md)), and decodes through the state's ordered migration chain. Idle state may move to object storage, leaving `value` null and a `cold_ref`; the next turn rehydrates it in the admission round trip. Only dirty keys are written. Relational values belong in actor tables; binary data uses `actor_blobs` with actor-scoped `bytea` chunks and turn-bound writes. Table schema changes use drizzle-kit rather than state migrations.

`actor_events` stores one row per committed event, keyed by `(routing_key, tenant_id, actor_type, actor_id, sequence)`, with the event tag, the emitting command id, the emit time, and the schema-encoded event compressed with the state codec. `actor_generations.event_sequence` holds the last sequence issued. A turn that emits advances it on the generation row it has already locked, so events get gap-free sequences, and pruning `actor_events` can never lead to a sequence being reused. Retention may delete only a prefix of an actor's events; replay treats a missing successor of the cursor as a retention gap.

Every backend writes intents and timers to `actor_outbox` on the sending actor's shard within the turn, keyed by `(routing_key, intent_id)` with a `(bucket, due_at)` index and a unique pending `timer_key` per actor. Any runner's relay claims due rows with `FOR UPDATE SKIP LOCKED`, moving `due_at_ms` to the end of a lease, delivers them as direct commands with the intent id as the command id, and deletes a row after the receiver's receipt commits. `bucket` is the top eight bits of `routing_key`; every runner scans all 256 buckets, and no runner owns any. Migration `0011_relay` replaces the due index with `(bucket, kind, due_at_ms)` and adds `scheduled_at_ms`, the time a row first became due, which claims and backoff leave unchanged; relay lag and the cron skip window read it. A `policy.cron` entry is a row with `timer_key = '$cron:<expression>'`, rewritten in place to its next tick ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)). A performed effect is an `actor_outbox` row of kind `effect` targeting its own actor (migration `0008_effects`); the relay claims each attempt in the row, a per-runner executor pool runs the executor and renews the claim, and the settle turns the row into an intent to its `onSuccess` or `onDeadLetter` route, recording exhausted effects in `actor_dead_letters`. The same path covers same-shard, cross-shard, and cross-region delivery ([ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md)). On Neki, actor data is placed by a `range` shard index on `routing_key`; turn connections set `__neki.fanout='single'` so an accidental scatter fails. Migration `0013_inspection_views` adds the `durable` schema: read-only views over these tables whose columns are the public inspection contract, while the `actor_*` tables stay private ([ADR 0028](../decisions/0028-sql-inspection-views.md); [inspection views](../operations/inspection-views.md)). The views add no index and no write cost. Workflows use the framework's own `WorkflowEngine`: steps live in `actor_workflow_step` on the owner's shard, and durable clocks are outbox timers ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)).

`actor_blobs` holds one row per chunk, keyed by `(routing_key, tenant_id, actor_type, actor_id, blob, name, chunk)` with a composite foreign key to `actor_generations`. Chunk 0 heads every entry: `set` rewrites it and deletes the rest, `append` inserts the next chunk number without reading earlier bytes, and `compact` folds every later chunk into chunk 0 in one statement. `get` concatenates chunks in order with `string_agg`. The chunk rows are the entry's only metadata, so deleting them removes metadata and bytes together.

Neki requires generation-row locking and `SET __neki.tx_mode='single'` on the connection that runs `BEGIN`. These are conformance requirements, not established provider behavior. Cluster-owned SQL layouts must be verified from the pinned Effect implementation; application tenant-column conventions do not imply that upstream Cluster tables contain the same columns.

Migration `0010_retention` indexes `actor_receipts (actor_type, expires_at_ms)`, `actor_events (actor_type, emitted_at_ms)`, and `actor_outbox (intent_id)` for the per-minute retention sweep, which deletes receipts and event prefixes in batches of 1,000 rows ([ADR 0038](../decisions/0038-retention-cleanup-and-receipt-horizon.md)). Retention and restore must preserve dependency order between messages, receipts, events, workflow records, effects, and dead letters. See [data model](data-model.md), [transactions](transaction-catalog.md), and [retention](../operations/retention.md).

# Runtime storage layout

All per-actor and per-tenant framework primary keys and unique indexes include `routing_key`; the migrated Postgres catalog test covers all 18 such tables and the outbox's partial timer key. Deployment registries are separate, colocated deployment-wide metadata, not actor records. The complete registry exception list and audit result are recorded in [ADR 0067](../decisions/0067-due-work-shard-ranges.md); no key repair or data migration was needed.

**Responsibility:** organize framework-private durable records.  
**Authority:** design.  
**Owner role:** database/runtime.
**Change policy:** a change that alters a contract guarantee requires an ADR.

Each deployment owns one Postgres database per region; a single-region deployment has one. A tenant's rows live in its home region's database ([ADR 0005](../decisions/0005-turn-latency-batching-and-regional-placement.md)). Every framework and actor-owned application table includes `tenant_id`; composite indexes include tenant scope, and deployments may enable row-level security as an additional isolation control. Actor identity and generation complete the ownership key where applicable.

Every framework and actor-owned row also carries `routing_key bigint`: an XXH3-64 hash of a versioned encoding of the actor type's placement key. The placement key defaults to the tenant; an actor type may instead be placed per actor. Parent placement ([ADR 0033](../decisions/0033-parent-actor-placement.md), M4.11) gives a whole family its root's routing key, and `actor_placements` records its `parent_type` (`0022_parent_placement`). Rows sharing a placement key share a shard, which makes group queries single-shard snapshots. The encoding never changes for existing rows. Update-heavy framework tables avoid indexes on columns that change every turn and set a fillfactor below 100 so updates stay heap-only. See [ADR 0006](../decisions/0006-scale-rules-placement-and-query-tiers.md).

Core records include generation fences, command receipts, `actor_state` keyed values, actor-owned tables, events, the outbox (intents, timers, workflow starts, and job obligations), workflow executions, dead letters, blobs, and connections. Commands have no message table: they are direct, and their receipt is their durable record. Framework tables are protected from application mutation. Actor tables remain ordinary Drizzle tables automatically scoped by `turn.rows`; `group` permits read-only joins within the placement group. Every supported write adapter uses the same turn transaction and trusted ownership context.

`actor_state` stores one value per declared key as schema-encoded `bytea` compressed by codec version 1 (one plain zstd frame, no dictionary; see [contract 06](../contracts/06-storage-ownership.md)), and decodes through the state's ordered migration chain. Idle state may move to object storage, leaving `value` null and a `cold_ref`; the next turn rehydrates it in the admission round trip. Only dirty keys are written. Relational values belong in actor tables; binary data uses `actor_blobs` with actor-scoped `bytea` chunks and turn-bound writes. Table schema changes use drizzle-kit rather than state migrations.

`actor_events` stores one row per committed event, keyed by `(routing_key, tenant_id, actor_type, actor_id, sequence)`, with the event tag, the emitting command id, the emit time, and the schema-encoded event compressed with the state codec. `actor_generations.event_sequence` holds the last sequence issued. A turn that emits advances it on the generation row it has already locked, so events get gap-free sequences, and pruning `actor_events` can never lead to a sequence being reused. Retention may delete only a prefix of an actor's events; replay treats a missing successor of the cursor as a retention gap.

Every backend writes intents and timers to `actor_outbox` on the sending actor's shard within the turn, keyed by `(routing_key, intent_id)` with a `(bucket, due_at)` index and a unique pending `timer_key` per actor. Any runner's relay claims due rows with `FOR UPDATE SKIP LOCKED`, moving `due_at_ms` to the end of a lease, delivers them as direct commands with the intent id as the command id, and deletes a row after the receiver's receipt commits. `bucket` is the top eight bits of `routing_key`; each runner scans its data shard map's ranges, with one range covering all 256 buckets on an ordinary database. Migration `0011_relay` replaces the due index with `(bucket, kind, due_at_ms)` and adds `scheduled_at_ms`, the time a row first became due, which claims and backoff leave unchanged; relay lag and the schedule skip window read it. A `schedules` entry is a row with `timer_key = '$cron:<zone> <canonical expression>'`, or `'$cron:@every <milliseconds>ms'` for an interval ([ADR 0042](../decisions/0042-cron-time-zones-intervals-and-daylight-saving.md)), rewritten in place to its next tick ([ADR 0021](../decisions/0021-multi-runner-relay-singleton-and-cron.md)). An enqueued job is an `actor_outbox` row of kind `job` targeting its own actor (migration `0008_effects`, renamed by `0026_jobs`); the relay claims each attempt in the row, a per-runner executor pool runs the executor and renews the claim, and the settle turns the row into an intent to its `onSuccess` or `onDeadLetter` route, recording exhausted jobs in `actor_dead_letters`. The same path covers same-shard, cross-shard, and cross-region delivery ([ADR 0011](../decisions/0011-direct-commands-outbox-and-performance.md)). On Neki, actor data is placed by a `range` shard index on `routing_key`; turn connections set `__neki.fanout='single'` so an accidental scatter fails. Migration `0013_inspection_views` adds the `durable` schema: read-only views over these tables whose columns are the public inspection contract, while the `actor_*` tables stay private ([ADR 0028](../decisions/0028-sql-inspection-views.md); [inspection views](../operations/inspection-views.md)). The views add no index and no write cost. Workflows use the framework's own `WorkflowEngine`: steps live in `actor_workflow_step` on the owner's shard, and durable clocks are outbox timers ([ADR 0012](../decisions/0012-workflows-internals-effects-defects-merging-regions.md)).

`actor_blobs` holds one row per chunk, keyed by `(routing_key, tenant_id, actor_type, actor_id, blob, name, chunk)` with a composite foreign key to `actor_generations`. Chunk 0 heads every entry: `set` rewrites it and deletes the rest, `append` inserts the next chunk number without reading earlier bytes, and `compact` folds every later chunk into chunk 0 in one statement, and `delete` removes every chunk of the entry. The `set` and `append` statements read the actor's byte total and its chunk-0 count, its entry count, in the same aggregate to enforce `policy.maxBlobBytes` and `policy.maxBlobEntries`. `get` concatenates chunks in order with `string_agg`. The chunk rows are the entry's only metadata, so deleting them removes metadata and bytes together.

Neki requires generation-row locking and `SET __neki.tx_mode='single'` on the connection that runs `BEGIN`. These are conformance requirements, not established provider behavior. Cluster-owned SQL layouts must be verified from the pinned Effect implementation; application tenant-column conventions do not imply that upstream Cluster tables contain the same columns.

Migration `0010_retention` indexes `actor_receipts (actor_type, expires_at_ms)`, `actor_events (actor_type, emitted_at_ms)`, and `actor_outbox (intent_id)` for the per-minute retention sweep, which deletes receipts and event prefixes in batches of 1,000 rows ([ADR 0038](../decisions/0038-retention-cleanup-and-receipt-horizon.md)). Retention and restore must preserve dependency order between messages, receipts, events, workflow records, jobs, and dead letters. See [data model](data-model.md), [transactions](transaction-catalog.md), and [retention](../operations/retention.md).

Migration `0020_content_blobs` ([ADR 0034](../decisions/0034-tenant-scoped-content-addressed-blobs.md), M4.13) stores shared content on the tenant's routing key: `tenant_contents` (`hash`, `size`, `granted_until_ms`, keyed by `(routing_key, tenant_id, hash)` and indexed by `(routing_key, tenant_id, granted_until_ms, hash)` for the sweep) and `tenant_content_chunks` (1 MiB `bytea` chunks from chunk 0; an empty content has one empty chunk). References live on the actor's shard in `actor_content_refs`, keyed by `(routing_key, tenant_id, actor_type, actor_id, blob, name)` with a composite foreign key to `actor_generations` and a `(tenant_id, hash)` index for the sweep's scan; nothing points from a reference or a chunk to a content row, and nothing counts references. `tenant_content_sweeps` lists every tenant that uploaded with its last sweep, `actor_content_types` records the longest `executionTimeout` of each actor type that declares content, and `actor_deployment.deployment_id` is the random id grants are bound to. The four tables with a `tenant_id` carry the `durable_tenant` row-level security policy ([ADR 0051](../decisions/0051-row-level-security.md)): a query reads references and chunks as the tenant role, while uploads, grants, and the sweep keep the exempt connecting role.

`0021_payload_versions` ([ADR 0032](../decisions/0032-event-and-effect-payload-evolution.md)) adds `payload_version` to `actor_events`, `actor_outbox`, and `actor_dead_letters`; `actor_payload_versions`, one row per `(actor_type, kind, tag, version)` some runtime has written, with `superseded_at_ms` and `cleared_at_ms`; and `actor_payload_writers`, each runtime's heartbeat per version it writes, with its `window_ms`. The migration refuses a database that already holds events, outbox rows, or dead letters, since their versions were never recorded; such a development database is recreated. The three `payload_version` columns sit on tables `0018_rls` already binds to `durable_tenant`. The two new tables are deployment-wide, keyed by actor type and runtime with no `tenant_id`, so they carry no policy; the runtime reads and writes them outside tenant-scoped transactions, as the connecting role.

The cold tier's migration ([ADR 0036](../decisions/0036-cold-tier.md)) is numbered when L.2 is scheduled.

# Cloud infrastructure verification

The infrastructure slice declares Fly apps and machines, certificates, Vercel DNS records, a Neki control-plane database, Axiom ingest tokens, Stripe webhook endpoints and the GitHub environments the deploy workflow runs in ([ADR 0089](../decisions/0089-fly-infrastructure-and-environments.md)). Its local evidence is documented here and in [cloud deployments](cloud-deployments.md); it does not establish real TLS, Fly proxy behavior, certificate issuance, Neki SQL or Stripe delivery.

**Responsibility:** distinguish local infrastructure evidence from provider deployment support.
**Authority:** evidence requirements.
**Owner role:** platform reliability.

The `infra` workspace is checked by repository typecheck, lint, structure, formatting and its unit tests. `bun run --cwd infra plan:offline` compiles the service stack for `prod`, `preview` and `pr-1` with registered providers, in-memory state and placeholder inputs. It does not run Alchemy's planner, query live resources or apply anything. `bun run --cwd infra test:integration` runs the logical-database provider against the Postgres in `TEST_DATABASE_URL`.

Local evidence rejects, for every stage, a Fly app outside the stage's organization (a preview in `rika-labs-prod`, `prod` in `rika-labs-dev`), a stage other than `prod`, `preview` and `pr-<n>` (including `dev` and `staging`), a Stripe key of the wrong mode, destroying `prod` or `preview` from CI, a pull request preview that creates a Neki cluster or Axiom dataset or monitor of its own, a `preview` stage that declares anything but the shared cluster and datasets, a shared cluster with replicas or more than one shard, machines of a preview that stay running or machines of `prod` that stop, a GitHub environment that gives production a reviewer or lets it deploy from any branch, a credential shared between the `preview` and `production` environments other than the Vercel token, a customer wildcard, hostname or DNS record in the wrong zone, a preview that declares a Fly certificate or Vercel record for a platform hostname (or `prod` that omits one), a preview whose API does not issue cross-site cookies or `prod` whose does, a session cookie without `SameSite=None; Secure; Partitioned` under `AUTH_COOKIE_SAME_SITE=none` or one that is not `SameSite=Lax` by default, an `AUTH_COOKIE_SAME_SITE` other than `lax` or `none`, a secret in a machine's plain environment, a secret reaching a service that does not read it, a Resend domain or a mail record the stack must not manage, and a pull-request comment on a pull request that is not the stage's. The Vercel provider is run against a recorded API that stores exactly what it is sent, so a create without the record's name and value, a duplicate after a lost state write, a record past the fiftieth page of a zone, an overwrite of a record it did not make and a swallowed denied delete all fail a test. The Neki role provider is run against a recorded PlanetScale API, so a role created before a lost state write must be adopted under a reset password instead of duplicated, and one of the same name with other privileges refused. The logical-database provider is run against real Postgres, including adoption of a database a lost run created, the propagation barrier after `CREATE DATABASE` on a stand-in, a drop while a connection is open and names that are not plain lowercase identifiers. The generated edge key is checked to be a consistent Ed25519 pair in the JWK form the edge reads. Bucket tests for the Neki topology must still cover the extreme signed values, zero, negative-one, and both sides of every shard boundary; those algebraic checks do not establish PlanetScale's interpretation of the topology or Neki SQL semantics.

Before claiming deployed support, run authorized tests with real credentials for the Fly organizations, and keep the `preview` environment's credentials away from production:

1. Deploy the `preview` stage from empty state, then a pull request preview, after buying `akter.run` in Vercel. Inspect the apps in `rika-labs-dev`, the amd64 images pulled from `registry.fly.io`, healthy machines on `/ready` and `/health`, and the DNS records in both zones: a preview has records only for its customer wildcard in `akter.run`, and `akter.dev` gains none. Repeat the deploy and confirm nothing changes, then delete a record by hand and confirm the next deploy restores it.
2. Sign in to a preview's console in Chrome and Firefox and confirm the session cookie is stored partitioned and sent on the console's requests to the API; Safari is expected to fail. Verify TLS for every hostname and for a customer hostname under the wildcard, through the edge. Confirm the edge reads the client address from `Fly-Client-IP` only because `EDGE_TRUST_FLY_PROXY` is set, and that a WebSocket and a server-sent stream survive the Fly proxy.
3. Send email from each stage's `EMAIL_FROM` through Resend. Confirm OTLP delivery from the API and the edge into the shared datasets with the `deployment.environment` attribute, that the error monitor alerts for `prod` and ignores a preview, that deploying `prod` and `preview` in either order adopts the same two datasets, and that the organization stays within three datasets and three monitors.
4. Create the shared Neki database in the `preview` stage and verify the topology, authoritative group and routers. Create a preview and verify that `CREATE DATABASE` and `DROP DATABASE` work through a Neki router, that the API creates its tables in the preview's database, and what a preview's role can read in another preview's database (roles are cluster-wide). If Neki refuses the statements, record the schema-per-preview fallback in the ADR and implement it. Retry after interruption and out-of-band deletion; reconciliation must converge without losing existing credentials, and a role adopted after a lost state write must receive a working password from PlanetScale's role reset. Create the production database and verify its replicas, routers and the service role's connections.
5. Exercise the preview lifecycle: open a pull request, confirm the deploy and one comment that updates on a push, wake a stopped preview with a request, close the pull request, and confirm the Fly apps, Neki role, logical database, Stripe endpoint and Axiom token are gone. Close a pull request while its deploy runs, and run the nightly job against a stage whose pull request is closed. Open more previews than Stripe allows webhook endpoints and confirm the failure is clear.
6. Merge a change to `main` and confirm `prod` deploys once `Verify` passes with no approval step, that a failing `Verify` deploys nothing, that two pushes in quick succession queue their deploys instead of overlapping, that a change under `infra/` also deploys `preview`, that a manual run from another branch is refused by the `production` environment, and that `guard destroy prod` and `guard destroy preview` fail in CI. Rotate a Fly secret and confirm the machines restart with the new value. Check production retention (the Neki database stays when the stack is destroyed in a rehearsal) without destructive tests on real customer data.
7. Run the existing Neki SQL conformance cases, including fencing, rollback, denied fanout, recovery and outbox ranges, and exercise authorized topology changes through Neki's provider workflow before claiming resharding support. [ADR 0096](../decisions/0096-neki-multi-shard-evidence.md) ran Neki's `Reshard` on a temporary three-shard cluster under live writes; it has not run on `akter-production`.

None of those live-provider gates are established by local checks or by an Alchemy plan. Existing Neki support remains unverified until its provider-specific evidence passes.

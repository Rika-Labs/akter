# Invariants

**Responsibility:** connect contracts to named tests.  
**Authority:** verification.  
**Owner role:** verification/reliability.
**Change policy:** a change requires the conformance suite to be updated in the same change.

Each invariant MUST have a named executable case in `describeConformance` or an integration suite. PGlite covers fast transactional cases; a real Postgres server covers contention; multi-runner and served HTTP harnesses cover compute routing and edge attribution. These are the only database backends ([ADR 0112](../decisions/0112-postgres-and-pglite-only.md)).

| M3 | A direct command is durable only once its receipt commits. | Runner loss before commit leaves no receipt or consequence; the caller's retry with the same id executes once. |
| B1 | Pipelined batches expose nothing before their own commit, and run no handler before their own fence. | Batch N+1's admission may share a flight with batch N's commit, but none of N+1's handlers runs until N+1's fence and receipt replies arrive; N+1's replies, broadcasts, and outbox rows stay hidden until N+1 commits; a failed batch N rolls back N+1's transaction before any N+1 handler runs. |
| C2 | Batch reducer folding equals sequential application. | Generated states and input lists satisfy the ordered fold law: reducing one at a time and reducing their in-order combination once both succeed with a schema-valid state and are equal (`checkBatchLaw`; an always-failing reducer is rejected); a merged turn of up to 1,024 waiting calls, from any runner, commits one receipt per original command id and replays each id alone. |
| C3 | Optimistic client state converges to committed state. | Browser handle rolls back failed reducers and matches committed state after every receipt. |
| Q1 | Queries observe the caller's own writes. | Replica or edge answer waits for or falls through past the handle's last-seen commit version. |
| C4 | Live output is never silently lost. | Connection buffer overflow, a broadcast sequence gap, an owner killed at every point between commit and flush (mid-turn, mid-batch, before its first message to a holder, racing a handler broadcast; randomized), an unreachable holder, a snapshot/live race in `open`, a stalled stream, and an ended activation each deliver everything or give the client a cursor from which event replay recovers every event-backed frame, and tell it to reload state for the rest. |
| C5 | Executor progress is never authoritative ([ADR 0030](../decisions/0030-executor-progress-frames.md); delivery M2.18). | Dropping every progress message leaves receipts, state, events, outbox rows, routes, and outcomes unchanged; no progress frame follows its effect's route or cancellation, or arrives more than 5 seconds after a route-less settle; a loss before a later delivered frame of the attempt is a visible `seq` gap; progress never closes a session. |
| X1 | Simulation failures reproduce from their seed. | The private `@akter/conformance` workspace's `simulate` and `simulateCluster` rerun a failing seed to the same fault schedule and outcome; the cluster's schedule includes each command's entry runner, crash point, and whether a commit landed before a connection loss. |
External replay and conflict cases assume an unexpired command identity and current receipt-access authorization. Rejected access or expiry must not invoke a handler under ordinary admission. Under [ADR 0115](../decisions/0115-warm-actor-fast-path.md), a warm speculative evaluation may be discarded before a receipt or expired fence-wait is discovered, but may commit no consequence or release any result. Known duplicates and uncertain redeliveries must skip speculation. Trusted internal recovery follows the retained obligation rather than rechecking the originating caller as a new external admission.

Warm fast-path cases in `conformance/pipeline.ts` exercise A1/T1/R1–R3/Q1 with real Postgres: one guarded commit flight; stale-fence rollback and reload; duplicate/conflict replay; lost COMMIT reply recovery through the same receipt; and versioned reads while a handler is staged, after declared failure, after a defect and after a SQL-aborted commit. The protocol relay counts physical flights, not calls to an SQL mock. Cached reads must never publish an unconfirmed state/version or combine cached state with live event rows; minimum-version misses must use the database path.

The `owner cache reads:` cases additionally require a fresh primary tuple check in one flight, refuse cached provenance after an ownership change or a same-generation state-only write, and exclude a foreign writer's uncommitted state. The multi-runner owner-cache case independently verifies asymmetric read-your-writes through another entry runner and after owner shutdown/restart. These strengthen the historical zero-flight read protocol under [ADR 0118](../decisions/0118-owner-cache-read-fencing.md).

M1, M2, and M3 for relay-delivered commands have single-runner, same-shard evidence from M1.6 on PGlite and a Postgres database, with SIGKILL cases on a Postgres database; the case names are in the conformance suites. Cross-region delivery and provider-specific cross-shard delivery remain unverified; multi-runner evidence is scoped by the [support matrix](../operations/support-matrix.md).

A1 has evidence with two real runners from M2.1 on a Postgres database: a stale activation fails its fence after another runner commits, and events stay gap-free while two runners race for one actor. M3 has evidence across a runner kill: a turn killed before COMMIT leaves no receipt or consequence and the caller's retry with the same id commits once on the new owner, and a turn killed after COMMIT but before its reply is replayed from its receipt on the new owner rather than run again. The case names are in the conformance suites.

W1 and W2 are specified further by [ADR 0022](../decisions/0022-workflow-engine-storage-and-version-markers.md): a wait sees the owner's events after its execution's cursor, including events of the turn that started it, and the cases that prove W1, W2 and H2 for workflows are named in the conformance suites.

P1 has single-runner evidence from M1.7 on PGlite and a Postgres database: a lost result reruns the executor under the same effect id, and a dead letter reports `ambiguous` unless the last attempt failed with a typed error; the case names are in the conformance suites. Provider-specific reconciliation remains per adapter.

The mapping from these invariants to normative guarantees is in [runtime contracts](../contracts/README.md); crash expectations are in the [failure matrix](02-failure-matrix.md).

A5's cross-routing-key creation checks are in `conformance/mint.ts`: the relay creates an actor-placed child of a tenant-placed parent, forged provenance is refused without a receipt, and interruption before source outbox deletion replays one child receipt. `conformance/single-shard.ts` additionally records that child's first delivery and refuses any parent-key parameter, outbox read, or placement-registry access. The pair uses opposite routing-key halves on the same Postgres/PGlite database; it establishes row scope and provenance, not physical data-shard separation.

R5 with automatic pruning (boundary, prune/retry race, crash inside a sweep, and restart) is executed in `conformance/retention.ts` and `crash/retention.test.ts`; its restore and version-skew cases are executed in `conformance/restore.ts` (M4.4). D1 is executed there only under the [restore procedure](../operations/04-backup-restore.md)'s precondition that every runner is stopped before the restore; a runner that survives a restore is not detected, and D1 is unverified for it.

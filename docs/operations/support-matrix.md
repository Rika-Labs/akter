# Backend support matrix

**Responsibility:** show real capability differences by backend.  
**Authority:** operational evidence.  
**Owner role:** platform/verification.
**Change policy:** a change requires operator review when a procedure or limit changes.

The only framework backends are **Postgres** and **PGlite**. Neki support, options, fixtures and CI selections have been removed by [ADR 0112](../decisions/0112-postgres-and-pglite-only.md); historical provider records are not a current support claim.

## Supported Postgres server versions

The supported server version range at launch is **Postgres server 18.6**. Continuous integration runs the conformance, integration, crash-drill, and property suites against the `postgres:18.6` image; other server versions are unverified and are not a support claim. PGlite is a separate embedded backend with the limits described below.

## Runtime portability

The framework supports Bun 1.4.2+ and Node 24+. Both run the core Postgres conformance suite, including served HTTP, WebSocket, SSE and Promise-client cases on the selected Effect HTTP server. `bun run test:node` launches Node workers and a clean installed-tarball PGlite quickstart restart; `check:ci` also runs the Bun quickstart. Native xxHash3 placement keys and zstd state frames are interoperable, so switching runtimes requires no database migration. The Node kernel-lock and fleet-maintainer subprocess cases are exercised, but separate actor crash drills and provider deployments are not established by core conformance. File-backed PGlite remains Linux/macOS on a local filesystem, one process per directory, with exclusive kernel locking; Windows, network filesystems and power-loss durability remain unsupported or unverified. Existing throughput and capacity measurements are not Node performance claims; V8's conformance object count excludes null-prototype objects, while its byte bound still measures retained JavaScript heap.

**Cross-database coordination:** real Postgres evidence uses two data databases and one authority in `runtime/database/coordination.test.ts`, covering retention/workflow mutual exclusion, interruption, authority-session loss with a local data fence, Cluster ownership and release in both lock modes, singleton lease reads, fleet lock placement/release, and capped-job generation locking. PGlite remains a single-process, single-connection backend ([ADR 0066](../decisions/0066-authoritative-coordination.md)).

Static scheduling ranges are covered by real Postgres range-boundary, `SKIP LOCKED`, failed-settle, public-API intent/timer/job/cron and holder-liveness tests in `runtime/database/shards.test.ts`. The default claim remains one statement and one network flight. `runtime/database/migrations.test.ts` checks all per-actor and per-tenant primary and unique keys from the migrated catalog, including partial indexes. Authority placement keeps the existing routing-key encoding and transactional conversion, tested in `runtime/storage/placements.test.ts`; it makes no physical-shard guarantee.

Support means the shared conformance suite in the unpublished `@akter/conformance` workspace (`tooling/conformance`) passes and deployment-specific gates are demonstrated. App developers use `@rikalabs/akter/testing`; framework conformance and cluster/simulation helpers are not published. A “verified” cell is supported only within its stated backend, runner count and process model. `Verify` runs on every pull request and `main` (`bun run check:ci`: PGlite, real Postgres with a streaming replica, and Docker drills); deterministic simulation and random-seed properties also run nightly. “Verified, single runner” means one runtime process, not a provider deployment. Every other cell says “unverified” or “unsupported” with its reason. Evidence paths below are relative to `tooling/conformance/src` unless prefixed with `runtime/` or another workspace.

**Startup migrations:** Postgres retains transactional rollback, tested through six concurrent fresh `Actors.layer` builds and six independent startup processes with separate data and coordination databases. Migration `0033_joined_inspection` is tested for dependent-view refusal, rollback, retry and restart without actor-row loss. PGlite's transactional startup is unchanged. See [removal verification](../verification/neki-removal.md) and [alpha upgrade notes](alpha-upgrades.md); previous alpha runners must be stopped before the `_v2` views are retired.

`turn.mint` carries committed creating-intent provenance in the relay request rather than reading the parent's outbox during the child's first turn ([ADR 0048 amendment](../decisions/0048-mint-progress-and-inspection-record-corrections.md#amendment-child-local-creating-intent-proof-485-2026-10-03)). Cross-routing-key creation, forgery refusal, and crash/replay evidence live in `conformance/mint.ts`; `conformance/single-shard.ts` records only child-key statements during that delivery.

## Evidence limits

Topology is a separate gate. A hosted multi-replica deployment needs a reachable private advertise address for every runner and provider-specific reachability and failover evidence. A service-per-runner alternative needs equivalent evidence; `Topology.k8s` was removed from the agreed public API. Public `Runner.socket` has three-process Bun evidence against a Postgres database over loopback for crash, clean drain, singleton failover and cron replay. Separate-host networking and hosted topologies still need their own evidence. Plaintext trusts the deployment's isolated network; `Runner.mtls` supplies TLS 1.3, deployment identity and peer authentication. Other features retain their stated process scope.

PGlite is a development/test backend except for the embedded-production row: [ADR 0035](../decisions/0035-pglite-embedded-production-backend.md) supports one process per locked `dataDir`, process-crash recovery (not power loss), stopped-copy backup, and Linux/macOS local filesystems. No contention, replica or multi-runner support; other PGlite cells are not production claims.

Runner capacity is measured on one runner, not certified: about 20 KiB heap per resident activation, or about 200 MiB at the 10,000 default, plus database connections. Size pools across runners as in [deployment](01-deployment.md#postgres-connections-across-runners). In-process benchmarks are not multi-process support. A connection pooler is unverified.

Served HTTP is verified behind Effect Bun/Node servers over loopback HTTP/1.1 only. Cleartext `node:http2` is benchmarked, not conformance-covered; TLS HTTP/2, proxies, load balancers, TLS terminators and providers are unverified. WebSocket settings belong to the application's HTTP server layer. SSE is read over `fetch`, not browser `EventSource`. The Promise client uses Bun/Node `fetch` for commands, optimistic rollback, feeds and connections. Removed Chromium fixtures do not establish current browser support. `@akter/react` and the Python client remain repo-only at launch.

An unverified cell remains gated. Wire compatibility is not evidence of locking, pooling, transaction or restore equivalence.

Command admission is bounded per runner ([ADR 0077](../decisions/0077-admission-control.md)): 64 executing commands, 64 FIFO waiters for up to 100 ms, 64 HTTP command handlers, 1,024 commands for an actor without a declared mailbox capacity, and 64 excess checkouts per Postgres pool including coordination. Excess work is retryable `ActorUnavailable`, served as `503` with `retry-after`. Real Postgres evidence covers saturation, cancellation, deadlines, refusal without receipts and same-id retry. This does not bound OS socket backlogs or proxy queues; provider overload and multi-host latency remain unverified.

# Served clock discontinuity evidence

> Historical 0.1 verification, retained as of 2026-10-12. Recorded observations below are unchanged; they do not establish support for the 0.2 bucket engine. See [current verification](README.md).

`packages/akter/src/serve/clock.test.ts` rejects retaining a pre-suspend offset after a 304-second backward or 155-second forward monotonic discontinuity. The expected clock comes from an independent database-time fixture, not from the cached offset. It also rejects preferring a faster obsolete sample, resampling once per concurrent request, adding a database read because a sample is merely old, and serving stale time when the required database refresh fails. These focused clock-algebra tests mock the clocks and sampler, not a storage-admission claim.

The HTTP conformance case `resamples served time after monotonic discontinuities before SDK-minted identities reach unchanged database admission` serves real `/protocol`, `/command-ids` and actor command endpoints over loopback on both Postgres and PGlite. It shifts only the served process's monotonic clock, compares body/header timestamps with independently read database time within 500 milliseconds, and requires SDK-local and server-minted IDs to execute through unchanged identity admission. Retaining the original offset fails the timestamp comparison; accepting future identities would not repair it.

Existing HTTP conformance keeps malformed, future, wrong-window and expired identity rejection, handler/receipt counts, and same-ID replay. No expiry grace, weaker admission predicate, production request or provider mutation is required for this evidence. Provider-specific suspend/network recovery remains separate from served clock correctness.

`omits a failed clock refresh header without replacing a committed reply, its request id or browser headers` injects a sampler failure while command execution and receipt storage remain real. It requires HTTP 200 with the committed result, one receipt, the same request id and allowed browser origin, and no `durable-now`. The same unavailable sampler must make `/protocol` return 503 without a stale time header. This rejects replacing a successful handler outcome with a clock error.

Fly's [provider description](https://community.fly.io/t/better-paradox-prevention-suspend-resume-clocks/25959), accessed 2026-10-12, permits a request before guest wall-clock correction. For the observed resume at 00:36:48.823Z, the first retained application timestamp was 00:36:59.002Z versus provider ingest at 00:36:59.003Z: correct within one millisecond by 10.179 seconds after resume, with the earlier correction latency unknown. Successful edge readiness probing finished about 00:37:04.026Z and therefore covered that event's residual window before forwarding `/protocol`. This is not proof that every faster resume waits for clock correction. When both local clocks remain paused together, the divergence detector has no independent host-time reference and may not yet detect suspension.

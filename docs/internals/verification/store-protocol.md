# Store protocol evidence

**Responsibility:** bind the 0.2 `Store` service's bucket-protocol claims to executed scenarios.  
**Authority:** verification evidence.  
**Owner role:** runtime/storage reliability.  
**Change policy:** a new store transition or bucket requirement needs a conformance scenario that names the wrong implementation it rejects.

`Store` is exported from `@rikalabs/akter/server` as a namespace: the layers `Store.s3`, `Store.fileSystem` and `Store.memory`, the probe `Store.check`, the probes that open no store (`Store.checkS3`, `Store.checkFileSystem`) and the service `Store.Store`. Its source is `packages/akter/src/store/`, and its normative target is the [storage contract](../contracts/06-storage.md) and [ADR 0136](../decisions/0136-stores-the-bucket-is-the-store.md). One bucket holds each shard's log segments (`s/<shard>/log/<offset>`), checkpoint manifests (`s/<shard>/cp/<inverted offset>`), content-addressed pages (`pages/<sha256>`), the identity record `meta/store` and lease objects under `cluster/` and `gc/`; the layout is the storage contract's. A segment is created once at `head + 1`, and that create-once write is the fence. No clock sits in the commit path. The adapters are `Store.s3` (S3-compatible, through `@aws-sdk/client-s3`), `Store.fileSystem` (one local directory) and `Store.memory`. The 0.1 runtime does not use the store yet, so nothing here is a claim about 0.1 behavior.

## Suite and backends

[`conformance/store.ts`](../../../tooling/conformance/src/conformance/store.ts) runs the same seventeen scenarios against every backend (sixteen in E2a, plus E2b's freshness scenario). The owners in a scenario are separate store instances, each with its own client and fault plan, over one shared location. The test clock drives `validFor` (10 s) and `trimAfter` (10 min), so the timing rules are tested at their boundaries, not by sleeping.

| Backend         | Test file                                             | Bun                                 | Node                                |
| --------------- | ----------------------------------------------------- | ----------------------------------- | ----------------------------------- |
| Process memory  | `packages/akter/src/store/memory.test.ts`             | `packages/akter` `test`             | `test:node:units`                   |
| Local directory | `packages/akter/src/store/file-system.test.ts`        | `packages/akter` `test`             | `test:node:units`                   |
| S3-compatible   | `packages/akter/src/store/s3.test.ts` (`TEST_S3_URL`) | `packages/akter` `test:integration` | `packages/akter` `test:integration` |

`packages/akter` `test` leaves `s3.test.ts` out; `test:integration` runs it through `packages/akter/vitest.integration.config.ts` on Bun and then on Node. CI's `framework-integration` shard starts MinIO RELEASE.2026-09-22 (`cgr.dev/chainguard/minio`, pinned by digest) with `docker run` and sets `TEST_S3_URL`. Locally, `docker compose -f packages/akter/compose.yaml up --wait` starts the same server, and the URL is in that file. Each S3 scenario writes under a fresh random key prefix in one bucket.

Faults come from `Faults.plan()`, which wraps a bucket between the store and its adapter. `Delay` and `Hold` postpone a matching call. `Unavailable` fails it before it reaches the bucket. `LoseResponse` performs it and then fails, the way a write lands but its response is lost. Faults model what a client can observe; they do not change how the provider behaves.

| Scenario                                                                                                                                              | Wrong implementation it rejects                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| A stale owner's append fails after another owner opens; each segment carries its writer's build                                                       | A fence kept only in process memory, or a plain `PUT` for segments                                            |
| Six concurrent opens get distinct epochs; only the newest lease appends                                                                               | An open without create-once, which lets two owners share an epoch                                             |
| A lost-response append is recognized as the owner's own and stored once                                                                               | Retrying at the next offset, or failing a write that committed                                                |
| A lost-response append that another owner overtook fails `StaleEpoch`                                                                                 | Treating every `412` after a retry as the owner's own write                                                   |
| A failed manifest write leaves the previous checkpoint authoritative                                                                                  | Recovering from pages that no durable manifest names                                                          |
| Recovery returns every acknowledged batch once, in order, from the newest checkpoint                                                                  | Reading the oldest checkpoint, duplicating lost-response batches, reordering                                  |
| Trim deletes only segments covered by a checkpoint known for `trimAfter`                                                                              | Trimming segments no checkpoint covers, or trimming as soon as a checkpoint exists                            |
| An owner idle past `validFor` whose next key was trimmed fails before it writes                                                                       | Appending without re-checking after `validFor`, which would recreate a trimmed key                            |
| An owner re-checks once after `validFor` and not within it                                                                                            | Never re-checking, or checking on every append                                                                |
| `fresh` expires at Store's `validFor`, is renewed by a successful check or append, makes no bucket call, and stays false after a fence                | A second engine validity window, freshness that ignores elapsed time, or freshness surviving a detected fence |
| Pages are stored once per content hash; an absent or altered page is the `PageCorrupt` defect                                                         | Keys not derived from content, or loads that trust stored bytes                                               |
| A `412` or `429` on a page write succeeds only when the key holds an object of the page's length                                                      | Trusting every refused or throttled write, or trusting a key that holds other bytes                           |
| Concurrent creators write one `meta/store` with its creation time and retention; a runner configured with another shard count or retention is refused | A last-writer-wins identity record, or adopting the stored shard count                                        |
| Open skips newer checkpoints that do not decode or name a missing page, reports them, and recovers from the previous checkpoint and the longer tail   | Trusting the newest manifest, or opening from empty state                                                     |
| Open refuses a shard when the log after the intact checkpoint no longer reaches a skipped one                                                         | Reopening at an offset whose entries were trimmed                                                             |
| Runner storage splits shards, moves a dead runner's shards and drops a paused runner's                                                                | Locks taken while their owner's heartbeat still moves                                                         |
| The backend passes `Store.check`, which removes everything it wrote                                                                                   | A backend whose conditional writes, compare-and-swap, listings or last-modified times do not behave like S3's |

Errors follow the [error model](../contracts/error-model.md): bucket calls, pages, leases and `meta/store` fail with `StorageUnavailable`; the log operations (`open`, `append`, `read`, `checkpoint`, `trim`, `verify`) with `LogUnavailable` or `StaleEpoch`; an undecodable segment, manifest or `meta/store` with `CorruptSegment`; a configuration that disagrees with `meta/store` with `StoreMismatch`. A page that is absent or does not hash to its key is the `PageCorrupt` defect. The store raises no `PageMiss`: in the [commands contract](../contracts/02-actions.md) that is the engine's signal that a command touched a page not yet in memory, which it loads and reruns, and a page missing from the bucket would make that rerun loop forever.

E2b adds `Store.fresh(lease)` as the engine's sole validity source. It is true through `validFor` after confirmation (default 10 seconds), false after expiry or a detected fence, and makes no bucket request. The engine verifies before reads and admission once freshness expires, including a duplicate id answered from memory. Page hashes in [`codec.ts`](../../../packages/akter/src/store/codec.ts) use synchronous SHA-256, so `Simulation` no longer patches global crypto. Its host-clock `TestClock` warning is disabled to keep host timing out of seed ordering.

The six engine-level scenarios in [`engine.ts`](../../../tooling/conformance/src/conformance/engine.ts) now run through the filesystem and S3 registrations beside these Store-only scenarios. [E2 recovery](e2-recovery.md) records restart with a pending timer, drain/handoff under load, build-matched refusal and recovery, ambiguous append, page/manifest interruption and SIGKILL recovery, with the boundary between filesystem results and MinIO/provider results.

Every segment carries a `build`: the runtime and its version, the engine and its version, platform, architecture and the ICU, Unicode and time-zone database versions, read from the running process, plus the application bundle digest and framework version the server passes as `build` (both empty until it does). [`build.test.ts`](../../../packages/akter/src/store/build.test.ts) checks the runtime fields on Bun and Node; Bun reports no time-zone database version, and its `process.versions.v8` names the Node version it emulates, so the engine version comes from `process.versions.webkit`.

`Store.check` is the probe that defines a supported bucket. It races concurrent create-once writers and concurrent compare-and-swap writers, checks that listings show completed creates and deletes, checks that twelve keys created out of order list in byte order and page correctly through `limit` and `startAfter`, checks that a plain `PUT` of identical bytes moves last-modified forward after a settle wait (two seconds by default, because S3 timestamps have one-second resolution), measures back-to-back writes to one key, and runs one batch delete. Each probe reports its verdict, a detail line and its measured numbers (`Probe.measured`, including `elapsedMillis`). `Store.checkS3` and `Store.checkFileSystem` run the same probe against a bucket or directory without opening a store there, so no `meta/store` is created. [`check.test.ts`](../../../packages/akter/src/store/check.test.ts) runs it against a bucket whose conditional create and compare-and-swap check and then write in two steps: exactly those two probes fail, and the same bucket with atomic writes passes. Running the race writers one at a time fails that test. It also runs the probe against a bucket that skips a plain `PUT` of bytes the key already holds, so the object keeps its first last-modified time: exactly the last-modified probe fails, and a bucket that refreshes it passes. A probe that writes different bytes the second time, or does not wait between the writes, passes that bucket and fails the test. A third scenario runs it against buckets that list newest-first, ignore `startAfter`, or ignore `limit`: exactly the ordered-listing probe fails on each, and a correct listing passes; a probe that lists once, or only checks that keys are present, passes all three and fails the test.

## The `akter storage check` command

[`check.test.ts`](../../../apps/cli/src/commands/storage/check.test.ts) runs `akter storage check` against a temporary directory and asserts the printed report, the JSON report, exit status 0, and that nothing exists outside `check/` afterwards. It runs the command with a probe that fails (a store whose writes to the rate-test key return 500) and asserts exit status 1, `FAIL` on exactly that probe, and a JSON report with `passed: false`. It asserts exit status 2 and no credential in the output for a missing target, both `--bucket` and `--directory`, an endpoint carrying credentials, an access key without its secret, a zero `--writers`, and a provider error that quotes the secret (printed as `[redacted]`). [`check.s3.test.ts`](../../../apps/cli/src/commands/storage/check.s3.test.ts) runs it against the MinIO bucket named by `TEST_S3_URL` with credentials from `AKTER_STORAGE_*` and from `AWS_*` plus flags, asserts exit status 0, all seven probes, a last-modified advance of at least a second, no objects left under the run's prefix (which also shows no `meta/store` was written), and no secret in stdout or stderr; with a wrong secret it asserts exit status 2 and no verdict. The S3 file runs in `apps/cli` `test:integration` (CI's `framework-integration` shard); `apps/cli` `test` leaves it out. The [support matrix](store-providers.md) records the passing runs.

## Adapter-specific evidence

The S3 adapter answers a `412` on a plain `PUT` with a failure that carries the status, so the page writer can resolve it, and `s3.test.ts` checks that against a stand-in server. It turns off the SDK's own retries, so every repeated write goes through the store's retry schedule, which reads a create-once write back to recognize its own. `s3.test.ts` also runs a local stand-in server that answers a conditional create with `412` and then drops the next request on that kept-alive connection without responding. MinIO RELEASE.2025-09-07 does this; RELEASE.2026-09-22 keeps the connection open. The test shows that the adapter sends a dropped read again exactly once, on a fresh connection, and never sends a write again. Removing the read resend, or resending writes too, fails the test.

The file-system adapter writes each object to a temporary file, fsyncs it, then links it into place for create-once or renames it for a plain put. A lease is a directory of numbered versions, and its etag is the version number. These guarantees hold on one host's local file system only. On a case-insensitive file system (macOS by default) two keys that differ only by case name one file; the store's own keys never differ only by case, and the listing-order probe uses names that do not.

## Packaging

[`pack.test.ts`](../../../.github/src/pack.test.ts) builds a consumer of `@rikalabs/akter/server` with Bun, without code splitting, for the Bun and Node targets. A server that composes only `Store.fileSystem` and `Store.memory` bundles no AWS or Smithy module, and one that composes `Store.s3` does, which shows the check can see the SDK. When `Store.s3` was a static member of the `Store` service class, the same filesystem-only build pulled in 111 AWS/Smithy modules for Bun and 41 for Node.

## Left to later milestones

The [storage contract](../contracts/06-storage.md) is a proposal; these parts of it belong to later milestones and are not met here:

- **E6 (history and garbage collection):** trim deletes covered segments once a checkpoint is `trimAfter` old; it does not yet wait for the retention recorded in `meta/store`, and no history archive is written before trim. `gc/` keys are accepted by the lease interface, but no collector exists.
- **E7 (operator commands):** `akter storage check` and the [support matrix](store-providers.md) exist, with MinIO as its only entry. `audit/<date>/<id>` belongs to the operator read commands (`inspect`, `log`, `snapshot`, `fork`, `replay`), which do not exist yet; nothing writes `audit/`, and the check does not.

Checkpoint fallback checks that a manifest decodes, matches its key and names only stored pages; it checks the existence of the pages the manifest names directly, not their digests or the pages they reference. A damaged page found later is the `PageCorrupt` defect.

## Not established

- No evidence for Cloudflare R2, Tigris or AWS S3; the [support matrix](store-providers.md) marks them "not established". The adapter maps AWS's `409` for a concurrent conditional write to `StorageUnavailable` from documentation, not from a test.
- MinIO runs as one node in one container. Distributed erasure sets, network partitions, real clock behavior and provider throttling are not exercised. The per-key write-rate probe records throttling but sets no bound. MinIO reports last-modified to the second, so the last-modified probe waits two seconds between its writes.
- The Store-only page/manifest scenario fails the manifest write. The E2b engine scenario interrupts a scope while that write is held, and its separate SIGKILL scenario kills a real owner process during command load; it does not place SIGKILL at the page/manifest boundary. The 30-second request timeout that bounds how late a paused owner's write can land is configured but not measured.
- With MinIO RELEASE.2025-09-07, many concurrent `412` responses can leave more than one dropped connection in the pool. A resent read can then meet a second one and surface `StorageUnavailable` to the store's retry schedule. This was seen once locally, in `Store.check`'s race probe.
- No throughput, latency or cost measurement.

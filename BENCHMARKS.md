# Akter benchmarks

This report measures Akter (formerly Durable Actors) and eight comparison configurations on the same cgroup-limited Daytona sandbox. It is a comparison of these single-node deployments and adapters, not a ranking of the vendors' managed services. In particular, local Cloudflare workerd does **not** run Cloudflare's production replication network, and Rivet's default state-saving policy does **not** acknowledge at the same durability boundary as the explicitly saved variant. Raw comparison records retain the system identifier `durable`; it denotes our framework, not a different competitor.

The clean comparison rounds are still being collected. No preliminary measurement below should be treated as a completed comparison. The final report will replace this notice with the repeat-round tables and their failure counts before publication.

## Why and what we measured

Durable Actors keeps actor state, receipts, events, and pending work in Postgres. The useful questions are how much that costs over plain database operations, how the actor and workflow alternatives behave under the same HTTP workload, and whether acknowledged operations survive interruptions without being applied twice. Actor wake time, whole-process restart time, workflow-start latency, and durable checkpoint cost answer different questions; they are not interchangeable.

The systems were Durable Actors, Rivet Actors with default saves, Rivet Actors with an awaited immediate save, Cloudflare Durable Objects on local workerd, Restate, Temporal, DBOS, a plain Postgres server, and a plain Redis server. Orleans and Akka were not run. They are architectural context, not measured competitors here.

All agent work, recovery of the old checkout, code edits, research, and repository tests ran on Dallen's Mac. The comparison load and the framework's internal benchmark suite ran on Daytona, not the Mac. The old worktree and scratch results were preserved outside the repository; the benchmark CLI, committed results/profiles, benchmark scripts, and Statements CI job were removed. This file is the consolidated repository artifact. No Markdown, document-link, or evidence linter was added.

## Hardware, isolation, and method

The primary Daytona sandbox ran Linux x86-64 on an AMD EPYC 9354P host, with Docker-in-Docker. Its outer cgroup allowed four CPUs (`cpu.max = 400000 100000`), 8 GiB RAM (`memory.max = 8589934592`), and a 10 GB filesystem. Every system's app, database, engine, worker, and HTTP front shared that allowance with the driver. Individual app/storage containers had limits of four CPUs and 8 GiB; these did **not** give each container four exclusive cores or 8 GiB independently of the outer limit. The driver had a one-CPU, 1 GiB limit. A separate two-CPU, 2 GiB sandbox was used only for debugging failures, not headline performance.

The internal harness's host probe reports 64 logical CPUs and 755.2 GiB RAM exposed by the underlying machine. Those are **not** the sandbox resources: the cgroup limits above are the available compute and memory for every result here. CPU percentages in internal results use one core as 100%, so a multi-core client/runtime can exceed 100% while the whole stack still shares four CPUs.

Systems ran serially. Compose projects and their volumes were removed between runs; images and build cache could be reused. Each comparison round used fresh state, not a fresh physical host. Round order was forward, reverse, then forward to expose some order effects. These are repeats on one sandbox, not three independent hosts. Daytona's quota does not establish exclusive physical cores or eliminate noisy neighbors. Linux load averages expose the host, not just the sandbox, and were recorded rather than represented as sandbox utilization.

Cases within a round are sequential on the same live deployment, not independent pristine fixtures. The one-key reads and open-loop cases follow the 10,000-key workload; they can reflect its retained metadata, capacity pressure, or unfinished work. The HTTP fronts do not uniformly propagate client cancellation, so an upstream SDK call can outlive a driver's timeout. A later case is therefore a post-churn observation, not proof of an isolated operation's best latency. Fresh-storage failure and memory rounds provide separate controls. Successful-case latency must not be generalized beyond this order and load history.

The final 10,000-key write and read tables use three additional isolated cohorts (`isolatedscale1`–`isolatedscale3`) for every system. The scale case starts on a fresh deployment, and each read case gets another fresh deployment with its own acknowledged setup writes. This removes the preceding hot/sequential actors from Akter's default 10,000-resident boundary and removes unfinished prior work from the read fixture. Setup results record expected, acknowledged, and failed keys. A setup timeout is an unknown write outcome, not evidence that an acknowledged state was lost. The earlier post-churn observations, including timeouts and zero-value reads after failed setup, remain diagnostic rather than silently becoming clean steady-state samples.

The common workload was an HTTP counter increment, a counter read, and an append/read log. Durable Actors used its real served actor routes; other adapters exposed the same logical operations behind their HTTP fronts. A counter write acknowledged only after the adapter's chosen persistence boundary. Requests carried unique command/idempotency IDs. Native deduplication was used where available; no deduplication table was invented for a system that lacked it. The baselines deliberately omit actor lifecycle, receipts, security, events, outbox, and workflow facilities.

Closed-loop latency times each actual request; it suffers coordinated omission during stalls. Open-loop latency starts at the intended schedule, so it includes scheduler lag and queueing, but a one-CPU driver can itself bottleneck. Open-loop achieved rate includes the drain after the 20-second schedule. Failed requests and dropped submissions do not become successful latency samples and must be read alongside the percentiles. Prepopulation failures can invalidate the premise of a spread workload even if the later measured requests succeed.

Percentiles are nearest-rank sample percentiles. Repeated-round summaries use the median of each round's statistic, with the minimum–maximum range and the number of complete rounds; they are not pooled request percentiles or confidence intervals. Most competitors use `clean2`, `clean3`, and `correctedperf`. Rivet variants use `correctedperf`, `verifiedperf2`, and `verifiedperf3`, after fixing our handler's return-value snapshot around its await. Akter uses `correctedperf`, `currentperf2`, and `currentperf3`, rerun after the package rename and concurrent main fixes so its headline samples all use the same current snapshot. Earlier framework/Rivet rounds remain diagnostic. All selected rounds use the corrected scan/value checks and scheduled-arrival driver. The final one-key write controls also reject repeated counter results under distinct command IDs. Small differences inside the range are not evidence of superiority. The external driver has a 180-second case deadline (420 seconds for failure drills); an aborted case is missing evidence, never a zero, a pass, or a latency estimate.

### Memory and restart measurements

Memory comes from Docker's per-container memory usage, not a language heap profile. It includes the relevant engine/storage processes. The first-round before/after delta follows the performance phases and then 10,000 additional counter creations, so it also reflects receipts, database caches, and accumulated work. The corrective memory round runs this phase alone on fresh storage. Dividing either delta by 10,000 is not a pure per-actor object size. The scan uses the same run identifier as populate; a failed populate or scan cannot establish the cost of reading 10,000 existing identities. Before the corrective sleepy population, the earlier counter population is left idle for 110 seconds rather than deliberately overlapping 20,000 residents against Durable Actors' default 10,000-resident cap. The sleepy variant records memory after population, after approximately 3 s, and after approximately 33 s, where the adapter supports it. Population errors still invalidate any claim about 10,000 successfully created sleepy actors.

Whole-process restart is measured five times per round: SIGKILL the app/worker, wait one second, start the container, and retry an existing counter command until the first acknowledgement. The reported timer starts at `docker start`, so it excludes the intentional one-second downtime. It includes starting the container, initialization, retries, and a command. It is **not** isolate cold start, image download time, a managed service scale-to-zero wake, or time since SIGKILL. Initial Compose build-to-health time is recorded separately and includes setup/build artifacts; it is not compared as actor cold start.

### Failure drills

The final drills run 16 callers against 256 append logs for 100 seconds. Four failures are injected at 15, 35, 55, and 75 seconds. App and storage drills send SIGKILL and restart the target; a supervisor also restarts exited dependent containers. The partition drill forcibly disconnects the app's Docker network, kills it, reconnects it, and restarts it. This is a vanished-container/network-removal drill, not a complete model of a WAN partition or split-brain cluster. Earlier 32-key diagnostics are identified separately: fast runs can reach the framework's default 64 KiB state limit per log, which confounds the intended recovery workload. We increased the number of logs for every comparator, not the framework's production limit.

Each logical append retains its ID and command key through retries. A request times out after 5 s, waits 100 ms, and retries for up to 90 s. The driver then reads every log and counts acknowledged IDs missing from storage, repeated IDs, unknown outcomes, unknown IDs that were applied, and verification read failures. Lost acknowledgement is the reverse direction: a command can commit without a response, so absence of native deduplication can turn a same-ID retry into another append. Duplicate counts are therefore a feature comparison as well as a failure observation.

A verification read failure means loss and duplication cannot be established for that log. SIGKILL preserves the host's page cache; even zero lost acknowledgements does not prove power-loss durability, replication, multi-region failover, or backup recovery. All storage is single-node in this comparison.

The initial driver counted every acknowledged ID absent from the successfully read logs as `lostAcknowledged`, even when one log was unreadable. Those raw missing-ID counts are not confirmed loss if `readErrors` is nonzero. The revised failure verifier retains that raw count and separately records confirmed loss, acknowledged IDs whose log could not be verified, unverified keys, and IDs found under the wrong key. A duplicate count with unreadable logs is a lower bound. No row with failed verification is called clean.

Durable Actors, Rivet, and Restate append by replacing an array-valued state field. Temporal keeps the array in workflow state and carries it into continue-as-new; its approximately 2 MiB payload ceiling bounds this adapter. Cloudflare, DBOS, Postgres, and Redis append to storage rows/lists. Counter workloads are the clearer performance comparison; the growing-log workload is for checking acknowledgement, retry, and recovery semantics, not establishing a constant-cost universal append rate.

Our original Rivet immediate-save handler read live state after awaiting the save. That could return other calls' changes if mutations overlap across the await. We changed the adapter to capture the new value/length immediately after its mutation, before the save wait. A controlled JavaScript reproduction yielded one unique reply for 64 increments with the original shape and 64 unique replies with the corrected shape, while both final counters were 64. This is an adapter precaution, not a claim that Rivet always interleaves those actions. The selected Rivet cohorts rerun with captured replies; the final one-key driver also rejects repeated results. Capturing a return value does not provide native deduplication or a durable result receipt.

Rivet's default-save adapter lost an acknowledged write in three immediate-after-reply SIGKILL smoke drills. The immediate-save variant awaits a stronger API boundary, but that is not proof of durability under every failure. Its first completed clean round observed zero lost acknowledgements in app kills, but 202 missing acknowledged IDs after engine kills (41,756 acknowledgements, zero verification-read errors); duplicates were 53 and 38 respectively, with no native deduplication. App logs around the engine restarts reported failed actor-state persistence to SQLite, closed transaction coordinators, and disk I/O errors. That workload followed a capacity-stressed performance/memory phase. On the fresh-storage repeat, app and partition kills again lost no acknowledgements, but the engine drill had one unreadable log, nine unknown outcomes, and 266 apparent missing acknowledged IDs; those 266 are **not confirmed loss** because verification was incomplete. These are observations of this pinned single-node adapter, not claims about all Rivet production backends. Local workerd passed immediate SIGKILL smoke drills, but its SQLite VFS fsync defaults were not independently established, and container SIGKILL cannot establish power-loss behavior.

The final verifier-aware fresh engine repeat separated those categories: Rivet saved had zero confirmed missing IDs among readable logs, 149 acknowledged IDs in one unreadable log, 12 unknown outcomes (10 found applied), and 57 repeated IDs. Its fresh app repeat verified all 17,893 acknowledgements with no loss but 66 repeated IDs. Rivet default's app repeat confirmed 844 missing acknowledgements out of 20,187 with complete reads, whereas its engine repeat had zero confirmed missing among readable logs and 208 acknowledged IDs left unverifiable. Incomplete engine verification is not a durability pass, and apparent omissions are not promoted into confirmed loss.

Relevant adapter semantics are documented by [Rivet state](https://rivet.dev/docs/actors/state), [Cloudflare lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), [Restate server](https://docs.restate.dev/server/overview), [Temporal entity workflows](https://docs.temporal.io/design-patterns/entity-workflow), [Temporal message handling](https://docs.temporal.io/handling-messages), [DBOS workflow IDs](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial), [Postgres synchronous commit](https://www.postgresql.org/docs/18/wal-async-commit.html), and [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). Hosted production configurations differ from these single-node development-style deployments.

The first Temporal hot-key case observed 181 request timeouts and only 5.4 successful responses/s, versus 118.4/s sequentially and 282.6/s over 10,000 keys. This is not representative of all Temporal workloads. The pinned [server defaults](https://github.com/temporalio/temporal/blob/v1.32.0/common/dynamicconfig/constants.go) allow only ten admitted-but-incomplete Updates per workflow, whereas the hot case sends 64 callers to one entity workflow. Captured worker logs show repeated `Workflow task not found` warnings for the same workflow run during that window, consistent with admission/retry contention; the retained server log does not cover the hot window, so the precise server-side causal chain is not established by these logs. The collapse starts before continue-as-new is reached. We did not raise the limit or switch to Signals: doing so would either tune the deployment or change the completed-response acknowledgement contract. Report the failed requests beside successful latency samples, not just their deceptively low p50.

## Bugs found and fixed

### A vanished runner left Postgres sessions holding shard locks

The prior investigation separately reproduced a partition-then-kill failure with dead-runner sessions visible in `pg_stat_activity`: a disappeared runner can leave its TCP sessions open without FIN/RST, and Postgres still holds that runner's session advisory locks and any open transaction's row locks. A lease or a newly started process does not make those sessions disappear. The original full drill also had 16 unknown outcomes and HTTP 500 defects, but those counts alone do **not** establish this root cause. The later stable-Effect 32-key drill reproduced 16 unknown outcomes with explicit `State exceeds policy.maxStateBytes` logs; that run hit the legitimate 64 KiB quota instead. We do not attribute every unknown outcome to stale sessions.

`Database.postgres` now requests server TCP probes on all three pools: 5 s idle, 2 s between probes, 3 failed probes. Caller `startupParameters`, `startupOptions`, and URL options retain precedence; replica overrides are independent. The defaults are prepended as startup options so they do not silently override a caller's existing `-c` setting. Settings of `0` use OS defaults. Unix sockets ignore TCP probes. Approximately 11 seconds is a probe budget, **not** a recovery SLO; scheduling, shard acquisition, activation, and backoff add time. Pooler and Neki compatibility were not established by these runs.

The real-Postgres regression tests inspect turn, off-turn, and replica sessions and reject an implementation that configures only the query pool, overwrites caller settings, or ignores URL/startup-option overrides. The failure drill tests the operational consequence separately from the settings test.

A controlled Docker/Postgres reproduction on the Mac independently checked the session-lock mechanism without measuring performance: two idle clients acquired different advisory locks, then their networks were removed and their containers killed. After 30 seconds the default client's idle session/lock remained and the client using the new probe settings was gone. A separate control that was still executing `pg_sleep` retained locks even with probes: a running backend must observe the closed socket before it can clean up. TCP settings therefore do not bound every long-running SQL statement's lock lifetime. The benchmark's short turns and final failure drills must be judged separately from this diagnostic.

### Postgres startup/shutdown errors became deterministic actor defects

During a real database restart, Postgres replied `57P03` (not accepting connections yet). The driver represented it as an unknown, non-retryable SQL error, so the runtime returned a deterministic actor defect instead of a retryable unavailability result.

The turn retry classifier now also recognizes `57P01`–`57P03` (shutdown, crash shutdown, startup/recovery refusal) and `53000`–`53300` (resource, disk, memory, connection exhaustion). It restarts the activation and answers the attempt with retryable `ActorUnavailable`; the caller retries the original command ID, and a committed receipt still resolves an unknown commit. This does not retry arbitrary SQLSTATE prefixes: `57P04` (database dropped), `57P05` (idle-session timeout), `53400` (configuration limit), and ordinary statement errors are not newly classified as transient. Disk/resource exhaustion can require an operator; retries do not create disk space or guarantee recovery before the delivery deadline.

The regression test injects a shutdown error immediately before commit, requires the handler to run twice, and independently asserts one committed total and one receipt. Its deterministic-error control requires rollback, no receipt, and no retry. Classification tests cover both sides of the permanent/transient boundary. These reject a fix that merely returns a nicer HTTP status or commits a duplicate state transition.

### Effect Bun server startup readiness

The failure logs also contain brief `404 not found` responses after the Bun server starts listening but before its routes install. This is upstream server startup behavior, not a durable-state loss. Gate production traffic on `GET /ready`; an open listening port alone is not readiness. The benchmark's cold/restart client records retries rather than hiding these responses. No workaround was added to framework production routing solely to improve the benchmark.

## Invalid and diagnostic runs

The original Durable Actors and Rivet memory scans used a different run identifier from populate. Rivet's scan therefore created another population rather than reading the existing one and stalled with `actor_ready_timeout` / `route_resolve_query_timeout` while its engine consumed the sandbox's CPU quota. Those scans are invalid. The first Rivet-saved performance run also overlapped a leftover Rivet engine; it is not a clean comparison. The old queue and orphaned driver were stopped, the engine removed, and the full comparison restarted serially with bounded drivers and cleanup between systems.

The debug partition queue was initially stuck because `pgrep -f` matched the queue's own shell command. Its shell was stopped and the drill executed directly. Retrieved post-fix debug app, storage, and partition drills observed 100,841 acknowledged commands, zero lost acknowledged IDs, zero duplicate IDs, zero unknown outcomes, and zero verification read failures. These were on the smaller debugging sandbox and the pre-stable Effect dependency snapshot; they are regression diagnostics, not performance headline data.

The old local unit-suite log is not a passing verification record. The recovered changes were installed on current main and rerun with stable Effect. Tests and benchmarks answer different questions: repository tests on the Mac establish the contracts they exercise, not clean-hardware latency.

The first matched-ID memory scan still reported an incorrect sum because its concurrent driver workers used `sum += await read()`. JavaScript reads the old accumulator before the await and overwrites other workers' additions when each read finishes. A minimal reproduction produced 100 rather than the expected 6,400; awaiting the value first and then adding produced exactly 6,400. This was a benchmark-driver race, not evidence of lost actor state. The corrected scan also checks each read against the independently expected value of 1. Earlier scan totals are invalid; rerun them rather than crediting their successful HTTP responses as a state-integrity check.

The first driver deadline relied on a subprocess option that did not stop the running Docker client/container. A later Rivet scan exceeded its intended budget and had to be terminated. Subsequent drivers use an explicit timer, kill the client, and remove its named container; incomplete cases remain errors in the raw record. A successful orchestrator exit alone does not mean every case completed.

The original open-loop scheduler could dispatch up to 1 ms before an intended arrival because it slept only when more than 1 ms remained. That biases sub-millisecond scheduled-arrival latency. The selected rounds instead sleep for the ceiling of every positive remaining delay and identify the driver revision in each record. The earlier open-loop curves are diagnostic, not headline latency samples.

Two internal-suite timeouts required fixture/budget corrections. The full cron scenario performs three 100,000-actor drains for each of 1, 2, and 4 runners, and its own drain wait permits 15 minutes per round. A 15-minute wrapper for the entire scenario was therefore not an adequate budget. Its retry keeps every actor count and all three repeats, splits the runner cohorts, and allows 45 minutes per cohort. The original aborted scenario has no raw completed-case JSON and is not reported as a pass.

The original held-turn batching fixture minted the queued commands' IDs only after opening the held transaction. ID minting reads the database clock, so on one-connection PGlite those calls waited for the held turn's connection while the held turn waited for their arrival: the fixture created the deadlock. The corrected fixture pre-mints each round's IDs before opening the gate, matching the existing conformance tests, and then attaches them to the queued calls. The full 32-command and 1,024-reducer cases retain their operation counts and are rerun on both Postgres and PGlite. The corrected whole-round timing includes that pre-minting; the timed-out original PGlite result remains unknown, not a fabricated latency or framework fix.

## Interpretation limits

The plain baselines omit substantial guarantees, and the actors/workflow engines provide different ones. A lower-latency counter does not imply equivalent retries, transaction scopes, authorization, outbox delivery, workflow history, connection hibernation, or multi-region placement. Growing-log append implementations also differ: storing an entire JSON array makes the operation grow with history, whereas an SQL row insert or Redis append does not. Failure-drill throughput is therefore not a steady-state counter benchmark.

We did not run Cloudflare's network, Temporal Cloud, hosted Restate, Rivet FoundationDB, multi-region replication, WAN RTT, paid serverless wake orchestration, power loss, a dedicated-host study, or Neki. No provider guarantee follows from a local substitute. Durable Actors may lose on isolate cold start, resident memory, and managed edge/multi-region placement; this report must not imply those advantages from same-host Postgres timings. A short idle-wake test does not establish scale-to-zero: durable timers/jobs still need a runner/provider to wake them.

The final result tables, internal suite results, and repository verification record are pending the active clean runs. Missing, failed, or aborted cases will remain explicitly unknown rather than being converted to successful measurements.

### Internal Akter evaluations on the sandbox

The retired internal suite is run from an external source bundle for the final measurements, not restored as repository tooling. Each of its 37 scenarios gets a separate process and result directory, on Postgres and PGlite, with the full profile. Scenarios that support multi-runner configurations also run with 1, 2, and 4 in-process runners on the same four-CPU sandbox; this is not four separate hosts or CPUs per runner. Every measured case creates its own runtime/database through the suite's fixture boundary. Internal timings are in-process public-API calls unless a scenario explicitly serves HTTP, so they are kept separate from the head-to-head HTTP table.

The wrapper gives each scenario 15 minutes, records exit status and timeout separately, and continues after a failure. The unmodified harness writes raw case percentiles, parameters, statement/round-trip counts, CPU, and available memory/storage details only after a scenario completes; an aborted scenario is unknown, not a set of fabricated raw measurements reconstructed from its log. The scenario list covers turns/batching, cold activation and process start, queries and replay, state size, events, 1k/10k/100k identities, resident/retained heap, stored overhead, outbox, owned rows, effect round trips and concurrency, multi-runner/relay/singleton recovery, blobs and content, reducers, capacity, inspection, retention, HTTP, subscriptions, workflows, connections, progress, SSE, compatibility checks, minting, cron, embedded PGlite, RLS, placement, and watched queries. Neki and provider behavior are not inferred from these backends.
